# 文档协作编写工作流

此技能提供结构化工作流，引导用户完成协作文档创建。作为主动引导者，带领用户经历三个阶段：上下文收集、精炼与结构化、读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到编写文档："写个文档"、"起草提案"、"创建规范"、"写一下"
- 用户提到特定文档类型："PRD"、"设计文档"、"决策文档"、"RFC"
- 用户似乎正在开始一项重要的写作任务

**初始提议：**
向用户提供协作编写文档的结构化工作流。解释三个阶段：

1. **上下文收集**：用户提供所有相关上下文，同时 Claude 提出澄清性问题
2. **精炼与结构化**：通过头脑风暴和编辑迭代构建每个部分
3. **读者测试**：使用全新的 Claude（无上下文）测试文档，在他人阅读之前发现盲点

解释这种方法有助于确保文档在他人的阅读体验中表现良好（包括当他们将其粘贴到 Claude 中时）。询问他们是否想尝试此工作流还是偏好自由形式。

如果用户拒绝，按自由形式工作。如果用户接受，进入阶段 1。

## 阶段 1：上下文收集

**目标：** 弥合用户所知与 Claude 所知之间的差距，为后续的智能引导奠定基础。

### 初始问题

首先向用户询问关于文档的元上下文：

1. 这是什么类型的文档？（例如，技术规范、决策文档、提案）
2. 主要受众是谁？
3. 读者阅读后期望产生什么影响？
4. 是否有模板或特定格式需要遵循？
5. 还有其他需要了解的约束或上下文吗？

告知他们可以使用简写或任何对自己最方便的方式来倾倒信息。

**如果用户提供了模板或提到文档类型：**
- 询问他们是否有模板文档可以分享
- 如果他们提供了共享文档的链接，使用相应的集成来获取
- 如果他们提供了文件，读取它

**如果用户提到编辑现有的共享文档：**
- 使用相应的集成读取当前状态
- 检查没有 alt 文本的图片
- 如果存在没有 alt 文本的图片，解释当其他人使用 Claude 理解文档时，Claude 将无法看到这些图片。询问他们是否想生成 alt 文本。如果是，请他们将每张图片粘贴到对话中以生成描述性 alt 文本。

### 信息倾倒

初始问题回答后，鼓励用户倾倒他们所有的上下文。请求以下信息：
- 项目/问题的背景
- 相关的团队讨论或共享文档
- 为什么不使用替代方案
- 组织上下文（团队动态、过往事件、政治因素）
- 时间压力或约束
- 技术架构或依赖
- 利益相关者的关切

建议他们不必担心组织信息——全部倾倒出来即可。提供多种提供上下文的方式：
- 意识流式信息倾倒
- 指向团队频道或线程供阅读
- 链接到共享文档

**如果集成可用**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），提及可以使用这些集成直接拉取上下文。

**如果未检测到集成且在 Claude.ai 或 Claude 应用中：** 建议他们可以在 Claude 设置中启用连接器，以允许直接从消息应用和文档存储中拉取上下文。

告知他们在完成初始倾倒后将提出澄清性问题。

**在上下文收集期间：**

- 如果用户提到团队频道或共享文档：
  - 如果集成可用：告知他们将立即读取内容，然后使用相应的集成
  - 如果集成不可用：解释缺乏访问权限。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到未知的项目/实体：
  - 询问是否应搜索已连接的工具以了解更多信息
  - 等待用户确认后再搜索

- 随着用户提供上下文，跟踪已了解和尚不清楚的内容

**提出澄清性问题：**

当用户表示已完成初始倾倒（或在提供大量上下文后），提出澄清性问题以确保理解：

根据上下文中的空白生成 5-10 个编号问题。

告知他们可以使用简写回答（例如，"1: 是的，2: 见 #channel，3: 不行因为向后兼容"），链接更多文档，指向要阅读的频道，或继续倾倒信息。选择对他们最高效的方式。

**退出条件：**
当问题显示出理解时——当可以询问边缘情况和权衡而无需解释基础内容时——说明已收集了足够的上下文。

**过渡：**
询问他们在此阶段是否还有更多上下文要提供，还是该开始起草文档了。

如果用户想添加更多内容，让他们继续。准备好后，进入阶段 2。

## 阶段 2：精炼与结构化

**目标：** 通过头脑风暴、筛选和迭代精炼逐节构建文档。

**给用户的说明：**
解释文档将逐节构建。对于每个部分：
1. 将就应包含的内容提出澄清性问题
2. 将进行 5-20 个选项的头脑风暴
3. 用户将指示保留/删除/合并哪些内容
4. 将起草该部分
5. 将通过精确编辑进行精炼

从未知内容最多的部分开始（通常是核心决策/提案），然后处理其余部分。

**部分排序：**

如果文档结构清晰：
询问他们想从哪个部分开始。

建议从未知内容最多的部分开始。对于决策文档，通常是核心提案。对于规范，通常是技术方法。总结部分最好留到最后。

如果用户不知道需要哪些部分：
根据文档类型和模板，建议 3-5 个适合该文档类型的部分。

询问此结构是否可行，还是他们想调整。

**结构确定后：**

创建初始文档结构，所有部分使用占位文本。

**如果可以使用制品：**
使用 `create_file` 创建制品。这为 Claude 和用户提供了可操作的骨架。

告知他们将创建包含所有部分标题和占位文本的初始结构。

创建包含所有部分标题和简短占位文本（如"[待编写]"或"[此处填写内容]"）的制品。

提供骨架链接并表示该开始填充每个部分了。

**如果无法使用制品：**
在工作目录中创建 Markdown 文件。适当命名（例如，`decision-doc.md`、`technical-spec.md`）。

告知他们将创建包含所有部分标题和占位文本的初始结构。

创建包含所有部分标题和占位文本的文件。

确认文件已创建并表示该开始填充每个部分了。

**对于每个部分：**

### 步骤 1：澄清性问题

宣布将开始 [部分名称] 部分的工作。提出 5-10 个关于应包含内容的澄清性问题：

根据上下文和部分目的生成 5-10 个具体问题。

告知他们可以使用简写回答或仅指出需要涵盖的重点。

### 步骤 2：头脑风暴

对于 [部分名称] 部分，头脑风暴可能包含的 [5-20] 个内容，视部分的复杂度而定。寻找：
- 可能被遗忘的已分享上下文
- 尚未提及的角度或考量

根据部分复杂度生成 5-20 个编号选项。最后，提供如果他们想要更多选项则继续头脑风暴的服务。

### 步骤 3：筛选

询问应保留、删除或合并哪些要点。请求简短的理由以帮助了解下一部分的优先级。

提供示例：
- "保留 1、4、7、9"
- "删除 3（与 1 重复）"
- "删除 6（受众已经知道这些）"
- "合并 11 和 12"

**如果用户给出自由形式的反馈**（例如，"看起来不错"或"我喜欢大部分但……"）而非编号选择，提取他们的偏好并继续。解析他们想保留/删除/更改的内容并应用。

### 步骤 4：空白检查

根据他们的选择，询问 [部分名称] 部分是否遗漏了重要内容。

### 步骤 5：起草

使用 `str_replace` 将该部分的占位文本替换为实际的起草内容。

宣布将根据他们的选择起草 [部分名称] 部分。

**如果使用制品：**
起草后，提供制品链接。

请他们通读并指出需要更改的内容。注意，具体的反馈有助于后续部分的学习。

**如果使用文件（无制品）：**
起草后，确认完成。

告知他们 [部分名称] 部分已在 [文件名] 中起草。请他们通读并指出需要更改的内容。注意，具体的反馈有助于后续部分的学习。

**给用户的关键说明（在起草第一部分时包含）：**
提供说明：不要直接编辑文档，而是指出需要更改的内容。这有助于学习他们的风格以应用于后续部分。例如："删除 X 要点——已被 Y 涵盖"或"让第三段更简洁"。

### 步骤 6：迭代精炼

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（永远不要重新打印整个文档）
- **如果使用制品：** 每次编辑后提供制品链接
- **如果使用文件：** 仅确认编辑完成
- 如果用户直接编辑文档并要求阅读：在心里记录他们所做的更改，并在后续部分中记住这些（这显示了他们的偏好）

**持续迭代**直到用户对该部分满意。

### 质量检查

在连续 3 次迭代没有实质性更改后，询问是否可以在不丢失重要信息的情况下删除某些内容。

当部分完成时，确认 [部分名称] 已完成。询问是否准备好进入下一部分。

**对所有部分重复此流程。**

### 接近完成

当接近完成（80%+ 的部分已完成）时，宣布打算重新阅读整个文档并检查：
- 各部分之间的流畅性和一致性
- 冗余或矛盾
- 任何感觉像"敷衍"或通用填充的内容
- 每句话是否有分量

阅读整个文档并提供反馈。

**当所有部分都已起草和精炼后：**
宣布所有部分已起草。表示打算最后一次审查完整文档。

审查整体连贯性、流畅性和完整性。

提供任何最终建议。

询问是否准备好进入读者测试，还是想进一步精炼。

## 阶段 3：读者测试

**目标：** 使用全新的 Claude（无上下文泄露）测试文档，验证它对读者是否有效。

**给用户的说明：**
解释现在将测试文档是否真正对读者有效。这可以发现盲点——对作者来说有意义但可能让他人困惑的内容。

### 测试方法

**如果可以使用子代理（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 步骤 1：预测读者问题

宣布将预测读者在尝试发现此文档时可能提出的问题。

生成 5-10 个读者实际会提出的问题。

### 步骤 2：使用子代理测试

宣布将使用全新的 Claude 实例（无本次对话的上下文）测试这些问题。

对于每个问题，调用子代理，仅提供文档内容和问题。

总结 Reader Claude 在每个问题上回答正确/错误的情况。

### 步骤 3：运行额外检查

宣布将执行额外检查。

调用子代理检查歧义、错误假设和矛盾。

总结发现的任何问题。

### 步骤 4：报告并修复

如果发现问题：
报告 Reader Claude 在特定问题上遇到困难。

列出具体问题。

表示打算修复这些空白。

回到问题部分的精炼阶段。

---

**如果无法使用子代理（例如 claude.ai 网页界面）：**

用户需要手动进行测试。

### 步骤 1：预测读者问题

询问人们在尝试发现此文档时可能会问什么问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者实际会提出的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开全新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用启用了连接器的共享文档平台，提供链接）
3. 向 Reader Claude 提出生成的问题

对于每个问题，指示 Reader Claude 提供：
- 答案
- 是否有歧义或不清晰的内容
- 文档假设读者已具备哪些知识/上下文

检查 Reader Claude 是否给出正确答案或误解了任何内容。

### 步骤 3：额外检查

同时询问 Reader Claude：
- "文档中什么内容可能对读者来说有歧义或不清晰？"
- "文档假设读者已具备哪些知识或上下文？"
- "是否存在内部矛盾或不一致？"

### 步骤 4：根据结果迭代

询问 Reader Claude 在哪些问题上回答错误或遇到困难。表示打算修复这些空白。

回到问题部分的精炼阶段。

---

### 退出条件（两种方法通用）

当 Reader Claude 始终正确回答问题且未发现新的空白或歧义时，文档就准备好了。

## 最终审查

当读者测试通过后：
宣布文档已通过 Reader Claude 测试。在完成之前：

1. 建议他们自己进行最终通读——他们拥有此文档并对其质量负责
2. 建议仔细检查任何事实、链接或技术细节
3. 请他们验证文档是否达到了期望的影响

询问他们是否想再做一次审查，还是工作已完成。

**如果用户想要最终审查，提供审查。否则：**
宣布文档完成。提供一些最终建议：
- 考虑在附录中链接此对话，以便读者了解文档的开发过程
- 使用附录提供深度而不使主文档膨胀
- 根据真实读者的反馈更新文档

## 有效引导的技巧

**语气：**
- 直接且程序化
- 在影响用户行为时简要解释理由
- 不要试图"推销"方法——直接执行

**处理偏差：**
- 如果用户想跳过某个阶段：询问他们是否想跳过并以自由形式编写
- 如果用户看起来感到沮丧：承认这比预期花费了更长时间。建议加速的方法
- 始终给予用户调整流程的自主权

**上下文管理：**
- 在整个过程中，如果缺少所提及内容的上下文，主动询问
- 不要让空白积累——在出现时解决

**制品管理：**
- 使用 `create_file` 起草完整部分
- 使用 `str_replace` 进行所有编辑
- 每次更改后提供制品链接
- 永远不要使用制品存放头脑风暴列表——那只是对话

**质量优于速度：**
- 不要匆忙通过各阶段
- 每次迭代都应带来有意义的改进
- 目标是创建真正对读者有效的文档
