# 完成定义（Definition of Done）

一项贯穿整个项目的固定标准，每个变更在算作完成之前都必须达到该标准。与验收标准（Acceptance Criteria）不同——验收标准因任务而异，回答的是"我们做了正确的事吗？"——完成定义每次都相同，回答的是"这达到了我们的完成标准吗？"。可将其用作 `planning-and-task-breakdown`、`incremental-implementation` 和 `shipping-and-launch` 中的最终关卡。

## 完成定义 vs. 验收标准

| | 验收标准（Acceptance Criteria） | 完成定义（Definition of Done） |
|---|---|---|
| 适用范围 | 针对单一任务或规格 | 适用于每一个增量 |
| 变化情况 | 每项内容各不相同 | 固定不变，重复使用 |
| 回答的问题 | "我们做了*这件事*吗？" | "它*准备好了吗*？" |
| 定义者 | 在规划任务时定义 | 为项目一次性定义 |
| 示例 | "用户可以通过邮件链接重置密码" | "测试通过，无回归，文档已更新" |

两者相辅相成。一个任务只有在**其**验收标准得到满足**且**固定的完成定义也被满足时，才算真正完成。跳过其中任何一项，都会导致工作看似完成实则不然。

## 固定检查清单

在宣布任何变更完成之前，都应应用此清单。

### 正确性（Correctness）
- [ ] 任务的所有验收标准均已满足
- [ ] 代码能够运行且行为符合预期，需通过运行时验证，而不仅仅是编译或类型检查通过
- [ ] 新行为有对应的测试覆盖，且这些测试在没有该变更时会失败、有该变更时通过
- [ ] 现有测试仍然通过；未引入任何回归
- [ ] 边界情况和错误路径已得到处理，而不仅仅是正常路径

### 质量（Quality）
- [ ] 代码通过命名和结构表达意图；无需注释来解释它*做了什么*
- [ ] 无重复的业务逻辑
- [ ] 无死代码、调试输出或被注释掉的代码块残留
- [ ] 变更范围仅限于当前任务；未混入无关的重构
- [ ] Lint 和格式化检查通过

这些条目背后的深度内容见 `code-review-and-quality`（五轴评审）和 `code-simplification`（在不改变行为的前提下降低复杂度）。

### 集成（Integration）
- [ ] 变更在整体系统中可正常工作，而不仅仅在隔离环境下
- [ ] 数据库迁移、配置变更和功能开关均已纳入考虑
- [ ] 对于任何公共接口或 API 变更，已考虑向后兼容性

### 文档（Documentation）
- [ ] 公共接口、API 及面向用户的行为已有文档说明
- [ ] 值得保留的架构决策已被记录（参见 `documentation-and-adrs`）
- [ ] 文档以 timeless 的语言描述当前状态，而非变更历史

### 发布就绪度（Ship-readiness）
- [ ] 已对涉及不可信输入、身份验证或数据处理的部分进行安全影响评审（参见 `security-and-hardening`）
- [ ] 新的关键路径已具备可观测性（日志、指标、追踪）（参见 `observability-and-instrumentation`）
- [ ] 对任何有风险的内容存在回滚方案（参见 `shipping-and-launch`）
- [ ] 人工已在合并或部署前完成评审并批准

## 如何应用

- **按任务**：在勾选任务完成之前，确认正确性和质量部分。
- **按功能**：在认为功能完成之前，确认集成和文档部分。
- **按发布**：完整检查清单是最低要求；`shipping-and-launch` 在此基础上增加了部署相关的关卡。

为项目定制一次清单，然后保持不变地重复使用。如果每个 Sprint 都要重新协商的完成定义，那就不是真正的完成定义。

## 危险信号

- "做完了，只是还没运行过"：未经验证的工作不算完成。
- 将"测试通过"当作完成的同义词，却跳过了文档、回归测试或运行时验证。
- 根据截止日期压力采用不同的标准。
- 将验收标准视为全部标准，缺乏固定的质量底线。
- 在需要人工评审的变更上，尚未进行人工评审就宣布"完成"。
