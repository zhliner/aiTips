# 废弃与迁移（Deprecation and Migration）

## 概述

代码是负债，而非资产。每一行代码都有持续的维护成本——需要修复 bug、更新依赖、应用安全补丁，以及帮助新工程师上手。废弃（deprecation）是一门移除不再产生价值的代码的纪律，而迁移（migration）是将用户从旧系统安全过渡到新系统的过程。

大多数工程团队擅长构建新事物，但很少擅长移除旧事物。本技能正是为弥补这一差距而设计。

## 适用场景

- 用新系统、API 或库替换旧的
- 下线不再需要的功能
- 合并重复的实现
- 移除没人负责但人人都依赖的死代码
- 规划新系统的生命周期（废弃规划从设计阶段就应开始）
- 决定是维护遗留系统还是投入迁移

## 核心原则

### 代码是负债

每一行代码都有持续的成本：它需要测试、文档、安全补丁、依赖更新，以及给所有接触它的工程师带来认知负担。代码的价值在于它提供的功能，而非代码本身。当同样的功能可以用更少的代码、更低的复杂度或更好的抽象来实现时——旧代码就应该被移除。

### Hyrum's Law 使移除变得困难

当用户足够多时，每一个可观察到的行为都会被依赖——包括 bug、时序特性和未记录的副作用。这就是为什么废弃需要主动迁移，而不仅仅是发布公告。当用户依赖了替代品没有复制的行为时，他们无法"直接切换"。

### 废弃规划从设计阶段开始

构建新系统时，要问："三年后我们会如何移除它？"拥有清晰接口、feature flag 和最小暴露面的系统，比到处泄露实现细节的系统更容易废弃。

## 废弃决策

在废弃任何事物之前，先回答这些问题：

```
1. 这个系统是否仍在提供独特的价值？
   → 如果是，继续维护。如果不是，继续下一步。

2. 有多少用户/消费者依赖它？
   → 量化迁移范围。

3. 替代品是否已存在？
   → 如果没有，先构建替代品。不要在没有替代方案的情况下废弃。

4. 每个消费者的迁移成本是多少？
   → 如果可以轻松自动化，就去做。如果需要大量手动工作，将其与维护成本进行权衡。

5. 不废弃的持续维护成本是多少？
   → 安全风险、工程师时间、复杂度带来的机会成本。
```

## 强制废弃与建议废弃

| 类型 | 适用场景 | 机制 |
|------|----------|------|
| **建议废弃（Advisory）** | 迁移是可选的，旧系统仍然稳定 | 警告、文档、引导。用户按自己的时间表迁移。 |
| **强制废弃（Compulsory）** | 旧系统存在安全问题、阻碍进展或维护成本不可持续 | 硬性截止日期。旧系统将在 X 日期前移除。提供迁移工具。 |

**默认使用建议废弃。** 仅在维护成本或风险足以证明强制迁移合理时才使用强制废弃。强制废弃需要提供迁移工具、文档和支持——不能仅仅宣布一个截止日期。

## 迁移流程

### 第 1 步：构建替代品

不要在没有可用替代方案的情况下废弃。替代品必须：

- 覆盖旧系统的所有关键用例
- 拥有文档和迁移指南
- 已在生产环境中验证（而不仅仅是"理论上更好"）

### 第 2 步：公告与文档

```markdown
## 废弃公告：OldService

**状态：** 自 2025-03-01 起废弃
**替代品：** NewService（参见下方迁移指南）
**移除日期：** 建议性——暂无硬性截止日期
**原因：** OldService 需要手动扩缩容且缺乏可观测性。
        NewService 可自动处理这两项。

### 迁移指南
1. 将 `import { client } from 'old-service'` 替换为 `import { client } from 'new-service'`
2. 更新配置（参见下方示例）
3. 运行迁移验证脚本：`npx migrate-check`
```

### 第 3 步：逐步迁移

逐个迁移消费者，而非一次性全部迁移。对每个消费者：

```
1. 识别与废弃系统的所有接触点
2. 更新为使用替代品
3. 验证行为一致（测试、集成检查）
4. 移除对旧系统的引用
5. 确认无回归
```

**变动规则（Churn Rule）：** 如果你拥有被废弃的基础设施，你有责任迁移你的用户——或提供无需迁移的向后兼容更新。不能宣布废弃后就把用户丢在一边。

### 第 4 步：移除旧系统

仅在所有消费者都已完成迁移后：

```
1. 验证零活跃使用（指标、日志、依赖分析）
2. 移除代码
3. 移除相关的测试、文档和配置
4. 移除废弃公告
5. 庆祝——移除代码是一项成就
```

## 迁移模式

### Strangler 模式

让新旧系统并行运行。逐步将流量从旧系统路由到新系统。当旧系统处理 0% 的流量时，将其移除。

```
阶段 1：新系统处理 0%，旧系统处理 100%
阶段 2：新系统处理 10%（金丝雀发布）
阶段 3：新系统处理 50%
阶段 4：新系统处理 100%，旧系统空闲
阶段 5：移除旧系统
```

### Adapter 模式

创建一个适配器，将旧接口的调用转换为新实现。消费者继续使用旧接口，同时你在后台迁移实现。

```typescript
// 适配器：旧接口，新实现
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 旧方法签名，委托给新实现
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }
}
```

### Feature Flag 迁移

使用 feature flag 逐个将消费者从旧系统切换到新系统：

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new LegacyTaskService();
}
```

## 僵尸代码（Zombie Code）

僵尸代码是指没人负责但人人都依赖的代码。它没有被积极维护，没有明确的负责人，并且不断积累安全漏洞和兼容性问题。迹象包括：

- 6 个月以上没有提交，但仍有活跃消费者
- 没有指定的维护者或团队
- 测试失败但无人修复
- 依赖项存在已知漏洞但无人更新
- 文档引用了已不存在的系统

**应对措施：** 要么指定负责人并妥善维护，要么制定具体的迁移计划将其废弃。僵尸代码不能一直悬而未决——要么投入资源维护，要么移除。

## 常见的自我安慰

| 自我安慰 | 现实 |
|----------|------|
| "它还能用，为什么要移除？" | 没人维护的可用代码会积累安全债务和复杂度。维护成本在暗中增长。 |
| "以后可能有人需要它" | 如果以后需要，可以重新构建。"以防万一"保留未使用的代码比重新构建的成本更高。 |
| "迁移成本太高了" | 将迁移成本与 2-3 年的持续维护成本进行比较。从长期来看，迁移通常更便宜。 |
| "等新系统做完再废弃" | 废弃规划从设计阶段就应开始。等新系统完成时，你会有新的优先级。现在就规划。 |
| "用户会自己迁移的" | 他们不会。提供工具、文档和激励——或者你自己来做迁移（变动规则）。 |
| "我们可以无限期地同时维护两个系统" | 两个做同样事情的系统意味着双倍的维护、测试、文档和新人上手成本。 |

## 危险信号

- 废弃的系统没有可用的替代品
- 废弃公告没有配套的迁移工具或文档
- "软"废弃——多年来一直是建议性的，但毫无进展
- 没有负责人但有活跃消费者的僵尸代码
- 向已废弃的系统添加新功能（应该投资替代品）
- 在未衡量当前使用量的情况下废弃
- 在未验证零活跃消费者的情况下移除代码

## 验证清单

完成废弃后：

- [ ] 替代品已在生产环境验证，覆盖所有关键用例
- [ ] 迁移指南包含具体步骤和示例
- [ ] 所有活跃消费者已完成迁移（通过指标/日志验证）
- [ ] 旧代码、测试、文档和配置已完全移除
- [ ] 代码库中不再存在对废弃系统的引用
- [ ] 废弃公告已移除（它们已完成使命）
