# Interview Me

## 概述

人们所要求的与他们真正想要的是两回事。他们要求"一个仪表盘"，因为人们就是这么要求的，而不是因为仪表盘能解决他们的问题。他们说"让它更快"，却没有给出一个具体数字。

发现这一差距最便宜的时刻，是在任何计划、规格或代码存在之前。一旦你开始构建，切换成本就是真实的，用户会把错误的东西合理化成一个"够用的"东西。不匹配就被锁死了。

这个技能在产生任何成本之前就弥合了这一差距。其他 Define 阶段的技能假设你已经大致知道想要什么：`idea-refine` 从一个想法生成变体，`spec-driven-development` 把需求写下来，`doubt-driven-development` 在你起草了计划之后对其进行压力测试。Interview-me 是所有这些之前的环节——每次只问一个问题，附上你的最佳猜测，直到你能在用户说出答案之前就预测到他们会说什么。

## 何时使用

在以下情况下使用此技能：

- 需求至少缺少以下之一：用户是**谁**、他们**为什么**想要、**成功**是什么样的、绑定的**约束**是什么
- 请求是惯例性的而非具体的（"给我做一个 X"、"让它更快"），而你不猜测就无法展开惯例背后的含义
- 你正准备从尚未浮出水面的假设开始
- 当两个合理的价值取向存在张力时（简洁 vs. 灵活、成本 vs. 速度），用户没有说明他们在优化哪个
- 用户明确要求："访谈我"、"拷问我"、"开始之前，我们确定吗？"、"压力测试一下我的想法"

**不应使用的场景：**

- 需求明确且自包含（"重命名这个变量"、"修复这个拼写错误"）
- 用户明确要求速度优先于验证
- 纯信息查询（"X 是怎么工作的？"、"这段代码做了什么？"）
- 机械性操作（重命名、格式化、文件移动）
- 你已经有 ≥95% 的信心；在假设自己信心不足之前，先重新阅读下方的停止条件

## 加载约束

此技能需要一个在线的、有响应的用户。**不要在非交互式上下文中调用**，如 CI 流水线、定时任务、`/loop` 或自动循环。如果你处于这些场景中且需求描述不充分，将其标记为阻塞问题告知用户，而不是猜测。

## 流程

### 步骤 1：假设，附带信心数值

在问任何问题之前，用**一句话**写下你当前对用户想要的东西的最佳判断，再加上一个诚实的信心数值（0–100%）：

```
HYPOTHESIS: 你想要一种在站会中回答"我们进展如何？"的方式，而"仪表盘"是脑海中浮现的惯例性答案。
CONFIDENCE: ~30% — 缺失：给谁用、"指标"在上下文中意味着什么、以及成功是什么样的
```

这个数值迫使你说实话。如果你写了一个高数值，但实际上无法预测用户对接下来三个问题的反应，那数值就是错的。从你能站得住脚的信心水平开始。

当信心低于约 70% 时，在同一行追加一个简短原因——什么仍然未解决或缺失。这告诉用户访谈需要挖掘什么，并防止这个数值变成一个模糊的信号。

### 步骤 2：每次只问一个问题，每个问题附带一个猜测

格式：

```
Q: <一个聚焦的问题>
GUESS: <你对答案的假设，以及产生这个假设的推理>
```

等待用户回应后再问下一个问题。

**为什么每次只问一个，而不是批量提问：**

- 如果你把假设埋在列表里，用户无法逐一回应
- 批量提问助长略读和表面回答
- 第三个问题往往取决于第一个问题的答案；一次性全问会锁定错误的框架
- 用户认真思考的精力是有限的；一次一个问题地消耗它

**为什么要附带猜测：**

- 用户对错误猜测的反应比对从零生成答案更快
- 它让你承诺一个可能被明显证伪的假设，从而保持诚实
- 它暴露了*你的*假设，而这正是访谈要揭示的东西

这里的风险是出于礼貌的用户为了迎合而同意你的猜测。通过表现出明显的愿意犯错的姿态来缓解，并偶尔猜测一个你预期用户会反驳的方向。

### 步骤 3：倾听"想要的 vs. 应该想要的"

最危险的答案是用户说出一个听起来深思熟虑的回答，而非他们真正想要的。注意以下信号：

- 回答模式化地匹配最佳实践话术（"我想要它是可扩展的"、"干净的架构"）却没有具体说明
- 回答诉诸惯例（"大多数应用的做法"、"标准方法"）
- 诸如"我可能应该……"、"我觉得我应该……"、"好的工程实践要求……"之类的短语
- 把流行词当目标——当"现代的"、"可扩展的"、"健壮的"成了答案，而非具体成果时

当你听到这些时，该问的问题是：

> *"如果你不需要向任何人证明这一点，你真正想要的是什么？"*

这一个问题往往比前五个问题更有效。

### 步骤 4：用用户自己的语言重述意图

当你的信心足够高时，把你现在认为用户想要的写回去。保持简洁（5–8 行），尽量使用他们的语言，并结构化地组织，让用户可以逐行确认或修正：

```
以下是我现在认为你想要的：

- 成果：      <一行>
- 用户：      <一行 — 谁受益>
- 为什么现在：<一行 — 什么发生了变化>
- 成功标准：  <一行 — 如何知道它起作用了>
- 约束：      <一行 — 绑定的限制>
- 不在范围内：<一行 — 我们明确不做什么>

确认 / 否定 / 修正？
```

包含"不在范围内"是不可商量的。一半的对齐偏差来自于对*不*构建什么的无声分歧。

### 步骤 5：确认——明确的"是"，而非"随便你怎么想"

门槛是一个明确的"是"。以下**不是**"是"：

- "你觉得怎么好就怎么来吧。" → 用户在委托，这意味着他们自己也没有 95% 的信心。用两个具体选项框定为选择题重新提问。
- "听起来不错。" → 模糊。追问："有什么要修正的吗？"沉默不是确认。
- "好的，开始吧。" → 通常是礼貌的退出，而非认可。同样追问。
- 沉默之后说"好的开始吧。" → 用户放弃了访谈，而非达成了共识。停下来问是否遗漏了什么。

如果他们纠正你，把纠正纳入并重新重述。循环直到你得到明确的"是"。

### 95% 信心停止条件

当你能对以下问题回答"是"时，你就完成了：

> *我能预测用户对接下来我会问的三个问题的反应吗？*

如果能，你们已经达成了共识。停止访谈，输出重述。如果不能，你还没完成；问下一个问题。

这是一个可检验的测试，不是一种感觉。它也有一个下限：如果你已经进行了几轮仍然无法预测，那是关于需求本身的信息，而不是继续追问的理由。停下来告诉用户："我已经问了 X 个问题，仍然无法预测你的反应。一些基础性的东西缺失了。要不要退一步重新审视？"

## 输出

此技能的输出是一个**已确认的意图声明**：步骤 4 的重述，加上步骤 5 中明确的"是"。这就是交付物。规格、计划和任务列表是下游产物；它们消费此技能产出的意图。

如果用户希望意图持久化（跨多个会话的项目、移交给其他协作者），提议将其保存到 `docs/intent/[topic].md`。仅在用户确认后保存。

## 示例

一个简短的前后对比。

**不使用 `interview-me`：**

```
User:  build me a dashboard for our metrics
Agent: <开始建议图表库和布局>
```

Agent 假设了：给谁用、什么指标、"for our team"意味着什么、成功是什么样的。这些都没有说明。每一个假设都是用户后来说"那不是我的意思"的地方。

**使用 `interview-me`：**

```
User: build me a dashboard for our metrics

Agent:
HYPOTHESIS: 你想要一种在站会中回答"我们进展如何？"的方式，而"仪表盘"是脑海中浮现的惯例性答案。
CONFIDENCE: ~30% — 缺失：给谁用、"指标"是什么、以及成功是什么样的

Q:     当你说"我们进展如何？"时，谁在问——只有你，工程团队在站会中，还是向上汇报（例如你的经理、高管、董事会）？
GUESS: 工程团队在站会中，因为"我们"通常限定了这个范围，而站会是问这个问题的场合。如果是给高管的，指标和框架会大不相同。

User: 其实是给我自己用的。我总是搞不清哪些实验在运行，它们的早期信号是什么样的。

Agent:
更新后的判断：根本不是团队仪表盘。是一个个人实验追踪器。信心：~60% — 仍然缺失："早期信号"意味着什么，以及完成是什么样的。

Q:     问题是你不知道有哪些实验，还是你无法在一个地方看到它们的结果？
GUESS: 第二个。你在某处有一份实验列表，但它们的结果分散在五个不同的工具中，手动整合这些正是你厌倦的事情。

User: 其实是第一个。我根本就没有列表。它们分散在不同的文档里。

Agent: <继续>
```

只问了两个问题，Agent 就发现真正的需求不是"一个仪表盘"，而是"一个列表"。不同的产物，不同的范围，不同的工作。仪表盘会是错的。

## 与其他技能的交互

- **`idea-refine`**：下游。如果已确认的意图是"我想要 X 但不知道如何界定范围"，移交给 `idea-refine` 针对现在已经明确的意图生成变体。
- **`spec-driven-development`**：下游。如果已确认的意图是具体的（"我想要为 Y 用户提供 X，成功标准是 Z"），移交给 `spec-driven-development` 将其写下来。
- **`planning-and-task-breakdown`**：此技能的两跳下游（在规格之后）。
- **`doubt-driven-development`**：时间线的另一端。Interview-me 是决策前的意图提取；doubt-driven 是决策后的产物审查。两者都捕捉偏差，但在不同的时刻。
- **`source-driven-development`**：正交的。Interview-me 澄清用户想要什么；SDD 验证框架事实。它们不竞争。

## 常见的自我合理化

| 合理化 | 现实 |
|---|---|
| "需求已经够清楚了" | 如果你现在无法用一句话写出用户期望的成果，需求就不够清楚。在决定之前先执行步骤 1。 |
| "问太多问题浪费他们的时间" | 4–6 个有针对性的问题浪费的时间很少。构建错误东西浪费的时间是巨大的，而承担这个成本的是用户。 |
| "我边做边搞清楚" | 代码存在之后的切换成本是现在的 10 倍。实现过程中的发现就是返工。 |
| "他们说了'随便你怎么想'，所以我应该自己决定" | "随便你怎么想"是委托，不是决策。用两个具体选项作为选择题重新提问。 |
| "我应该给他们几个选项来选择" | 当用户知道他们想要什么并在权衡取舍时，选项是有效的。他们还不知道自己想要什么。列出选项会扩大搜索范围；提问会缩小它。 |
| "如果我附带猜测，就是在引导他们" | 引导正是目的。反应比从零生成更快。风险是谄媚，不是引导；通过表现出明显的愿意犯错的姿态来缓解。 |
| "我们聊得够多了，我懂了" | 测试一下：你能预测他们对接下来三个问题的反应吗？如果不能，你还没懂。 |
| "用户说了是，我们完成了" | 如果是的回答跟在模糊的重述或开放式的"听起来不错"之后，这个"是"是空洞的。具体地重述并重新确认。 |

## 危险信号

- 单条消息中有三个或更多问题：那是批量提问，不是访谈
- 一个问题没有附带你的假设：那是调查，不是承诺
- 接受"你觉得怎么好就怎么来"作为最终答案
- 在用户明确确认你的重述之前就产出规格、计划或任务列表
- 问题框定为"最佳实践是什么？"而非"你真正想要什么？"
- 用户给出了一个显示复杂度的回答（"可扩展的"、"干净的"、"现代的"），而你未经探究就接受了，没有确认这是否是他们真正想要的
- 三轮或更多轮之后你的信心没有明显上升：你在问错误的问题，退一步重新构建
- 信心数值低于约 70% 却没有附带原因：如果用户不知道缺失了什么，他们无法帮助弥合差距
- 在用户确认之前就保存意图文档（文档本身就暗示了一个用户没有给出的"是"）
- 在重述中跳过"不在范围内"一行（关于非目标的无声分歧是一半的偏差来源）

## 验证

应用 interview-me 之后：

- [ ] 在第一轮中明确陈述了附带信心数值的假设
- [ ] 每个低于约 70% 的信心数值都附带了一行原因（什么仍然未解决或缺失）
- [ ] 问题每次只问一个，每个都附带 Agent 的猜测
- [ ] 当用户给出显示复杂度或惯例的回答时，至少运行了一次"如果你不需要证明，你真正想要什么？"的追问
- [ ] 具体的重述（成果 / 用户 / 为什么现在 / 成功标准 / 约束 / 不在范围内）已写回给用户
- [ ] 用户以明确的"是"确认了重述（不是"随便你怎么想"，不是"听起来不错"，不是沉默）
- [ ] 在停止点，Agent 能够预测对接下来三个问题的反应
- [ ] 任何向下游技能（`idea-refine`、`spec-driven-development`）的移交都基于已确认的意图，而非原始的模糊需求
