# 规划与任务分解（Planning and Task Breakdown）

## 概述

将工作分解为小的、可验证的任务，并附带明确的验收标准。良好的任务分解是区分一个能可靠完成工作的 agent 与一个只会制造混乱的 agent 的关键。每个任务都应足够小，能够在一次专注的会话中完成实施、测试和验证。

## 何时使用

- 你有一份规格说明，需要将其拆分为可实施的单元
- 任务感觉太大或太模糊，无法着手
- 工作需要在多个 agent 或会话之间并行执行
- 你需要向人类传达工作范围
- 实施顺序不明显

**何时不应使用：** 范围明确的单文件修改，或者规格说明中已经包含定义良好的任务。

## 规划流程

### 第 1 步：进入规划模式

在编写任何代码之前，以只读模式运作：

- 阅读规格说明和相关的代码库部分
- 识别现有的模式和约定
- 梳理组件之间的依赖关系
- 记录风险和未知因素

**规划期间不要编写代码。** 输出是一份计划文档，而非实现。

### 第 2 步：识别依赖图

梳理依赖关系：

```
数据库 schema
    │
    ├── API 模型/类型
    │       │
    │       ├── API 端点
    │       │       │
    │       │       └── 前端 API 客户端
    │       │               │
    │       │               └── UI 组件
    │       │
    │       └── 校验逻辑
    │
    └── 种子数据 / 迁移
```

实施顺序遵循依赖图自底向上：先构建基础。

### 第 3 步：纵向切片

不要先构建整个数据库，再构建整个 API，再构建整个 UI —— 而是一次构建一个完整的功能路径：

**错误做法（横向切片）：**
```
任务 1：构建整个数据库 schema
任务 2：构建所有 API 端点
任务 3：构建所有 UI 组件
任务 4：连接所有部分
```

**正确做法（纵向切片）：**
```
任务 1：用户可以创建账户（注册功能的 schema + API + UI）
任务 2：用户可以登录（认证 schema + API + UI）
任务 3：用户可以创建任务（任务 schema + API + UI）
任务 4：用户可以查看任务列表（查询 + API + UI）
```

每个纵向切片都交付可运行、可测试的功能。

### 第 4 步：编写任务

每个任务遵循以下结构：

```markdown
## 任务 [N]：[简短描述性标题]

**描述：** 一段话说明此任务的目标。

**验收标准：**
- [ ] [具体的、可测试的条件]
- [ ] [具体的、可测试的条件]

**验证：**
- [ ] 测试通过：`npm test -- --grep "feature-name"`
- [ ] 构建成功：`npm run build`
- [ ] 手动检查：[描述需要验证的内容]

**依赖：** [此任务依赖的任务编号，或"无"]

**可能涉及的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**预估范围：** [小：1-2 个文件 | 中：3-5 个文件 | 大：5+ 个文件]
```

### 第 5 步：排序与检查点

按以下原则排列任务：

1. 依赖关系得到满足（先构建基础）
2. 每个任务完成后系统处于可运行状态
3. 每 2-3 个任务后设置验证检查点
4. 高风险任务排在前面（快速失败）

添加明确的检查点：

```markdown
## 检查点：任务 1-3 完成后
- [ ] 所有测试通过
- [ ] 应用构建无错误
- [ ] 核心用户流程端到端可用
- [ ] 继续之前与人类评审
```

## 任务规模指南

| 规模 | 文件数 | 范围 | 示例 |
|------|--------|------|------|
| **XS** | 1 | 单个函数或配置变更 | 添加一条校验规则 |
| **S** | 1-2 | 一个组件或端点 | 添加一个新的 API 端点 |
| **M** | 3-5 | 一个功能切片 | 用户注册流程 |
| **L** | 5-8 | 多组件功能 | 带筛选和分页的搜索 |
| **XL** | 8+ | **太大 —— 需要进一步拆分** | — |

如果任务为 L 或更大，应拆分为更小的任务。Agent 在 S 和 M 规模的任务上表现最佳。

**何时需要进一步拆分任务：**
- 需要超过一次专注会话的时间（大约 2 小时以上的 agent 工作量）
- 你无法在 3 个或更少的要点中描述验收标准
- 涉及两个或更多独立的子系统（例如，认证和计费）
- 你发现自己在任务标题中写了"和"（说明这是两个任务）

## 计划文档模板

```markdown
# 实施计划：[功能/项目名称]

## 概述
[一段话总结我们要构建的内容]

## 架构决策
- [关键决策 1 及其理由]
- [关键决策 2 及其理由]

## 任务列表

### 阶段 1：基础
- [ ] 任务 1：...
- [ ] 任务 2：...

### 检查点：基础
- [ ] 测试通过，构建无错误

### 阶段 2：核心功能
- [ ] 任务 3：...
- [ ] 任务 4：...

### 检查点：核心功能
- [ ] 端到端流程可用

### 阶段 3：完善
- [ ] 任务 5：...
- [ ] 任务 6：...

### 检查点：完成
- [ ] 所有验收标准已满足
- [ ] 准备好进行评审

## 风险与缓解措施
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| [风险] | [高/中/低] | [策略] |

## 待解决问题
- [需要人类输入的问题]
```

## 并行化机会

当有多个 agent 或会话可用时：

- **可以并行：** 独立的功能切片、已实现功能的测试、文档
- **必须串行：** 数据库迁移、共享状态变更、依赖链
- **需要协调：** 共享 API 契约的功能（先定义契约，再并行化）

## 常见的自我合理化

| 合理化说法 | 现实 |
|---|---|
| "我边做边想" | 这就是你最终制造混乱和返工的原因。10 分钟的规划能节省数小时。 |
| "任务很明显" | 无论如何写下来。明确的任务能暴露隐藏的依赖和遗忘的边界情况。 |
| "规划是额外开销" | 规划本身就是任务。没有计划的实施只是在打字。 |
| "我都能在脑子里记住" | 上下文窗口是有限的。书面计划能跨越会话边界和压缩而保留。 |

## 危险信号

- 没有书面任务列表就开始实施
- 任务写着"实现功能"但没有验收标准
- 计划中没有验证步骤
- 所有任务都是 XL 规模
- 任务之间没有检查点
- 没有考虑依赖顺序

## 验证

在开始实施之前，确认：

- [ ] 每个任务都有验收标准
- [ ] 每个任务都有验证步骤
- [ ] 任务依赖已识别并正确排序
- [ ] 没有任务涉及超过约 5 个文件
- [ ] 主要阶段之间存在检查点
- [ ] 人类已审阅并批准计划

## 另见

验收标准是针对每个任务的，回答"我们是否构建了正确的东西？"。它建立在项目级 Definition of Done 之上，后者是每个任务在算作完成之前必须达到的持续标准。参见 `references/definition-of-done.md`。
