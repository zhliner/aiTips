# 可观测性与插桩（Observability and Instrumentation）

## 概述

无法观测的代码就无法运维。可观测性是指从外部利用代码发出的遥测数据来回答"系统在做什么，为什么？"的能力。插桩不是上线后的附加项——它应当与功能代码同步编写，就像测试一样。如果一个功能在没有遥测数据的情况下发布了，那么第一个用户报告的 bug 就会变成考古工作，而不是一次查询。

## 适用场景

- 构建任何将在生产环境中运行的功能
- 添加新的服务、端点、后台任务或外部集成
- 生产事故诊断耗时过长（"我们无法判断发生了什么"）
- 设置或审查告警规则
- 审查涉及 I/O、重试、队列或跨服务调用的 PR

**不适用于：**
- 诊断正在发生的故障——请使用 `debugging-and-error-recovery` 技能（可观测性正是让该技能在下次更快的前提）
- 性能分析与优化已测量的慢速问题——请使用 `performance-optimization` 技能
- 上线日的监控检查清单与回滚触发条件——请参阅 `shipping-and-launch` 技能；本技能涵盖的是为其提供数据支撑的插桩工作

## 流程

### 1. 在插桩之前定义"正常工作"

没有问题的遥测数据就是噪音。在添加任何插桩之前，写下 2–4 个值班工程师会针对该功能提出的问题：

```
功能：结账支付重试
值班工程师会问的问题：
1. 首次尝试支付成功的比例与重试后成功的比例各是多少？
2. 当支付最终失败时，原因是什么？（提供商错误？超时？校验失败？）
3. 支付提供商的响应是否比平时更慢？
→ 下面的每一个信号都必须能帮助回答上述问题之一。
```

如果你无法列出这些问题，说明你还没有准备好进行插桩——你会记录一切却什么也学不到。

### 2. 为每个问题选择合适的信号

| 信号 | 回答的问题 | 成本特征 | 示例 |
|---|---|---|---|
| **结构化日志** | "这个特定情况下发生了什么？" | 按事件计；随流量增长 | 带有提供商错误码的 `payment_failed` |
| **指标** | "总体上多频繁/多快？" | 每个序列固定成本；查询开销低 | 提供商调用的 p99 延迟 |
| **追踪** | "时间在各服务间是如何消耗的？" | 按请求计；通常采样 | 一次慢速结账，按跳分解 |

经验法则：指标告诉你**有**问题，追踪告诉你问题**在哪里**，日志告诉你**为什么**。

### 3. 结构化日志

记录事件，而非叙述。每一行日志都应是带有稳定事件名称和机器可读字段的 JSON 对象：

```typescript
// 错误做法：字符串插值——无法查询，格式不一致
logger.info(`Payment ${id} failed for user ${userId} after ${n} retries`);

// 正确做法：稳定的事件名称 + 结构化字段
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, 'payment failed');
```

**日志级别——保持一致使用：**

| 级别 | 含义 | 值班操作 |
|---|---|---|
| `error` | 不变量被打破；可能需要人工介入 | 调查 |
| `warn` | 降级但已处理（重试成功、使用了回退方案） | 关注趋势 |
| `info` | 重要的业务事件（订单已创建、任务已完成） | 无需操作 |
| `debug` | 诊断详情 | 生产环境默认关闭 |

**关联 ID 是强制性的。** 在系统边界处生成（或接收）一个请求 ID，并将其附加到每一行日志、每一个 span 以及每一个出站调用上。没有它，你无法从交错的日志中重建单个请求：

```typescript
// Express：每个请求创建子 logger，ID 向下游传播
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

**绝不在日志中记录密钥、令牌、密码或完整的 PII（个人身份信息）。** 这是来自 `security-and-hardening` 技能的硬性规则——遥测管道是经典的数据泄露路径。使用字段白名单；不要记录完整的请求体。

### 4. 指标

对于请求驱动的服务，在每个端点和每个外部依赖上插桩 **RED** 指标：**R**ate（请求数/秒）、**E**rrors（失败率）、**D**uration（延迟直方图，而非平均值）。对于资源（队列、连接池、主机），使用 **USE** 指标：**U**tilization（利用率）、**S**aturation（饱和度）、**E**rrors（错误）。

与追踪一样，厂商中立的路径是 OpenTelemetry metrics API（与第 5 步使用相同的 SDK 和上下文）。下面的示例使用 Prometheus 的 `prom-client`——这是一种常见的后端选择，但不是唯一选择；RED/USE 和基数规则在任何后端下都相同。

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status_class'],  // '2xx'，而非 '200'
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**基数是失败的根源。** 每一个唯一的标签组合都是一个独立的时间序列。标签必须来自小型、固定的集合（路由模板、状态码类别、提供商名称）。切勿使用用户 ID、原始 URL、错误消息或其他无界值作为标签——这些应放在日志和追踪中。

```
可作为标签：  route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
绝不能作为标签：user_id、email、request_id、完整 URL、错误消息文本
```

永远不要追踪平均值，始终追踪百分位数：平均值会掩盖那 1% 正在经历糟糕体验的用户。使用直方图并读取 p50/p95/p99。

### 5. 分布式追踪

使用 OpenTelemetry——它是厂商中立的标准，自动插桩几乎零代码即可覆盖 HTTP、gRPC 和常见的数据库客户端：

```typescript
// tracing.ts——必须在所有其他代码之前导入
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

仅在有意义的内部工作单元（例如 `applyDiscounts`、`chargeProvider`）周围添加手动 span，并附加值班工程师会用来过滤的属性。在每个异步边界（HTTP 头、队列消息元数据）上传播上下文——否则追踪会在断点处终止。默认使用低比率的头部采样；如果你的后端支持尾部采样，则保留 100% 的错误请求。

### 6. 告警

基于**用户能感知到的症状**告警，而非基于原因：

```
症状（值得呼叫）：              原因（看仪表盘，不必呼叫）：
错误率 > 1% 持续 5 分钟         CPU 达到 85%
p99 延迟 > 2 秒                 一个 pod 重启了
队列积压时间 > 10 分钟           磁盘使用率 70%
```

基于原因的告警会在没有问题时触发，并且会遗漏你没有预见到的故障。基于症状的告警恰好在用户受到影响时触发，无论原因是什么。

你创建的每一条告警都应遵循以下规则：

1. **必须是可操作的。** 如果响应是"忽略它，它会自愈"，就删掉这条告警。
2. **必须链接到运维手册（runbook）**——哪怕只有三行：它意味着什么、第一个要执行的查询、升级路径。
3. **必须有阈值和持续时间**，由 SLO 或历史数据来证明其合理性，而非凭猜测。
4. 只使用两个严重级别：**page**（影响用户，立即行动）和 **ticket**（降级，本周内处理）。第三个级别会变成噪音，让人们习惯忽略一切。

### 7. 验证遥测数据本身

插桩也是代码；它可能出错。在宣布工作完成之前，触发相关路径并查看实际输出：

- 在预发布环境（staging）中强制触发一个错误 → 通过 `requestId` 在日志中找到它，确认字段是结构化的（而非 `[object Object]`）
- 发送测试流量 → 确认指标序列以预期的标签和合理的值出现
- 在追踪 UI 中跟踪一个请求跨服务的完整路径 → 没有断裂的 span
- 触发每条新告警一次（临时降低阈值） → 确认它到达了正确的渠道，运维手册链接有效

## 常见的自我安慰

| 自我安慰 | 现实 |
|---|---|
| "等功能跑通了我再加日志" | "之后"变成了"第一次事故之后"，而那是发现自己是盲人时最昂贵的时刻。边构建边插桩。 |
| "日志越多 = 可观测性越强" | 非结构化的噪音只会让事故处理更慢，而非更快。三个可查询的事件胜过三百行叙述性日志。 |
| "console.log 暂时够用了" | 非结构化的输出无法过滤、关联或告警。结构化日志器只需多花五分钟。 |
| "出问题时看仪表盘就行了" | 没有预先定义问题就构建的仪表盘，除了答案什么都会展示给你。从值班工程师的问题出发。 |
| "所有重要的都加告警，之后再调优" | 频繁呼叫的寻呼机会让人们学会忽略它。调优永远不会发生；漏掉的真实呼叫却会。 |
| "把用户 ID 作为指标标签方便调试" | 它也会让你的指标后端崩溃。高基数查询应放在日志和追踪中。 |
| "我们只有两个服务，追踪太夸张了" | 两个服务已经意味着存在跨服务延迟问题，而日志无法回答。自动插桩让成本微乎其微。 |

## 危险信号

- 一个涉及重试、队列或外部调用的功能 PR，却没有新增任何遥测
- 日志行通过字符串插值构建，而非结构化字段
- 没有关联/请求 ID——每行日志都是孤立的
- 指标标签使用了用户 ID、原始 URL 或错误消息文本（基数炸弹）
- 延迟以平均值追踪，没有百分位数
- 每天触发且被确认但未采取行动的告警
- 基于原因（CPU、内存）的告警在呼叫人类，而面向用户的错误率却没有被监控
- 日志中出现密钥、令牌或完整的请求体
- "在我机器上是好的"作为生产功能健康的唯一证据

## 验证

在完成功能的插桩后，确认：

- [ ] 该功能的值班问题已写下，且每个信号都映射到其中一个问题
- [ ] 所有日志输出都是结构化的（JSON），具有稳定的事件名称和每行都有的关联 ID
- [ ] 任何日志行中都没有密钥、令牌或未脱敏的 PII（抽查实际输出）
- [ ] 每个新端点和每个外部依赖都有 RED 指标，标签集是有界的
- [ ] 延迟使用直方图；p95/p99 可查询
- [ ] 在追踪 UI 中可以端到端跟踪单个请求，没有断裂的 span
- [ ] 每条新告警都是基于症状的，有运维手册链接，并且已经测试触发过一次
- [ ] 在预发布环境中人为制造的故障仅通过遥测数据定位，无需阅读源码
