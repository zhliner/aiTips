# 代码审查与质量（Code Review and Quality）

## 概述

多维度代码审查，配合质量门禁。每次变更在合并前都必须经过审查——没有例外。审查涵盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：** 当变更确实能改善整体代码健康度时，即使它并不完美，也应批准。完美的代码不存在——目标是持续改进。不要因为变更不是你会写的方式就阻止它。如果它改善了代码库并遵循了项目约定，就批准它。

## 使用时机

- 在合并任何 PR 或变更之前
- 在完成功能实现之后
- 当其他 agent 或模型生成了你需要评估的代码时
- 在重构现有代码时
- 在任何 bug 修复之后（同时审查修复代码和回归测试）

## 五维度审查

每次审查都从以下维度评估代码：

### 1. 正确性

代码是否完成了它声称要做的事情？

- 是否符合规格说明或任务要求？
- 是否处理了边界情况（null、空值、边界值）？
- 是否处理了错误路径（而不仅仅是正常路径）？
- 是否通过了所有测试？测试是否真的在测试正确的东西？
- 是否存在差一错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一位工程师（或 agent）能否在不依赖作者解释的情况下理解这段代码？

- 命名是否具有描述性且与项目约定一致？（不要使用无上下文的 `temp`、`data`、`result`）
- 控制流是否清晰直接（避免嵌套三元运算符、深层回调）？
- 代码组织是否合理（相关代码分组、模块边界清晰）？
- 是否存在应该简化的"巧妙"技巧？
- **能否用更少的代码实现？**（1000 行代码能用 100 行完成就是失败）
- **抽象是否值得其复杂度？**（在第三个用例出现之前不要过度泛化）
- 注释是否有助于阐明非显而易见的意图？（但不要注释显而易见的代码）
- 是否存在死代码残留：无用变量（`_unused`）、向后兼容的垫片代码、或 `// removed` 注释？
- **是否将新的条件分支强加到不相关的流程上？** 这是设计问题，不是小毛病——应该将逻辑推入独立的 helper、状态或策略中，而不是缠绕在现有路径上。
- **是否出现了基于相同数据结构的重复条件判断？** 它们暗示缺少模型或分发器。一个"临时"分支通常是永久的技术债。

### 3. 架构

变更是否符合系统的设计？

- 是否遵循了现有模式或引入了新模式？如果是新模式，是否有正当理由？
- 是否保持了清晰的模块边界？
- 是否存在应该共享的重复代码？
- 依赖方向是否正确（没有循环依赖）？
- 抽象层次是否适当（不过度工程化，不过度耦合）？
- **这次重构是降低了复杂度还是仅仅转移了复杂度？** 计算读者需要同时记住的概念数量。如果一个"更清晰"的版本让这个数量不变，那它并不更清晰——优先选择能让整个分支、模式或层次消失的重构，而不是将相同逻辑重新集中的那种。优先删除抽象而非打磨它。
- **特定功能的逻辑是否泄漏到了共享或通用模块中？** 将逻辑保留在其所属层中，复用现有的规范 helper 而非近乎重复的实现，不要将架构漂移正常化。
- **类型边界是否显式？** 质疑无理由的 `any`/`unknown`/可选类型/类型断言以及掩盖不清晰不变量的静默回退——使边界显式通常能让周围的控制流更简单。

### 4. 安全性

详细安全指导请参阅 `security-and-hardening`。变更是否引入了漏洞？

- 用户输入是否经过验证和清洗？
- 密钥是否远离代码、日志和版本控制？
- 是否在需要的地方检查了认证/授权？
- SQL 查询是否使用了参数化（不使用字符串拼接）？
- 输出是否经过编码以防止 XSS？
- 依赖是否来自可信来源且没有已知漏洞？
- 来自外部来源的数据（API、日志、用户内容、配置文件）是否被视为不可信？
- 外部数据流是否在使用于逻辑或渲染之前于系统边界处进行了验证？

### 5. 性能

详细的性能分析和优化请参阅 `performance-optimization`。变更是否引入了性能问题？

- 是否存在 N+1 查询模式？
- 是否存在无界循环或无限制的数据获取？
- 是否存在应该异步的同步操作？
- UI 组件中是否存在不必要的重渲染？
- 列表端点是否缺少分页？
- 是否在热点路径中创建了大对象？

## 结构性修复

当你发现结构性问题时，提出具体的移动方案——而不仅仅是指出问题。只说"这很复杂"的审查让作者无从下手。使用具名的重构方式：

- **用类型化模型或显式分发器替换条件链。**
- **将重复的分支折叠为单一更清晰的流程。**
- **将编排逻辑与业务逻辑分离**，使各自独立可读。
- **将特定功能的逻辑从共享模块移到拥有该概念的包中。**
- **复用规范的 helper** 而非定制的近似重复实现。
- **使类型边界显式化**，从而消除下游的分支判断。
- **删除透传包装器**——它只增加了间接层而没有澄清 API。
- **提取 helper，或将大文件拆分为聚焦的模块。**

优先选择能减少活动部件的修复方案，而非将相同复杂度分散开来的方案。

## 变更规模

小而聚焦的变更更容易审查、更快合并、部署更安全。目标规模：

```
约 100 行变更   → 良好。一次审查即可完成。
约 300 行变更   → 如果是单一逻辑变更，可以接受。
约 1000 行变更  → 太大。需要拆分。
```

**关注文件大小，而不仅仅是 diff 大小。** 一个小的 diff 仍可能将文件推过健康的边界——单个文件约 1000 *总*行数（不同于上面约 1000 *变更*行的阈值）是一个常见的检查信号，不是硬性上限。当变更显著增长了一个已经很大的文件时，先考虑是否应该提取 helper、子组件或模块，然后再堆叠更多内容。先分解，再添加。

**什么算作"一个变更"：** 一个自包含的修改，解决一个问题，包含相关测试，并在提交后保持系统功能正常。功能的一部分——而不是整个功能。

**变更过大时的拆分策略：**

| 策略 | 方法 | 适用场景 |
|------|------|----------|
| **堆叠（Stack）** | 提交一个小变更，基于它开始下一个 | 顺序依赖 |
| **按文件分组** | 为需要不同审查者的文件组分别提交变更 | 跨领域关注点 |
| **水平拆分** | 先创建共享代码/桩，再创建消费者 | 分层架构 |
| **垂直拆分** | 将功能拆分为更小的全栈切片 | 功能开发 |

**大型变更可以接受的场景：** 完整的文件删除和自动化重构，审查者只需验证意图而非每一行。

**将重构与功能开发分开。** 一个既重构现有代码又添加新行为的变更实际上是两个变更——分别提交。小型清理（如变量重命名）可由审查者酌情决定是否包含。

## 变更描述

每个变更都需要一个能在版本控制历史中独立存在的描述。

**第一行：** 简短、祈使句、独立成句。用"删除 FizzBuzz RPC"而非"正在删除 FizzBuzz RPC"。必须提供足够的信息，让搜索历史的人无需阅读 diff 就能理解变更。

**正文：** 变更了什么以及为什么。包含代码本身中不可见的上下文、决策和推理。链接到 bug 编号、基准测试结果或设计文档。承认方法存在的不足之处。

**反模式：** "修复 bug"、"修复构建"、"添加补丁"、"将代码从 A 移到 B"、"第一阶段"、"添加便捷函数"。

## 审查流程

### 步骤 1：理解上下文

在查看代码之前，理解意图：

```
- 这个变更试图实现什么？
- 它实现了哪个规格说明或任务？
- 预期的行为变化是什么？
```

### 步骤 2：先审查测试

测试揭示意图和覆盖范围：

```
- 变更是否有对应的测试？
- 测试是否测试行为（而非实现细节）？
- 边界情况是否覆盖？
- 测试是否有描述性的名称？
- 如果代码发生变化，测试能否捕获回归？
```

### 步骤 3：审查实现

带着五个维度走查代码：

```
对于每个变更的文件：
1. 正确性：这段代码是否完成了测试所期望的？
2. 可读性：我能否在没有帮助的情况下理解它？
3. 架构：它是否适合这个系统？
4. 安全性：是否存在漏洞？
5. 性能：是否存在瓶颈？
```

### 步骤 4：分类发现

为每条评论标注严重程度，让作者知道什么是必须的、什么是可选的：

| 前缀 | 含义 | 作者操作 |
|------|------|----------|
| *（无前缀）* | 必须的变更 | 合并前必须处理 |
| **Critical：** | 阻止合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit：** | 次要、可选 | 作者可以忽略——格式、风格偏好 |
| **Optional：** / **Consider：** | 建议 | 值得考虑但不强制 |
| **FYI** | 仅供参考 | 无需操作——为将来参考提供上下文 |

这可以防止作者将所有反馈都视为必须处理而浪费时间在可选建议上。

**优先呈现重要的内容。** 按影响力排序发现：正确性和安全性优先，然后是结构性回归和遗漏的简化，最后才是其他。不要把真正的问题埋在表面性的 nit 之下——几条高置信度的评论胜过一长串。如果你有一个结构性问题和十个 nit，那个结构性问题*就是*审查的重点。

### 步骤 5：验证验证过程

检查作者的验证情况：

```
- 运行了哪些测试？
- 构建是否通过？
- 变更是否经过手动测试？
- UI 变更是否有截图？
- 是否有前后对比？
```

## 多模型审查模式

使用不同的模型获取不同的审查视角：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人类做出最终决定
```

这能捕获单一模型可能遗漏的问题——不同的模型有不同的盲点。

**审查 agent 的示例 prompt：**
```
审查此代码变更的正确性、安全性以及对我们项目约定的遵循。
规格说明要求 [X]。变更应该 [Y]。
将任何问题标记为 Critical、Required、Optional 或 Nit。
```

## 死代码清理

在任何重构或实现变更之后，检查孤立的代码：

1. 识别现在不可达或未使用的代码
2. 明确列出它们
3. **删除前先询问：**"我应该删除这些现在未使用的元素吗：[列表]？"

不要留下死代码——它会让未来的读者和 agent 困惑。但也不要默默删除你不确定的东西。有疑问时，先问。

```
识别到的死代码：
- src/utils/date.ts 中的 formatLegacyDate() —— 已被 formatDate() 替代
- src/components/ 中的 OldTaskCard 组件 —— 已被 TaskCard 替代
- src/config.ts 中的 LEGACY_API_URL 常量 —— 没有剩余引用
→ 可以安全删除这些吗？
```

## 审查速度

缓慢的审查会阻塞整个团队。切换到审查的上下文切换成本低于强加给其他人的等待成本。

- **在一个工作日内响应** —— 这是最大时限，不是目标
- **理想节奏：** 在收到审查请求后尽快响应，除非正处于深度专注编码中。一个典型的变更应该在一天内完成多轮审查
- **优先快速 individual 响应** 而非快速最终批准。即使需要多轮，快速反馈也能减少挫败感
- **大型变更：** 要求作者拆分，而不是审查一个巨大的变更集

## 处理分歧

在解决审查争议时，应用以下优先级：

1. **技术事实和数据** 优先于意见和偏好
2. **风格指南** 是风格问题的绝对权威
3. **软件设计** 必须基于工程原则评估，而非个人偏好
4. **代码库一致性** 是可接受的，前提是不降低整体健康度

**不要接受"我以后再清理。"** 经验表明延迟的清理很少会发生。要求提交前完成清理，除非是真正的紧急情况。如果无法在本次变更中处理周围的问题，要求创建一个 bug 并自行分配。

## 审查中的诚实

当审查代码时——无论是你写的、其他 agent 写的还是人类写的：

- **不要橡皮图章。** 没有审查证据的"LGTM"对任何人都没有帮助。
- **不要弱化真正的问题。** 当它是一个会影响生产环境的 bug 时，说"这可能是一个小问题"是不诚实的。
- **尽可能量化问题。** "这个 N+1 查询会为列表中的每个项目增加约 50ms"比"这可能会慢"更好。
- **对有明确问题的方法提出反对。** 谄媚是审查中的一种失败模式。如果实现有问题，直接说出来并提出替代方案。
- **优雅地接受否决。** 如果作者拥有完整上下文并不同意，尊重他们的判断。评论代码，而非人——将个人批评重新聚焦到代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**在添加任何依赖之前：**
1. 现有技术栈能否解决这个问题？（通常可以。）
2. 依赖有多大？（检查包体积影响。）
3. 是否在积极维护？（检查最近提交、未关闭的 issues。）
4. 是否有已知漏洞？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 优先使用标准库和现有工具而非新依赖。每个依赖都是一项负债。

## 审查清单

```markdown
## 审查：[PR/变更标题]

### 上下文
- [ ] 我理解这个变更做了什么以及为什么

### 正确性
- [ ] 变更符合规格说明/任务要求
- [ ] 边界情况已处理
- [ ] 错误路径已处理
- [ ] 测试充分覆盖变更

### 可读性
- [ ] 命名清晰一致
- [ ] 逻辑清晰直接
- [ ] 无不必要的复杂度

### 架构
- [ ] 遵循现有模式
- [ ] 无不必要的耦合或依赖
- [ ] 适当的抽象层次
- [ ] 重构降低了复杂度而非转移了复杂度
- [ ] 共享模块中无功能逻辑；文件保持在健康的大小范围内

### 安全性
- [ ] 代码中无密钥
- [ ] 输入在边界处验证
- [ ] 无注入漏洞
- [ ] 认证检查就位
- [ ] 外部数据源被视为不可信

### 性能
- [ ] 无 N+1 模式
- [ ] 无无界操作
- [ ] 列表端点有分页

### 验证
- [ ] 测试通过
- [ ] 构建成功
- [ ] 手动验证完成（如适用）

### 结论
- [ ] **批准** —— 准备合并
- [ ] **请求变更** —— 问题必须解决
```

## 常见的自我合理化

| 合理化 | 现实 |
|--------|------|
| "能运行就行" | 能运行但不可读、不安全或架构错误的代码会创造不断复利的技术债。 |
| "我写的，所以我知道它是对的" | 作者对自己的假设视而不见。每次变更都受益于另一双眼睛。 |
| "我们以后再清理" | "以后"永远不会来。审查就是质量门禁——使用它。要求合并前清理，而非合并后。 |
| "AI 生成的代码应该没问题" | AI 代码需要更多审查，而非更少。它自信且看似合理，即使在错误的时候。 |
| "测试通过了，所以没问题" | 测试是必要的但不充分的。它们无法捕获架构问题、安全问题或可读性问题。 |
| "重构让它更清晰了" | 转移复杂度不等于降低复杂度。如果读者仍需记住同样数量的概念，结构就没有改善——寻找让分支消失的版本。 |
| "只是对这个文件的小 additions" | 小的 diff 仍会将文件推过健康大小，并将分支强加到不相关的流程上。判断结果结构，而非 diff 大小。 |

## 危险信号

- PR 未经任何审查就合并
- 审查只检查测试是否通过（忽略其他维度）
- 没有实际审查证据的"LGTM"
- 安全敏感的变更没有安全聚焦的审查
- "太大无法仔细审查"的大型 PR（拆分它们）
- bug 修复 PR 没有回归测试
- 审查评论没有严重程度标签——让人不清楚什么是必须的、什么是可选的
- 接受"我以后修复"——永远不会发生
- 重构只是移动代码而没有减少读者需要记住的概念数量
- 变更增长了一个已经很大的文件而不是分解它
- 新的条件判断分散到不相关的代码路径中（缺失的抽象）
- 定制的 helper 复制了现有的规范 helper，或功能逻辑放在了共享模块中

## 验证

审查完成后：

- [ ] 所有 Critical 问题已解决
- [ ] 所有 Required（无前缀）变更已解决或明确推迟并附理由
- [ ] 测试通过
- [ ] 构建成功
- [ ] 验证情况已记录（变更了什么，如何验证的）

**假定阻止项：** 为以下每项揭示并提议更简单的设计；仅当变更主动使结构变差时才升级为 Required：重构转移了复杂度而非降低复杂度；变更将文件推过大小边界而没有分解；功能逻辑添加到共享模块；现有规范 helper 的近似重复；掩盖不清晰不变量的静默回退。
