# 打磨与评估标准

在阶段 2（评估与收敛）中使用此评估规则来压力测试想法方向。并非每条标准都适用于每个想法——请运用判断力确定哪些维度对特定场景最为重要。

## 核心评估维度

### 1. 用户价值

最重要的维度。如果价值不明确，其他都无关紧要。

**止痛药 vs. 维生素：**
- **止痛药：** 解决一个急性的、高频的问题。用户会主动寻求它，会从当前方案切换过来。信号：人们谈及问题时带有情绪，已经自行搭建了临时方案，愿意为解决方案付费。
- **维生素：** 锦上添花。让某件事稍微好一点。用户不会特意追求。信号：人们礼貌地点头，说"挺酷的"，然后行为没有任何改变。

**需要追问的问题：**
- 你能说出 3 个此刻正有这个问题的具体人名吗？
- 他们现在在用什么替代方案？（真正的竞争对手永远是当前的临时方案。）
- 他们会从当前方法切换过来吗？什么能促使他们切换？
- 他们遇到这个问题的频率如何？（每天遇到的问题 > 每月遇到的问题）
- 这是一个"拉"的问题（用户在主动要求）还是"推"的问题（你认为他们应该想要）？

**危险信号：**
- "所有人都能用"——如果你说不出一个具体用户，价值就不清晰
- "它像 X 但更好"——边际改进很少能驱动采用
- 问题是真实的但罕见——高强度但低频率很少能支撑一个产品

### 2. 可行性

你真的能做出来吗？不仅是技术上，还有实践上。

**技术可行性：**
- 核心技术是否存在且能可靠运行？
- 最难的技术问题是什么？是已知的难题还是全新的问题？
- 是否依赖你无法控制的第三方、API 或数据源？
- 所需的最小技术栈是什么？（如果答案是"很多"，这是一个警示信号。）

**资源可行性：**
- 构建 MVP 所需的最小团队/投入是多少？
- 是否需要你不具备的专业能力？
- 是否有监管、法律或合规要求？

**价值交付时间：**
- 你能多快把东西放到用户面前？
- 是否存在一个能在几天/几周而非几个月内交付价值的版本？
- 关键路径是什么？什么必须先完成？

**危险信号：**
- "我们只需要先解决[非常难的研究问题]"
- 多个依赖项都需要同时就绪
- MVP 仍然需要数月工作——可能还不够"最小"

### 3. 差异化

什么让它真正不同？不是更好——是*不同*。

**需要追问的问题：**
- 如果用户向朋友描述这个，他们会怎么说？这个描述有说服力吗？
- 这件事做了而其他产品没做到的那一点是什么？（如果你说不上来，那就是问题。）
- 这种差异化是持久的吗？竞争对手能在一周内复制吗？
- 这个差异是用户真正在意的，还是只有构建者觉得有趣？

**差异化类型（从最强到最弱）：**
1. **新能力：** 做到了以前不可能的事情
2. **10 倍改进：** 在关键维度上好太多，足以改变用户行为
3. **新受众：** 将现有能力带给此前被排除在外的人群
4. **新场景：** 在现有方案失效的场景中发挥作用
5. **更好的 UX：** 相同能力，体验显著更简单
6. **更便宜：** 相同的东西，更低的成本（最弱——容易被竞争侵蚀）

**危险信号：**
- 差异化完全围绕技术，而非用户体验
- "我们更快/更便宜/更漂亮"却没有结构性原因
- 形成差异化的功能并非用户最关心的功能

## 假设审计

对每个想法方向，在以下三个类别中明确列出假设：

### 必须为真（致命条件）
如果为错，会彻底扼杀这个想法的假设。这些在构建前必须验证。

示例："用户愿意将数据共享给我们"——如果他们不愿意，整个产品就无法运作。

### 应当为真（重要）
显著影响成功但不会扼杀想法的假设。如果这些为错，你可以调整方案。

示例："用户更喜欢自助服务而非人工服务"——如果为错，你需要不同的市场策略，但核心产品仍然可行。

### 可能为真（锦上添花）
关于次要功能或优化的假设。在核心价值得到验证之前不要花精力验证这些。

示例："用户会想把结果分享给团队成员"——这是一个增长功能，不是核心价值主张。

## 决策框架

在选择方向时，按以下矩阵排列：

|                    | 高可行性 | 低可行性 |
|--------------------|----------|----------|
| **高价值**          | 优先做这个 | 值得冒险 |
| **低价值**          | 仅当成本微不足道 | 不要做 |

然后以差异化作为同一象限中选项之间的决胜条件。

## MVP 范围确定原则

在确定选定方向的 MVP 范围时：

1. **做好一件事。** MVP 应该精准地完成一项用户任务。不是三项任务做到半途而废。
2. **最危险的假设优先。** MVP 的首要目的是测试最可能为错的假设。
3. **时间盒，而非功能列表。** "我们在[时间范围]内能构建并测试什么？"优于"我们需要哪些功能？"
4. **"不做"清单是必须的。** 明确列出你砍掉了什么以及为什么。这能防止范围蔓延，迫使诚实的优先级排序。
5. **如果第一版不让人尴尬，说明你等太久了。** 第一个版本对构建者来说应该感觉不完整。如果不觉得，说明你构建过度了。
