# 可观测性与仪表化

## 概述

你无法观测的代码就是无法运维的代码。可观测性是利用代码发出的遥测数据从外部回答"系统在做什么以及为什么？"的能力。仪表化不是发布后附加的——它像测试一样，与功能一同编写。如果一个功能发布时没有遥测数据，第一个用户报告的 bug 就会变成考古学而不是一次查询。

## 何时使用

- 构建任何将在生产中运行的功能
- 添加新服务、端点、后台任务或外部集成
- 生产事件花了太长时间才诊断（"我们无法判断发生了什么"）
- 设置或审查告警规则
- 审查添加了 I/O、重试、队列或跨服务调用的 PR

**不适用于：**
- 诊断正在发生的故障——使用 `debugging-and-error-recovery` skill（可观测性是让那个 skill 下次更快的东西）
- 分析和优化已测量的缓慢——使用 `performance-optimization` skill
- 上线当天的监控检查清单和回滚触发器——参见 `shipping-and-launch` skill；此 skill 涵盖为其提供数据的仪表化

## 流程

### 1. 在仪表化之前定义"正常"

没有问题的遥测数据只是噪音。在添加任何仪表化之前，写出值班工程师会对这个功能问的 2-4 个问题：

```
FEATURE: 结账支付重试
QUESTIONS ON-CALL WILL ASK（值班人员会问的问题）:
1. 支付在首次尝试时成功的比例与重试后成功的比例各是多少？
2. 当支付永久失败时，为什么？（服务商错误？超时？验证？）
3. 支付服务商是否比平时更慢？
→ 下面每个信号必须帮助回答这些问题之一。
```

如果你不能说出问题，你就没准备好仪表化——你会记录一切却学不到任何东西。

### 2. 为每个问题选择合适的信号

| 信号 | 回答的问题 | 成本特征 | 示例 |
|---|---|---|---|
| **结构化日志** | "这个特定案例中发生了什么？" | 每个事件；随流量增长 | 带服务商错误码的 `payment_failed` |
| **指标** | "多频繁/多快，从总体看？" | 每个序列固定；查询便宜 | 服务商调用的 p99 延迟 |
| **追踪** | "时间花在哪里，跨服务？" | 每个请求；通常抽样 | 一次慢结账，按跳分解 |

经验法则：指标告诉你**有异常**，追踪告诉你**在哪里**，日志告诉你**为什么**。

### 3. 结构化日志

记录事件，而非散文。每一行日志都是一个带稳定事件名称和机器可读字段的 JSON 对 象：

```typescript
// BAD: 字符串插值——不可查询、不一致
logger.info(`Payment ${id} failed for user ${userId} after ${n} retries`);

// GOOD: 稳定的事件名称 + 结构化字段
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, 'payment failed');
```

**日志级别——一致地使用它们：**

| 级别 | 含义 | 值班操作 |
|---|---|---|
| `error` | 不变量被破坏；可能需要有人处理 | 调查 |
| `warn` | 降级但已处理（重试成功、使用了回退） | 关注趋势 |
| `info` | 重要的业务事件（订单已下、作业已完成） | 无 |
| `debug` | 诊断细节 | 生产环境默认关闭 |

**关联 ID 是强制性的。** 在系统边界生成（或接受）一个请求 ID，并将其附加到每一行日志、每个 span 和每个出站调用。没有它，你无法从交错的日志中重建单个请求：

```typescript
// Express: 每个请求的子 logger，ID 向下游传播
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

**永远不要记录 secrets、tokens、密码或完整的 PII。** 这是来自 `security-and-hardening` skill 的一条硬性规则——遥测管道是经典的数据泄露路径。使用 allowlist 白名单字段；不要记录整个请求体。

### 4. 指标

对于请求驱动的服务，为每个端点和每个外部依赖仪表化 **RED**：**R**ate（请求/秒）、**E**rrors（失败率）、**D**uration（延迟直方图，非平均值）。对于资源（队列、池、主机），使用 **USE**：**U**tilization（利用率）、**S**aturation（饱和度）、**E**rrors（错误）。

与追踪一样，供应商中立路径是 OpenTelemetry 指标 API（和步骤 5 相同的 SDK 和上下文）。下面的示例使用 Prometheus 的 `prom-client`——一种常见的后端选择，不是唯一的；RED/USE 和基数规则两种方式完全相同。

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 请求持续时间',
  labelNames: ['method', 'route', 'status_class'],  // '2xx'，而非 '200'
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**基数是失败模式。** 每个唯一的标签组合都是一个单独的时间序列。标签必须来自小的、固定的集合（路由模板、状态码类别、服务商名称）。永远不要使用用户 ID、原始 URL、错误消息或其他无界值作为标签——那些属于日志和追踪。

```
可以作为标签:    route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
永远不要作为标签:  user_id, email, request_id, 完整 URL, 错误消息文本
```

永远不要跟踪平均值，始终跟踪百分位数：平均值隐藏了 1% 体验极差的用户。使用直方图并读取 p50/p95/p99。

### 5. 分布式追踪

使用 OpenTelemetry——它是供应商中立的标 准，自动仪表化通过近乎零代码覆盖 HTTP、gRPC 和常见的数据库客户端：

```typescript
// tracing.ts — 必须在任何其他内容之前导入
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

仅在有意义的工作单元周围添加手动 span（如 `applyDiscounts`、`chargeProvider`）并附加值班人员会用于过滤的属性。在每个异步边界传播上下文——HTTP 头、队列消息元数据——否则追踪会在缝隙处中断。默认以低比率进行头采样；如果你的后端支持尾采样，保留 100% 的错误。

### 6. 告警

告警应针对**用户感受到的症状**，而非原因：

```
SYMPTOM (值得 page):              CAUSE (放在仪表盘上，不要 page):
error rate > 1% for 5 min         CPU 在 85%
p99 latency > 2s                  一个 pod 重启了
queue age > 10 min                磁盘在 70%
```

基于原因的告警会在一切正常时误报，并漏掉你没有预测到的故障。基于症状的告警恰好在用户受到影响时触发，无论原因是什么。

你创建的每条告警的规则：

1. **它必须是可操作的。** 如果响应是"忽略它，它会自愈"，删除这条告警。
2. **它链接到 runbook**——即使只有三行：它意味着什么、要运行的第一个查询、升级路径。
3. **它有一个由 SLO 或历史数据（而非猜测）证明合理的阈值和持续时间。**
4. 只使用两种严重性：**page**（面向用户，立即行动）和 **ticket**（退化，本周内处理）。第三个级别会成为噪音，训练人们忽略一切。

### 7. 验证遥测数据本身

仪表化是代码；它可能是错的。在把工作称为完成之前，触发这些路径并查看实际输出：

- 在 staging 环境中强制产生一个错误 → 通过 `requestId` 在日志中找到它，确认字段是结构化的（不是 `[object Object]`）
- 发送测试流量 → 确认指标序列按预期标签和合理值出现
- 在追踪 UI 中跨服务追踪一个请求 → 没有断开的 span
- 触发每条新的告警一次（临时降低阈值）→ 确认它到达了正确的通道且 runbook 链接有效

## 常见借口

| 借口 | 现实 |
|---|---|
| "它工作了再加日志" | "之后"变成"第一次事件后"，那是发现你什么也看不到的最昂贵时机。边构建边仪表化。 |
| "越多日志 = 越多可观测性" | 非结构化噪音让事件更慢，而非更快。三个可查询的事件胜过三百行散文。 |
| "console.log 现在够用" | 非结构化输出无法被过滤、关联或告警。结构化日志一次多花五分钟。 |
| "出问题了我们直接看仪表盘就行" | 没有定义问题就建的仪表盘会向你展示一切，除了答案。从值班问题出发。 |
| "所有重要的事情都告警，以后再做调整" | 嘈杂的 pager 训练人们忽略它。调整从不会发生；错过的真实 page 却会。 |
| "用户 ID 作为指标标签让调试更容易" | 它也会让你的指标后端挂掉。高基数查找属于日志和追踪。 |
| "我们的两个服务追踪有点过度" | 两个服务已经意味着日志无法回答跨服务延迟问题。自动仪表化让成本微不足道。 |

## 警示信号

- 一个有重试、队列或外部调用的功能 PR 没有任何新增遥测
- 日志行通过字符串插值构建，而非结构化字段
- 没有关联/请求 ID——每行日志都是孤儿
- 指标以用户 ID、原始 URL 或错误消息文本为标签（基数炸弹）
- 延迟以平均值跟踪，没有百分位数
- 告警每天都触发，被确认但未处理
- 基于原因（CPU、内存）的告警在 page 人，而面向用户的错误率未受监控
- Secrets、tokens 或完整请求体出现在日志中
- "在我机器上正常工作"是生产功能健康的唯一证据

## 验证

仪表化一个功能后，确认：

- [ ] 此功能的值班问题已写下来，每个信号对应一个问题
- [ ] 所有日志输出是结构化的（JSON），有稳定的事件名称和每行的关联 ID
- [ ] 没有任何 secrets、tokens 或未脱敏的 PII 出现在任何日志行中（抽查实际输出）
- [ ] 每个新端点和每个外部依赖存在 RED 指标，标签集合有界
- [ ] 延迟是直方图；p95/p99 可查询
- [ ] 单个请求可以在追踪 UI 中端到端追踪，没有断开的 span
- [ ] 每条新告警是基于症状的，有 runbook 链接，并被测试触发过一次
- [ ] 在 staging 中诱导的故障仅通过遥测数据就被定位，无需阅读源码
