# 废弃与迁移

## 概述

代码是负债，而非资产。每一行代码都有持续的维护成本——bug 要修复、依赖要更新、安全补丁要应用、新工程师要上手。废弃是移除不再值得保留的代码的纪律，迁移是将用户从旧的系统安全地迁移到新的系统的过程。

大多数工程组织擅长建东西。少数擅长移除东西。此 skill 解决这个差距。

## 何时使用

- 用新系统、API 或库替换旧系统
- 淘汰不再需要的功能
- 合并重复的实现
- 移除无人负责但每个人都在依赖的死代码
- 规划新系统的生命周期（废弃规划从设计时开始）
- 决定是维护遗留系统还是投入迁移

## 核心原则

### 代码是负债

每一行代码都有持续的成本：它需要测试、文档、安全补丁、依赖更新，以及给任何在附近工作的人带来的心智开销。代码的价值是它提供的功能，而不是代码本身。当同样的功能可以用更少的代码、更少的复杂性或更好的抽象来提供时——旧代码应该去掉。

### Hyrum 定律使移除变得困难

有了足够多的用户，每一个可观察的行为都会成为被依赖的行为——包括 bug、时序上的怪异和无文档化的副作用。这就是为什么废弃需要主动迁移，而不仅仅是公告。当用户依赖于替代品没有复制的行为时，他们无法"就这样切换"。

### 废弃规划从设计时开始

在构建新东西时，问自己："我们怎样在 3 年后移除它？"以干净的接口、功能标志和最小的表面积设计的系统，比到处泄漏实现细节的系统更容易废弃。

## 废弃决策

在废弃任何东西之前，回答这些问题：

```
1. 这个系统是否仍然提供独特的价值？
   → 如果是，维护它。如果否，继续。

2. 有多少用户/消费者依赖它？
   → 量化迁移范围。

3. 是否存在替代品？
   → 如果没有，先构建替代品。没有替代方案就不要废弃。

4. 每个消费者的迁移成本是多少？
   → 如果可以自动化地微不足道，就做。如果是手动的且高投入，权衡维护成本。

5. 不废弃的持续维护成本是什么？
   → 安全风险、工程师时间、复杂性的机会成本。
```

## 强制 vs. 建议性废弃

| 类型 | 何时使用 | 机制 |
|------|-------------|-----------|
| **建议性** | 迁移是可选的，旧系统是稳定的 | 警告、文档、提示。用户按自己的时间线迁移。 |
| **强制** | 旧系统有安全问题、阻碍进展、或维护成本不可持续 | 硬性截止日期。旧系统将在日期 X 被移除。提供迁移工具。 |

**默认为建议性。** 仅当维护成本或风险证明强制迁移合理时使用强制方式。强制废弃要求提供迁移工具、文档和支持——你不能只是宣布一个截止日期。

## 迁移流程

### 第 1 步：构建替代品

没有可行的替代品就不要废弃。替代品必须：

- 覆盖旧系统的所有关键用例
- 有文档和迁移指南
- 在生产中得到验证（不仅仅是"理论上更好"）

### 第 2 步：公告和文档化

```markdown
## Deprecation Notice（废弃通知）: OldService

**Status（状态）:** 自 2025-03-01 起废弃
**Replacement（替代品）:** NewService（参见下面的迁移指南）
**Removal date（移除日期）:** 建议性——尚无硬性截止日期
**Reason（原因）:** OldService 需要手动扩缩容且缺乏可观测性。
             NewService 自动处理这些。

### Migration Guide（迁移指南）
1. 替换 `import { client } from 'old-service'` 为 `import { client } from 'new-service'`
2. 更新配置（参见下面的示例）
3. 运行迁移验证脚本: `npx migrate-check`
```

### 第 3 步：增量迁移

一次迁移一个消费者，而不是一次性全部迁移。对每个消费者：

```
1. 识别与废弃系统的所有接触点
2. 更新为使用替代品
3. 验证行为匹配（测试、集成检查）
4. 移除对旧系统的引用
5. 确认没有回归
```

**搅动规则：** 如果你拥有被废弃的基础设施，你有责任迁移你的用户——或提供不需要迁移的向后兼容更新。不要宣布废弃然后让用户自行解决。

### 第 4 步：移除旧系统

仅在所有消费者都已迁移之后：

```
1. 验证零活跃使用（指标、日志、依赖分析）
2. 移除代码
3. 移除相关测试、文档和配置
4. 移除废弃通知
5. 庆祝——移除代码是一项成就
```

## 迁移模式

### Strangler 模式

并行运行新旧系统。将流量从旧系统增量路由到新系统。当旧系统处理 0% 流量时，移除它。

```
Phase 1: 新系统处理 0%，旧系统处理 100%
Phase 2: 新系统处理 10%（金丝雀）
Phase 3: 新系统处理 50%
Phase 4: 新系统处理 100%，旧系统闲置
Phase 5: 移除旧系统
```

### Adapter 模式

创建一个适配器，将来自旧接口的调用转换到新实现。消费者继续使用旧接口，同时你迁移后端。

```typescript
// Adapter: 旧接口，新实现
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 旧方法签名，委托给新实现
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }
}
```

### 功能标志迁移

使用功能标志将消费者一次一个地从旧系统切换到新系统：

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new LegacyTaskService();
}
```

## 僵尸代码

僵尸代码是无人负责但每个人都在依赖的代码。它不被主动维护，没有明确的所有者，并累积安全漏洞和兼容性问题。迹象：

- 6 个月以上没有提交，但有活跃消费者
- 没有指派的维护者或团队
- 失败的测试无人修复
- 有已知漏洞的依赖无人更新
- 文档引用已经不存在的系统

**响应：** 要么指定一个所有者并正确维护它，要么用一个具体的迁移计划废弃它。僵尸代码不能留在 limbo 中——要么得到投入，要么被移除。

## 常见借口

| 借口 | 现实 |
|---|---|
| "它还能用，为什么要移除？" | 能运行但无人维护的代码会累积安全债务和复杂性。维护成本在无声增长。 |
| "有人以后可能需要它" | 如果以后需要，可以重建。保留不用的代码"以防万一"比重建代价更高。 |
| "迁移太贵了" | 比较迁移成本与 2-3 年的持续维护成本。迁移通常在长期来看更便宜。 |
| "我们完成新系统后再废弃它" | 废弃规划从设计时开始。到新系统完成时，你会有新的优先级。现在就规划。 |
| "用户会自行迁移" | 他们不会。提供工具、文档和激励——或由你自己做迁移（搅动规则）。 |
| "我们可以无限期地维护两个系统" | 两个做同一件事的系统是双倍的维护、测试、文档和上手成本。 |

## 警示信号

- 废弃的系统没有可用的替代品
- 废弃公告没有迁移工具或文档
- "软"废弃已建议多年但没有进展
- 僵尸代码没有所有者且有活跃消费者
- 向废弃的系统添加新功能（应投资于替代品）
- 未测量当前使用量就废弃
- 未验证零活跃消费者就移除代码

## 验证

完成废弃后：

- [ ] 替代品已在生产中得到验证并涵盖所有关键用例
- [ ] 迁移指南存在，包含具体步骤和示例
- [ ] 所有活跃消费者已迁移（通过指标/日志验证）
- [ ] 旧代码、测试、文档和配置已完全移除
- [ ] 代码库中不再有对废弃系统的引用
- [ ] 废弃通知已移除（它们已经完成了使命）
