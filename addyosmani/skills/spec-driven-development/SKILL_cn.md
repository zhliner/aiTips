# Spec 驱动开发

## 概述

在编写任何代码之前编写结构化的规格说明。Spec 是你和人类工程师之间共享的真实来源——它定义了我们正在构建什么、为什么、以及我们如何知道完成了。没有 spec 的代码是猜测。

## 何时使用

- 开始一个新项目或功能
- 需求模糊或不完整
- 变更涉及多个文件或模块
- 你即将做出架构决策
- 任务需要超过 30 分钟来实现

**何时不使用：** 单行修复、拼写错误修正，或需求明确且自包含的变更。

## 门控工作流

Spec 驱动开发有四个阶段。在当前阶段被验证之前，不要推进到下一个阶段。

```
SPECIFY（规格说明）──→ PLAN（计划）──→ TASKS（任务）──→ IMPLEMENT（实现）
    │                    │                 │                   │
    ▼                    ▼                 ▼                   ▼
  人类审查             人类审查           人类审查            人类审查
```

### 阶段 1：规格说明

从一个高层次的愿景开始。向人类提问澄清，直到需求具体化。

**立即公开假设。** 在编写任何 spec 内容之前，列出你正在假设的内容：

```
ASSUMPTIONS I'M MAKING（我正在做的假设）:
1. 这是一个 Web 应用（非原生移动端）
2. 认证使用基于 session 的 cookie（非 JWT）
3. 数据库是 PostgreSQL（基于现有的 Prisma schema）
4. 我们仅针对现代浏览器（不支持 IE11）
→ 现在纠正我，否则我将基于这些推进。
```

不要默默填补模糊的需求。Spec 的全部目的就是在代码编写之前暴露误解——假设是最危险的误解形式。

**编写涵盖这六个核心领域的 spec 文档：**

1. **Objective（目标）** — 我们正在构建什么以及为什么？用户是谁？成功是什么样子？

2. **Commands（命令）** — 完整的可执行命令及标志，不仅仅是工具名称。
   ```
   Build: npm run build
   Test: npm test -- --coverage
   Lint: npm run lint --fix
   Dev: npm run dev
   ```

3. **Project Structure（项目结构）** — 源代码在哪里、测试放哪里、文档在哪里。
   ```
   src/           → 应用源代码
   src/components → React 组件
   src/lib        → 共享工具函数
   tests/         → 单元和集成测试
   e2e/           → 端到端测试
   docs/          → 文档
   ```

4. **Code Style（代码风格）** — 一个展示你风格的真实代码片段胜过三段描述它的文字。包含命名约定、格式化规则和良好输出的示例。

5. **Testing Strategy（测试策略）** — 什么框架、测试放哪里、覆盖率期望、不同关注点使用哪个测试级别。

6. **Boundaries（边界）** — 三层系统：
   - **始终做：** 提交前运行测试、遵循命名约定、验证输入
   - **先询问：** 数据库模式变更、添加依赖、更改 CI 配置
   - **永远不做：** 提交 secrets、编辑 vendor 目录、未经批准删除失败的测试

**Spec 模板：**

```markdown
# Spec: [项目/功能名称]

## Objective（目标）
[我们正在构建什么以及为什么。用户故事或验收标准。]

## Tech Stack（技术栈）
[框架、语言、关键依赖及版本]

## Commands（命令）
[构建、测试、lint、开发 — 完整命令]

## Project Structure（项目结构）
[带描述的目录布局]

## Code Style（代码风格）
[示例代码片段 + 关键约定]

## Testing Strategy（测试策略）
[框架、测试位置、覆盖率要求、测试级别]

## Boundaries（边界）
- Always（始终做）: [...]
- Ask first（先询问）: [...]
- Never（永远不做）: [...]

## Success Criteria（成功标准）
[我们如何知道这完成了——具体的、可测试的条件]

## Open Questions（未解决问题）
[任何未解决的需要人类输入的问题]
```

**将指令重构为成功标准。** 当收到模糊需求时，将其转化为具体条件：

```
REQUIREMENT: "让仪表盘更快"

REFRAMED SUCCESS CRITERIA（重构后的成功标准）:
- 仪表盘 LCP 在 4G 连接下 < 2.5s
- 初始数据加载在 < 500ms 内完成
- 加载期间无布局偏移 (CLS < 0.1)
→ 这些是正确的目标吗？
```

这让你能够朝一个清晰的目标循环、重试和解决问题，而不是猜测"更快"意味着什么。

### 阶段 2：计划

有了已验证的 spec，生成技术实现计划：

1. 识别主要组件及其依赖
2. 确定实现顺序（必须先构建什么）
3. 注明风险及缓解策略
4. 识别什么可以并行构建 vs. 什么必须按顺序
5. 定义各阶段之间 的验证检查点

> 遵循 `planning-and-task-breakdown` 了解这些步骤背后的依赖图映射和垂直切片机制；它是规范来源。以上要点是轻量摘要；如果它们不一致，以 `planning-and-task-breakdown` 为准。

计划应该是可审查的：人类应该能够阅读它并说"是的，这是正确的方法"或"不，改变 X。"

### 阶段 3：任务

将计划分解为离散的、可实现的任 务：

- 每个任务应该可以在一个专注会话中完成
- 每个任务有明确的验收标准
- 每个任务包含一个验证步骤（测试、构建、手动检查）
- 任务按依赖排序，而非按感知的重要性
- 没有任务应要求修改超过约 5 个文件

> 遵循 `planning-and-task-breakdown` 了解完整的任务规模和依赖排序机制；它是规范来源。下面的模板是轻量内联形式；如果它们不一致，以 `planning-and-task-breakdown` 为准。

**任务模板：**
```markdown
- [ ] Task（任务）: [描述]
  - Acceptance（验收）: [完成时必须为真的条件]
  - Verify（验证）: [如何确认 — 测试命令、构建、手动检查]
  - Files（文件）: [将涉及哪些文件]
```

### 阶段 4：实现

一次执行一个任务，遵循 `skills/incremental-implementation/SKILL.md`（`incremental-implementation`）和 `skills/test-driven-development/SKILL.md`（`test-driven-development`）。使用 `skills/context-engineering/SKILL.md`（`context-engineering`）在每个步骤加载正确的 spec 节和源文件，而不是用整个 spec 浇灌 agent。

## 保持 Spec 活跃

Spec 是一份活文档，而非一次性产物：

- **当决策变化时更新** — 如果你发现数据模型需要改变，先更新 spec，再实现。
- **当范围变化时更新** — 添加或削减的功能应反映在 spec 中。
- **提交 spec** — Spec 与代码一起属于版本控制。
- **在 PR 中引用 spec** — 链接回每个 PR 实现的 spec 节。

## 常见借口

| 借口 | 现实 |
|---|---|
| "这很简单，我不需要 spec" | 简单任务不需要*长* spec，但它们仍然需要验收标准。两行的 spec 也可以。 |
| "我编码后再写 spec" | 那是文档，不是规格说明。Spec 的价值在于在代码之前强制清晰。 |
| "Spec 会让我们慢下来" | 15 分钟的 spec 预防数小时的返工。15 分钟的瀑布胜于 15 小时的调试。 |
| "需求反正是会变的" | 这就是 spec 是活文档的原因。过时的 spec 仍然比没有 spec 好。 |
| "用户知道他们想要什么" | 即使清晰的请求也有隐含的假设。Spec 暴露那些假设。 |

## 警示信号

- 没有任何书面需求就开始写代码
- 在澄清"完成"意味着什么之前就问"我应该开始构建吗？"
- 实现任何 spec 或任务列表中未提及的功能
- 做出架构决策而没有记录它们
- 因为"建什么很明显"就跳过 spec

## 验证

在进入实现阶段之前，确认：

- [ ] Spec 涵盖所有六个核心领域
- [ ] 人类已审查并批准该 spec
- [ ] 成功标准是具体且可测试的
- [ ] 边界（Always/Ask First/Never）已定义
- [ ] Spec 已保存到仓库中的文件
