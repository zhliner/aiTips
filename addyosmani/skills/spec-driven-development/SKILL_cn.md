# 规格驱动开发（Spec-Driven Development）

## 概述

在编写任何代码之前，先编写结构化的规格说明。规格说明是你与人类工程师之间的共享真实来源——它定义了我们正在构建什么、为什么构建，以及如何判断它已完成。没有规格说明的代码就是在猜测。

## 何时使用

- 启动新项目或新功能时
- 需求模糊或不完整时
- 变更涉及多个文件或模块时
- 即将做出架构决策时
- 任务实现时间超过 30 分钟时

**不应使用的场景：** 单行修复、拼写纠正，或需求明确且自包含的变更。

## 门控工作流（Gated Workflow）

规格驱动开发分为四个阶段。在当前阶段验证通过之前，不要进入下一阶段。

```
SPECIFY ──→ PLAN ──→ TASKS ──→ IMPLEMENT
   │          │        │          │
   ▼          ▼        ▼          ▼
 人类        人类      人类       人类
 审核        审核      审核       审核
```

### 阶段 1：规格说明（Specify）

从高层愿景开始。向人类提出澄清性问题，直到需求变得具体明确。

**立即暴露假设。** 在编写任何规格内容之前，列出你所做的假设：

```
我所做的假设：
1. 这是一个 Web 应用（而非原生移动端）
2. 认证使用基于 session 的 cookie（而非 JWT）
3. 数据库是 PostgreSQL（基于现有 Prisma schema）
4. 我们只针对现代浏览器（不支持 IE11）
→ 请现在纠正我，否则我将按这些假设继续。
```

不要默默填充模糊的需求。规格说明的全部目的就是在代码编写*之前*暴露误解——假设是最危险的误解形式。

**编写覆盖以下六个核心领域的规格文档：**

1. **目标** — 我们在构建什么？为什么？用户是谁？成功的样子是什么？

2. **命令** — 完整的可执行命令及参数，而不仅仅是工具名称。
   ```
   Build: npm run build
   Test: npm test -- --coverage
   Lint: npm run lint --fix
   Dev: npm run dev
   ```

3. **项目结构** — 源代码在哪里，测试放在哪里，文档归属何处。
   ```
   src/           → 应用程序源代码
   src/components → React 组件
   src/lib        → 共享工具库
   tests/         → 单元测试和集成测试
   e2e/           → 端到端测试
   docs/          → 文档
   ```

4. **代码风格** — 一个展示你风格的真实代码片段胜过三段描述性文字。包含命名规范、格式化规则和良好输出的示例。

5. **测试策略** — 使用什么框架，测试放在哪里，覆盖率期望，哪些测试级别对应哪些关注点。

6. **边界** — 三层体系：
   - **始终执行：** 提交前运行测试，遵循命名规范，验证输入
   - **先询问：** 数据库 schema 变更，添加依赖，修改 CI 配置
   - **绝不执行：** 提交密钥，编辑 vendor 目录，未经批准删除失败的测试

**规格模板：**

```markdown
# 规格说明：[项目/功能名称]

## 目标
[我们在构建什么以及为什么。用户故事或验收标准。]

## 技术栈
[框架、语言、关键依赖及版本]

## 命令
[构建、测试、代码检查、开发——完整命令]

## 项目结构
[目录布局及描述]

## 代码风格
[示例代码片段 + 关键规范]

## 测试策略
[框架、测试位置、覆盖率要求、测试级别]

## 边界
- 始终：[...]
- 先询问：[...]
- 绝不：[...]

## 成功标准
[我们如何知道这已完成——具体的、可测试的条件]

## 待解决问题
[任何需要人类输入的未解决事项]
```

**将指令重构为成功标准。** 当收到模糊的需求时，将其转化为具体条件：

```
需求："让仪表板更快"

重构后的成功标准：
- 仪表板在 4G 连接下 LCP < 2.5s
- 初始数据加载在 < 500ms 内完成
- 加载期间无布局偏移（CLS < 0.1）
→ 这些是正确的目标吗？
```

这让你能够围绕一个清晰的目标进行循环、重试和问题解决，而不是猜测"更快"意味着什么。

### 阶段 2：规划（Plan）

基于已验证的规格说明，生成技术实现计划：

1. 识别主要组件及其依赖关系
2. 确定实现顺序（什么必须先构建）
3. 记录风险和缓解策略
4. 识别哪些可以并行构建，哪些必须按顺序进行
5. 定义各阶段之间的验证检查点

> 关于依赖图映射和纵向切片机制，请遵循 `planning-and-task-breakdown`；它是权威来源。上述要点是简要概述；如有分歧，以 `planning-and-task-breakdown` 为准。

计划应该是可审核的：人类应该能够阅读它并说"是的，这是正确的方法"或"不，修改 X。"

### 阶段 3：任务（Tasks）

将计划拆分为离散的、可实现的任务：

- 每个任务应能在一次专注的会话中完成
- 每个任务有明确的验收标准
- 每个任务包含一个验证步骤（测试、构建、手动检查）
- 任务按依赖关系排序，而非按感知的重要性排序
- 每个任务不应涉及修改超过约 5 个文件

> 关于完整的任务规模评估和依赖排序机制，请遵循 `planning-and-task-breakdown`；它是权威来源。以下模板是简要的内联形式；如有分歧，以 `planning-and-task-breakdown` 为准。

**任务模板：**
```markdown
- [ ] 任务：[描述]
  - 验收标准：[完成时必须满足的条件]
  - 验证方式：[如何确认——测试命令、构建、手动检查]
  - 涉及文件：[将被修改的文件]
```

### 阶段 4：实现（Implement）

逐个执行任务，遵循 `skills/incremental-implementation/SKILL.md`（`incremental-implementation`）和 `skills/test-driven-development/SKILL.md`（`test-driven-development`）。使用 `skills/context-engineering/SKILL.md`（`context-engineering`）在每一步加载正确的规格部分和源文件，而不是将整个规格一次性灌给 agent。

## 保持规格说明的时效性

规格说明是活文档，不是一次性产物：

- **决策变更时更新** — 如果你发现数据模型需要更改，先更新规格说明，然后再实现。
- **范围变更时更新** — 新增或删减的功能应反映在规格说明中。
- **提交规格说明** — 规格说明应与代码一起纳入版本控制。
- **在 PR 中引用规格说明** — 链接回每个 PR 所实现的规格说明部分。

## 常见的自我合理化

| 自我合理化 | 现实 |
|---|---|
| "这很简单，不需要规格说明" | 简单任务不需要*长篇*规格说明，但仍然需要验收标准。两行规格说明就够了。 |
| "我先写完代码再补规格说明" | 那是文档，不是规格说明。规格说明的价值在于*在编码之前*迫使你理清思路。 |
| "规格说明会拖慢我们" | 15 分钟的规格说明能避免数小时的返工。15 分钟的瀑布式规划胜过 15 小时的调试。 |
| "需求反正会变" | 正因如此规格说明才是活文档。过时的规格说明仍然好过没有规格说明。 |
| "用户知道他们想要什么" | 即使是明确的需求也有隐含假设。规格说明能暴露这些假设。 |

## 危险信号

- 没有任何书面需求就开始写代码
- 在澄清"完成"的含义之前就问"我是不是直接开始做就好？"
- 实现了规格说明或任务列表中未提及的功能
- 做出架构决策却不记录下来
- 因为"很明显该构建什么"就跳过规格说明

## 验证

在进入实现之前，确认：

- [ ] 规格说明涵盖了所有六个核心领域
- [ ] 人类已审核并批准规格说明
- [ ] 成功标准是具体的、可测试的
- [ ] 边界（始终/先询问/绝不）已定义
- [ ] 规格说明已保存到仓库中的文件
