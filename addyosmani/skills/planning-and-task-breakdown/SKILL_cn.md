# 规划与任务拆解

## 概述

将工作分解为具有明确验收标准的小型、可验证任务。好的任务拆解是 agent 能够可靠完成工作与产生一团乱麻之间的区别。每个任务应该小到能在单次聚焦会话中实现、测试和验证。

## 适用场景

- 你已有规格文档，需要将其拆分为可实施单元
- 某项任务感觉太大或太模糊而无法开始
- 需要跨多个 agent 或会话并行化工作
- 需要向人类传达范围
- 实现顺序不明显

**不适用时：** 范围明显的单文件变更，或规格中已包含定义良好的任务时。

## 规划过程

### 第 1 步：进入规划模式

在编写任何代码之前，以只读模式操作：

- 阅读规格和代码库相关部分
- 识别现有的模式和约定
- 映射组件之间的依赖关系
- 记录风险和未知项

**规划期间不要编写代码。** 输出是规划文档，不是实现。

### 第 2 步：识别依赖图

映射什么依赖什么：

```
数据库 schema
    │
    ├── API 模型/类型
    │       │
    │       ├── API 端点
    │       │       │
    │       │       └── 前端 API 客户端
    │       │               │
    │       │               └── UI 组件
    │       │
    │       └── 验证逻辑
    │
    └── 种子数据/迁移
```

实现顺序自底向上遵循依赖图：先构建基础。

### 第 3 步：垂直切片

并非先构建所有数据库，再构建所有 API，再构建所有 UI——而是一次构建一条完整的功能路径：

**不好（水平切片）：**
```
任务 1：构建整个数据库 schema
任务 2：构建所有 API 端点
任务 3：构建所有 UI 组件
任务 4：连接一切
```

**好（垂直切片）：**
```
任务 1：用户可以创建账户（注册的 schema + API + UI）
任务 2：用户可以登录（登录的认证 schema + API + UI）
任务 3：用户可以创建任务（任务创建的 schema + API + UI）
任务 4：用户可以查看任务列表（列表视图的查询 + API + UI）
```

每个垂直切片都交付可工作、可测试的功能。

### 第 4 步：编写任务

每个任务遵循以下结构：

```markdown
## 任务 [N]：[简短描述性标题]

**描述：** 一段话说明本任务完成什么。

**验收标准：**
- [ ] [具体的、可测试的条件]
- [ ] [具体的、可测试的条件]

**验证：**
- [ ] 测试通过：`npm test -- --grep "feature-name"`
- [ ] 构建成功：`npm run build`
- [ ] 手动检查：[说明要验证什么]

**依赖项：** [本任务依赖的任务编号，或"无"]

**可能涉及的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**预估范围：** [小：1-2 个文件 | 中：3-5 个文件 | 大：5+ 个文件]
```

### 第 5 步：排序和检查点

安排任务顺序，使得：

1. 依赖关系得到满足（先构建基础）
2. 每个任务使系统处于可工作状态
3. 每 2-3 个任务后有验证检查点
4. 高风险任务排在前面（尽早失败）

添加明确的检查点：

```markdown
## 检查点：任务 1-3 之后
- [ ] 所有测试通过
- [ ] 应用无错误构建
- [ ] 核心用户流程端到端工作
- [ ] 继续前与人类评审
```

## 任务规模指南

| 规模 | 文件数 | 范围 | 示例 |
|------|-------|-------|---------|
| **XS** | 1 | 单个函数或配置变更 | 添加一个验证规则 |
| **S** | 1-2 | 一个组件或端点 | 添加一个新的 API 端点 |
| **M** | 3-5 | 一个功能切片 | 用户注册流程 |
| **L** | 5-8 | 多组件功能 | 带筛选和分页的搜索 |
| **XL** | 8+ | **太大了——进一步拆分** | — |

如果任务是 L 级或更大，应将其拆分为更小的任务。Agent 在 S 和 M 级别的任务上表现最佳。

**何时需要进一步拆分任务：**
- 需要超过一次聚焦会话（大约 2 小时以上的 agent 工作）
- 你无法用 3 个或更少的要点描述验收标准
- 涉及两个或更多独立子系统（例如认证和计费）
- 你发现自己在任务标题中写"和"（这表明它实际上是两个任务）

## 规划文档模板

```markdown
# 实现计划：[功能/项目名称]

## 概述
[一段话总结我们在构建什么]

## 架构决策
- [关键决策 1 和理由]
- [关键决策 2 和理由]

## 任务列表

### 阶段 1：基础
- [ ] 任务 1：...
- [ ] 任务 2：...

### 检查点：基础
- [ ] 测试通过，构建无错误

### 阶段 2：核心功能
- [ ] 任务 3：...
- [ ] 任务 4：...

### 检查点：核心功能
- [ ] 端到端流程正常工作

### 阶段 3：打磨
- [ ] 任务 5：...
- [ ] 任务 6：...

### 检查点：完成
- [ ] 所有验收标准已满足
- [ ] 准备好评审

## 风险与缓解措施
| 风险 | 影响 | 缓解策略 |
|------|--------|------------|
| [风险] | [高/中/低] | [策略] |

## 待定问题
- [需要人类输入的问题]
```

## 并行化机会

当有多个 agent 或会话可用时：

- **可安全并行：** 独立的功能切片、已实现功能的测试、文档
- **必须顺序执行：** 数据库迁移、共享状态变更、依赖链
- **需要协调：** 共享一个 API 合约的功能（先定义合约，然后并行化）

## 常见合理化借口

| 借口 | 现实 |
|---|---|
| "我边做边想" | 这就是你会搞成一团乱麻并需要重做的原因。10 分钟规划节省数小时。 |
| "任务很明显啊" | 无论如何都写下来。显式化的任务会暴露出隐藏的依赖和被遗忘的边缘情况。 |
| "规划是额外开销" | 规划就是任务本身。没有计划的实现只是打字。 |
| "我脑子里都装着就行了" | 上下文窗口是有限的。写下来的计划能跨会话边界和压缩存活。 |

## 危险信号

- 没有书面任务列表就开始实现
- 任务只写"实现某某功能"而没有验收标准
- 计划中没有验证步骤
- 所有任务都是 XL 级
- 任务之间没有检查点
- 没有考虑依赖顺序

## 验证

开始实现前，确认：

- [ ] 每个任务都有验收标准
- [ ] 每个任务都有验证步骤
- [ ] 任务依赖关系已识别并正确排序
- [ ] 没有任务涉及超过约 5 个文件
- [ ] 主要阶段之间存在检查点
- [ ] 人类已评审并批准计划

## 参见

验收标准针对每个任务，回答"我们是否构建了正确的东西？"。它建立在项目级完成定义（Definition of Done）之上，后者是每个任务在算作完成前必须达到的固定标准。参见 `references/definition-of-done.md`。
