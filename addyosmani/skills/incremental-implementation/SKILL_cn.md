# 增量实现（Incremental Implementation）

## 概述

以薄的垂直切片构建——实现一部分，测试它，验证它，然后扩展。避免一次性实现整个功能。每个增量都应使系统处于可工作、可测试的状态。这是使大型功能可控的执行纪律。

## 何时使用

- 实现任何涉及多文件的变更
- 从任务分解中构建新功能
- 重构现有代码
- 任何时候你想要在测试前编写超过约 100 行代码

**不应使用的场景：** 单文件、单函数的变更，范围已经很小。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐        │
│       ▲                     │        │
│       └───── 提交 ◄─────────┘        │
│              │                       │
│              ▼                       │
│          下一个切片                    │
│                                      │
└──────────────────────────────────────┘
```

对于每个切片：

1. **实现** 最小完整的功能单元
2. **测试** — 运行测试套件（或编写测试，如果尚不存在）
3. **验证** — 确认切片按预期工作（测试通过、构建成功、手动检查）
4. **提交** — 使用描述性消息保存进度（参见 `git-workflow-and-versioning` 获取原子提交指导）
5. **进入下一个切片** — 继续前进，不要重新开始

## 切片策略

### 垂直切片（推荐）

构建一条贯穿技术栈的完整路径：

```
切片 1：创建任务（DB + API + 基础 UI）
    → 测试通过，用户可以通过 UI 创建任务

切片 2：列出任务（查询 + API + UI）
    → 测试通过，用户可以查看他们的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户可以修改任务

切片 4：删除任务（删除 + API + UI + 确认）
    → 测试通过，完整 CRUD 完成
```

每个切片交付可工作的端到端功能。

### 契约优先切片

当后端和前端需要并行开发时：

```
切片 0：定义 API 契约（types、interfaces、OpenAPI spec）
切片 1a：根据契约实现后端 + API 测试
切片 1b：根据匹配契约的 mock 数据实现前端
切片 2：集成并进行端到端测试
```

### 风险优先切片

优先处理风险最高或最不确定的部分：

```
切片 1：验证 WebSocket 连接可用（最高风险）
切片 2：在已验证的连接上构建实时任务更新
切片 3：添加离线支持和重连功能
```

如果切片 1 失败，你在投入切片 2 和 3 之前就能发现问题。

## 实现规则

### 规则 0：简单优先

编写任何代码之前，问自己："能工作的最简单方案是什么？"

编写代码之后，对照以下检查项审查：
- 能否用更少的代码完成？
- 这些抽象是否值得其复杂性？
- 一位资深工程师看到后会说"你为什么不直接……"吗？
- 我是在为假设的未来需求构建，还是为当前任务？

```
简洁性检查：
✗ 为一个通知功能使用通用 EventBus 加中间件管道
✓ 简单的函数调用

✗ 为两个相似组件使用抽象工厂模式
✓ 两个简单组件配合共享工具函数

✗ 为三个表单使用配置驱动的表单构建器
✓ 三个表单组件
```

三行相似的代码优于过早的抽象。先实现朴素的、明显正确的版本。只在测试证明正确性之后再优化。

### 规则 0.5：范围纪律

只修改任务要求的部分。

不要：
- "顺手清理"变更附近的代码
- 在你未修改的文件中重构 import
- 删除你不完全理解的注释
- 添加规格中不存在的功能，仅仅因为它们"看起来有用"
- 在你只是阅读的文件中现代化语法

如果你注意到任务范围外值得改进的地方，记录下来——不要修复它：

```
注意到但不处理：
- src/utils/format.ts 有一个未使用的 import（与本任务无关）
- auth middleware 可以使用更好的错误消息（单独的任务）
→ 需要我为这些创建任务吗？
```

### 规则 1：一次一件事

每个增量只改变一个逻辑事项。不要混合关注点：

**错误：** 一个提交同时添加新组件、重构现有组件并更新构建配置。

**正确：** 三个独立提交——每个变更一个。

### 规则 2：保持可编译

每个增量之后，项目必须能够构建且现有测试必须通过。不要在切片之间让代码库处于损坏状态。

### 规则 3：为未完成的功能使用 Feature Flags

如果功能尚未准备好面向用户，但你需要合并增量：

```typescript
// 用于进行中功能的 Feature flag
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新的分享 UI
}
```

这让你可以将小增量合并到主分支，而不暴露未完成的工作。

### 规则 4：安全默认值

新代码应默认采用安全、保守的行为：

```typescript
// 安全：默认禁用，需主动开启
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：易于回滚

每个增量应可独立回滚：

- 增量变更（新文件、新函数）易于回滚
- 对现有代码的修改应尽量最小化和聚焦
- 数据库迁移应有对应的回滚迁移
- 避免在一个提交中删除某内容并在同一提交中替换——分开处理

## 与 Agent 协作

当指导 agent 增量实现时：

```
"让我们实现计划中的任务 3。

先从数据库 schema 变更和 API 端点开始。
暂时不要动 UI——我们将在下一个增量中处理。

实现后，运行 `npm test` 和 `npm run build` 来验证
没有破坏任何东西。"
```

明确每个增量的范围内和范围外内容。

## 增量检查清单

每个增量之后，验证：

- [ ] 变更只做一件事且完整完成
- [ ] 所有现有测试仍然通过（`npm test`）
- [ ] 构建成功（`npm run build`）
- [ ] 类型检查通过（`npx tsc --noEmit`）
- [ ] Lint 检查通过（`npm run lint`）
- [ ] 新功能按预期工作
- [ ] 变更已使用描述性消息提交

**注意：** 在可能影响验证命令的变更后运行每个验证命令。成功运行后，不要重复运行同一命令，除非代码在此期间发生了变更——在未变更的代码上重新运行不会增加任何信息。

## 常见的自我合理化

| 合理化借口 | 现实 |
|---|---|
| "我最后再一起测试" | Bug 会叠加。切片 1 的 Bug 会导致切片 2-5 全部出错。每个切片都要测试。 |
| "一次性做完更快" | 在出问题之前你*感觉*更快，然后你无法在 500 行变更中找到是哪行导致了问题。 |
| "这些变更太小了，不值得单独提交" | 小提交没有成本。大提交隐藏 Bug 并使回滚痛苦。 |
| "我稍后再加 feature flag" | 如果功能未完成，它不应该对用户可见。现在就加 flag。 |
| "这个重构足够小，可以包含进去" | 重构与功能混合会使两者都更难审查和调试。分开处理。 |
| "让我再运行一次构建命令确认一下" | 成功运行后，重复运行同一命令不会增加任何信息，除非代码在此期间发生了变更。在后续编辑后再运行，而不是作为心理安慰。 |

## 危险信号

- 编写超过 100 行代码而未运行测试
- 单个增量中包含多个不相关的变更
- "让我顺便也加上这个"的范围蔓延
- 为了加快速度而跳过测试/验证步骤
- 增量之间构建或测试处于损坏状态
- 大量未提交的变更在累积
- 在第三个使用场景出现之前就构建抽象
- "既然在这儿了"就修改任务范围外的文件
- 为一次性操作创建新的工具文件
- 连续两次运行相同的构建/测试命令而中间没有任何代码变更

## 验证

完成一个任务的所有增量后：

- [ ] 每个增量都已单独测试并提交
- [ ] 完整测试套件通过
- [ ] 构建干净无错
- [ ] 功能按规格端到端正常工作
- [ ] 没有未提交的变更残留

## 另见

每个增量的验证是局部检查。在宣布任务完成之前，应用项目级的 Definition of Done 作为最终关卡——无论什么任务，每个增量都必须达到的标准。参见 `references/definition-of-done.md`。
