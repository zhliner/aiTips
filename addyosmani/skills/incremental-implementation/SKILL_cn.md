# 增量实现

## 概述

以薄薄的垂直切片进行构建——实现一片、测试、验证，然后扩展。避免一次性实现整个功能。每个增量都应使系统处于可工作、可测试的状态。这是让大型功能可管理的执行纪律。

## 适用场景

- 实现任何多文件变更
- 根据任务拆解构建新功能
- 重构现有代码
- 任何你倾向于在测试前编写超过约 100 行代码的时候

**不适用时：** 单文件、单函数变更，范围已经很小的场景。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐         │
│       ▲                     │         │
│       └───── 提交 ◄─────────┘         │
│              │                        │
│              ▼                        │
│          下一片                       │
│                                      │
└──────────────────────────────────────┘
```

对每一片：

1. **实现**——最小的完整功能片段
2. **测试**——运行测试套件（或编写测试，如果还不存在）
3. **验证**——确认该片段按预期工作（测试通过、构建成功、手动检查）
4. **提交**——用描述性消息保存进度（参见 `git-workflow-and-versioning` 了解原子提交指导）
5. **进入下一片**——继续向前，不要重新开始

## 切片策略

### 垂直切片（首选）

构建一个贯穿整个技术栈的完整路径：

```
切片 1：创建任务（数据库 + API + 基础 UI）
    → 测试通过，用户可以通过 UI 创建任务

切片 2：列出任务（查询 + API + UI）
    → 测试通过，用户可以查看他们的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户可以修改任务

切片 4：删除任务（删除 + API + UI + 确认）
    → 测试通过，完整 CRUD 完成
```

每个切片都交付可工作的端到端功能。

### 合约优先切片

当后端和前端需要并行开发时：

```
切片 0：定义 API 合约（类型、接口、OpenAPI spec）
切片 1a：根据合约实现后端 + API 测试
切片 1b：根据匹配合约的模拟数据实现前端
切片 2：集成并进行端到端测试
```

### 风险优先切片

首先处理风险最高或最不确定的部分：

```
切片 1：证明 WebSocket 连接可行（风险最高）
切片 2：在已验证的连接上构建实时任务更新
切片 3：添加离线支持和重连
```

如果切片 1 失败了，你在投入切片 2 和 3 之前就能发现。

## 实现规则

### 规则 0：简单优先

在编写任何代码之前，先问："能工作的最简单方案是什么？"

编写代码后，对照以下检查进行评审：
- 可以用更少的行数完成吗？
- 这些抽象值得其带来的复杂度吗？
- 一位资深工程师看了会说"你为什么没直接……"吗？
- 我是在为假设中的未来需求做构建，还是为当前任务做构建？

```
简单性检查：
✗ 为一个通知构建带中间件管道的通用 EventBus
✓ 简单的函数调用

✗ 为两个相似组件使用抽象工厂模式
✓ 两个直接的组件加上共享工具函数

✗ 为三个表单构建配置驱动的表单生成器
✓ 三个表单组件
```

三行相似代码胜过过早的抽象。先实现朴素、明显正确的版本。仅在有测试证明正确性后再优化。

### 规则 0.5：范围纪律

只触碰任务需要的内容。

不要：
- "顺手清理"你变更旁边的代码
- 重构你没有修改的文件中的导入
- 移除你不完全理解的注释
- 因为"看起来有用"而添加规格中没有的功能
- 升级你只是读取的文件的语法

如果你注意到任务范围外值得改进的地方，记录下来——但不要修复：

```
注意到但不处理：
- src/utils/format.ts 中有一个未使用的导入（与本次任务无关）
- 认证中间件可以使用更好的错误消息（独立任务）
→ 需要我为这些创建任务吗？
```

### 规则 1：一次只做一件事

每个增量只改变一个逻辑上的内容。不要混合关注点：

**不好：** 一次提交添加一个新组件、重构一个现有组件并更新构建配置。

**好：** 三次独立的提交——每个变更一次。

### 规则 2：保持可编译

每次增量之后，项目必须能够构建，已有测试必须通过。不要在切片之间让代码库处于破损状态。

### 规则 3：为未完成功能使用功能开关

如果某个功能尚未准备好给用户使用，但你需要合并增量：

```typescript
// 进行中工作的功能开关
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新的共享 UI
}
```

这让你可以在不暴露未完成工作的情况下将小增量合并到主分支。

### 规则 4：安全默认值

新代码应默认采用安全、保守的行为：

```typescript
// 安全：默认禁用，选择加入
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：可回滚性

每个增量应该可以独立回退：

- 增量式变更（新文件、新函数）容易回退
- 对现有代码的修改应当最小化且聚焦
- 数据库迁移应有对应的回滚迁移
- 避免在一次提交中删除某个东西并替换它——将其分开

## 与 Agent 协作

在指导 agent 增量实现时：

```
"让我们从计划中实现任务 3。

仅从数据库 schema 变更和 API 端点开始。
先不要动 UI——我们在下一个增量中做。

实现后运行 `npm test` 和 `npm run build` 验证
没有东西被破坏。"
```

对每个增量明确说明哪些在范围内，哪些不在范围内。

## 增量检查清单

每次增量之后，验证：

- [ ] 变更做了一件事，且完整地完成了它
- [ ] 所有已有测试仍然通过 (`npm test`)
- [ ] 构建成功 (`npm run build`)
- [ ] 类型检查通过 (`npx tsc --noEmit`)
- [ ] 代码检查通过 (`npm run lint`)
- [ ] 新功能按预期工作
- [ ] 变更已经以描述性消息提交

**注意：** 在可能影响验证结果的变更后运行每个验证命令。成功运行后，除非代码此后发生变更，否则不要重复同一命令——对未变更的代码重新运行不会增加任何信息。

## 常见合理化借口

| 借口 | 现实 |
|---|---|
| "我最后一起测试" | Bug 会复合增长。切片 1 的 bug 会让切片 2-5 都出错。测试每个切片。 |
| "一次性做完更快" | 感觉更快，直到某些东西出错后你无法从 500 行变更中找出原因。 |
| "这些变更太小了，不值得单独提交" | 小提交是免费的。大提交隐藏 bug，让回滚痛苦。 |
| "功能开关我后面再加" | 如果功能不完整，它不应该对用户可见。现在就加开关。 |
| "这个重构很小，可以顺带做" | 与功能混在一起的重构让两者的评审和调试都更难。分开它们。 |
| "我再跑一次构建命令确认一下" | 成功运行后，除非代码此后发生变更，重复同一命令不会增加任何信息。在后续编辑后再运行，而非为了心安而重复。 |

## 危险信号

- 编写超过 100 行代码却未运行测试
- 单个增量中包含多个无关变更
- "让我顺便再加这个"的范围蔓延
- 为了更快而跳过测试/验证步骤
- 增量之间构建或测试处于破损状态
- 大量未提交的变更累积
- 在第三个用例要求之前就构建抽象
- "既然来了"顺手触碰任务范围外的文件
- 为一次性操作创建新工具文件
- 连续两次运行同一个构建/测试命令而没有任何代码变更

## 验证

完成某项任务的所有增量后：

- [ ] 每个增量都已单独测试并提交
- [ ] 完整测试套件通过
- [ ] 构建无错误
- [ ] 功能按规格要求端到端工作
- [ ] 无未提交的变更残留

## 参见

逐增量的验证是本地检查。在声明任务完成前，将项目级的完成定义（Definition of Done）作为最终门禁，这是每个增量无论什么任务都需达到的固定标准。参见 `references/definition-of-done.md`。
