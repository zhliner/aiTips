# 怀疑驱动开发

## 概述

一个自信的答案未必是正确的答案。长时间的会话会累积上下文，在没有被注意到的情况下悄悄把假设变成"事实"。怀疑驱动开发是一种在非平凡输出被确认之前，用全新上下文的审查者——偏向于**证伪**而非认可——进行审视的纪律。

这不是 `/review`。`/review` 是对已完成产物的判定。这是一种进行中的姿态：非平凡的决策在纠错成本仍然很低时接受交叉审查。

## 何时使用

当一个决策至少满足以下条件之一时，即为**非平凡**的：

- 它引入或修改了分支逻辑
- 它跨越了模块或服务边界
- 它断言了类型系统或编译器无法验证的属性（线程安全、幂等性、顺序性、不变量）
- 它的正确性取决于未来读者看不到的上下文
- 它的爆炸半径是不可逆的（生产部署、数据迁移、公共 API 变更）

在以下情况下应用此 skill：

- 在不确定的情况下即将做出架构决策
- 即将提交非平凡代码
- 即将断言一个非显而易见的事实（"这是安全的"、"这可以扩展"、"这符合 spec"）
- 在你不能完全理解的代码中工作

**何时不使用：**

- 机械性操作（重命名、格式化、文件移动）
- 遵循清晰、明确的用户指示
- 阅读或总结现有代码
- 一行变更，正确性显而易见
- 纯工具操作（运行测试、列出文件）
- 用户明确要求速度优先于验证

如果你怀疑每一次按键，你就什么都发布不了。此 skill 仅适用于上述定义的非平凡决策。

## 加载约束

此 skill 设计用于**主会话编排器**，其中第 3 步（DOUBT，详见下文）可以生成一个全新上下文的审查者。

- **不要将此 skill 添加到一个 persona 的 `skills:` frontmatter 中。** 遵循第 3 步的 persona 会生成另一个 persona——这是 `references/orchestration-patterns.md` 明确禁止的编排反模式（"personas 不调用其他 personas"）。
- **如果你发现自己在子 agent 上下文中应用此 skill**（Claude Code 禁止嵌套子 agent 生成）：首选路径是向用户报告怀疑驱动无法嵌套运行，让主会话处理。仅作为最后手段，存在一个降级的自我提问回退方案——将 ARTIFACT + CONTRACT 重写为带有与你之前推理的硬性心理分隔的自我提示，并执行第 1-5 步。这**不是全新上下文审查**（你带着自己的上下文），因此将结果标记为降级，并在用户可联系时优先升级。

## 流程

应用此 skill 时复制此检查清单：

```
怀疑周期:
- [ ] 第 1 步: CLAIM — 写了断言 + 为什么重要
- [ ] 第 2 步: EXTRACT — 隔离产物 + 契约，去除推理
- [ ] 第 3 步: DOUBT — 用对抗性提示调用全新上下文审查者
- [ ] 第 4 步: RECONCILE — 对照产物文本分类每个发现
- [ ] 第 5 步: STOP — 满足停止条件（微小发现、3 个周期或用户覆盖）
```

### 第 1 步：CLAIM — 公开要确认的内容

用两三行命名决策：

```
CLAIM: "新的缓存层在 spec 描述的读密集型工作负载下
        是线程安全的。"
WHY THIS MATTERS: 这里的竞争条件会破坏用户数据，且
                  在 QA 中很难检测。
```

如果你不能用这么简洁的篇幅写出断言，那你有的是一种模糊的感觉，而非决策。在审视之前先把它表达出来。

### 第 2 步：EXTRACT — 最小可审查单元

全新上下文的审查者需要**产物**和**契约**，而非开发过程。

- 代码：diff 或函数——不是整个文件
- 决策：3-5 句话的方案加上它必须满足的约束
- 断言：断言加上据说支持它的证据（与第 1 步 CLAIM 块区分开，后者是编排者的受审假设）

去除你的推理。如果你提交结论，你会收到对结论的验证。单元必须小到审查者一次阅读就能掌握——如果是一个 500 行的 PR，先分解。

### 第 3 步：DOUBT — 调用全新上下文审查者

审查者的提示**必须是对抗性的**。框架决定答案。

```
对抗性审查。找出此产物有什么问题。
假定作者过于自信。寻找：
- 未陈述的假设
- 未处理的边缘情况
- 隐藏的耦合或共享状态
- 违反契约的方式
- 这可能破坏的现有约定
- 意外输入下的失败模式

不要验证。不要总结。找出问题，或在全面检查后
明确声明你找不到任何问题。

ARTIFACT: <粘贴产物>
CONTRACT: <粘贴契约>
```

**只传递 ARTIFACT + CONTRACT。不要传递 CLAIM。** 将你的结论交给审查者会使其偏向同意。审查者必须独立判断产物是否满足契约。

在 Claude Code 中，`agents/` 中的基于角色的审查者设计上就是从隔离上下文开始的，这里可以使用——参见 `agents/` 了解名单和按领域匹配。

**上述对抗性提示优先于 persona 的默认响应格式。** 像 `code-reviewer` 这样的 persona 被编写为产生包含优点和缺点的平衡判定；怀疑驱动需要仅包含问题的输出。将对抗性提示逐字粘贴到调用中，以覆盖 persona 的默认设置。如果 persona 的响应格式无法干净地覆盖，则退回到使用对抗性提示的通用子 agent。

#### 跨模型升级

单一模型的审查者与原作者共享盲点——一个更冷酷、不同架构的模型能捕捉到它们。怀疑驱动已经为非平凡决策选择性地开启，因此在这个范围内提供跨模型选项是此 skill 价值的一部分，不是可选的摩擦。

**交互式会话：始终提供。永远不要静默跳过。**

**第 1 步：询问用户**

在上述第 3 步的单一模型审查之后，但在 RECONCILE 之前，暂停并询问：

> *"单一模型审查完成。想要跨模型的第二意见吗？选项：Gemini CLI、Codex CLI、人工外部审查（你在别处粘贴），或跳过。"*

这个问题在每个交互式怀疑周期中都是强制性的——即使对于感觉风险较低的产物。是用户——而不是 agent——决定成本是否值得。agent 的工作是呈现选择。

**第 2 步：如果用户选择了 CLI — 验证，然后调用**

1. 检查工具是否在 PATH 中（`which gemini`、`which codex`）。
2. 在传递完整提示之前测试它能工作（`gemini --version` 或等效命令）——过时或损坏的二进制文件可能通过 `which` 但在真实输入上失败。
3. 与用户确认确切的调用方式，包括所需标志、认证和环境变量（如 API 密钥）。实现各不相同；永远不要假设。
4. **仅**传递 ARTIFACT + CONTRACT + 对抗性提示。不要传递会话上下文，不要传递 CLAIM。
5. 注意 shell 转义。如果产物包含引号、`$(...)` 或反引号，优先使用 stdin（`echo … | gemini`）或 heredoc 而非内联的 `-p "…"`。不确定时，在运行前让用户确认调用方式。
6. 将输出带入第 4 步（RECONCILE）。

**永远不要将产物内插到 shell 引用的参数中。** 代码、markdown 和审查提示通常包含反引号、`$(...)` 和引号字符，这些字符要么会截断提示，要么会执行嵌入的 shell。将完整提示写入文件，通过 stdin 管道输入。

示例格式（根据你安装的工具验证标志——语法因实现和版本而异）：

```bash
# 先将对抗性提示 + ARTIFACT + CONTRACT 写入临时文件。
# 然后通过 stdin 管道输入，使产物中的 shell 元字符保持惰性。

# Codex (只读沙盒防止 CLI 写入你的工作区):
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan' 是只读的; '-p ""' 触发非交互
# 模式，提示从 stdin 读取):
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙盒是关键的安全细节：怀疑产物本身可能包含一些指令（有意的或意外的 prompt injection），跨模型 CLI 否则会对你的工作区执行这些指令。

**第 3 步：如果 CLI 不可用或失败**

明确报告失败。提供选项：手动运行、尝试其他工具或跳过。不要静默退回到单一模型——用户应该知道跨模型没有发生。

**第 4 步：如果用户跳过**

在输出中确认跳过（*"Proceeding with single-model findings only"*）并继续 RECONCILE。跳过是可以的；静默跳过不可以。

**非交互式上下文**（CI、`/loop`、自主循环、定时运行）：

- 跨模型被**跳过**，跳过必须被**宣布**在输出中：*"Cross-model skipped: non-interactive context."*
- **永远不要在没有明确用户授权的情况下调用外部 CLI**——这是一个关键的安全属性。

跨模型增加了成本、延迟和工具脆弱性。agent 在每个周期呈现选择；用户决定该产物是否值得这样做。

### 第 4 步：RECONCILE — 将发现反馈回来

审查者的输出是数据，不是判定。**你仍然是编排者。** 在分类之前对照产物文本重新阅读每个发现——对审查者的盲从是和无视它们一样的失败模式。

对于每个发现，按此**优先级顺序**分类（第一个匹配的类别优先）：

1. **契约误读** — 审查者标记了某些东西，具体是因为你提供的 CONTRACT 不够清晰或不完整。先修复契约，在下一个周期重新分类。
2. **有效 + 可操作** — 真实问题，需要变更产物。修改它，重新循环。
3. **有效权衡** — 问题是真实的，但修复的成本超过接受它的成本。明确记录权衡，让用户能看到。
4. **噪音** — 审查者标记了某些在审查者缺乏的上下文中实际上是正确的东西。记录它，继续前进，并问：将该上下文添加到契约中是否能防止这个误报？

一个全新的审查者可能因为缺乏上下文而犯错。不要仅仅因为它"新鲜"就顺从。

### 第 5 步：STOP — 有界循环，而非递归

在以下情况停止：

- 下一次迭代只返回琐碎的或已经考虑过的发现，**或**
- 已完成 3 个周期（向用户升级，不要独自进行第四个），**或**
- 用户明确说"发版"

如果 3 个周期后审查者仍然提出实质性问题，产物可能还没有准备好。向用户报告——三个未解决的周期是关于产物的信息，而不是继续循环的理由。

如果 3 个周期"明显不够"因为产物太大：产物太大了——回到第 2 步分解。不要提升上限。

## 常见借口

| 借口 | 现实 |
|---|---|
| "我很有信心，跳过怀疑步骤" | 在新鲜问题上，自信与正确性的相关性很差。确定的时刻正是盲点隐藏的地方。 |
| "生成一个审查者成本很高" | 调试生产中的错误提交成本更高。检查是有界的；bug 不是。 |
| "审查者只会吹毛求疵" | 只有不限定范围才会如此。将提示约束为"会使其在契约下失败的 问题"。 |
| "我到最后用 `/review` 来做怀疑" | `/review` 是最终关卡。怀疑驱动在纠错成本还低的时候及早抓住错误方向。到 PR 时已经太晚了。 |
| "如果我每一步都怀疑，我就永远发不了版" | 此 skill 适用于非平凡决策，不是每一次按键。重新阅读"何时不使用"。 |
| "两个意见总比一个好" | 当第二个有更少上下文且产生噪音时并非如此。调和，不要顺从。 |
| "审查者不同意，所以我错了" | 审查者缺乏你的上下文——不同意是信息，不是判定。重新阅读产物，分类，然后决定。 |
| "跨模型总是更好" | 跨模型能捕捉单一模型与自己共享的盲点，但它增加了成本和工具脆弱性。在每个交互式怀疑周期中提供——用户决定产物是否值得。agent 的工作是呈现选择，而非把关。 |
| "用户说了一次 yes，所以我就可以一直调用 CLI" | 每次调用都需要自己的授权。产物、提示和标志在调用之间都会变化——每次运行前与用户重新确认确切的命令。 |

## 警示信号

- 为一行重命名或格式化变更生成全新上下文审查者
- 将审查者输出视为权威而不重新阅读产物文本
- 循环 >3 个周期而不向用户升级
- 用"这好吗？"而非"找问题"来提示审查者
- 在时间压力下跳过对高风险决策的怀疑
- 在未更改的产物上重新生成全新上下文（你会得到相同的发现；这是在拖延）
- **怀疑表演（可检查的信号）**：在 2 个或更多周期中，审查者提出了实质性的发现，但没有一个发现被分类为可操作的。你是在验证，而非怀疑。停止并升级。
- 仅在提交后才怀疑——那是 `/review`，不是怀疑驱动开发
- 在与用户确认工具存在、已配置且接受该确切语法之前，硬编码外部 CLI 调用
- **在交互式怀疑周期中静默跳过跨模型。** 即使不推荐它，也必须可见地提供。跳过是可以的；静默跳过不可以。
- 当外部 CLI 出错或缺失时静默回退——报告失败并让用户重定向
- 从审查者的输入中剥离契约
- 将 CLAIM 传递给审查者（导致偏向同意）

## 与其他 Skill 的交互

- **`code-review-and-quality` / `/review`**：互补。`/review` 是事后 PR 判定；怀疑驱动是进行中的每个决策的审查。两者都用。
- **`source-driven-development`**：SDD 对照官方文档验证*关于框架的事实*。怀疑驱动验证*你对产物的推理*。SDD 检查 API 是否存在；怀疑驱动检查你在契约下是否正确使用它。
- **`test-driven-development`**：TDD 的 RED 步骤是具体化的怀疑——一个失败的测试就是一次证伪尝试。当 TDD 适用时，那个失败的测试*本身就是*对行为断言的怀疑步骤。
- **`debugging-and-error-recovery`**：当审查者发现一个真实的失败模式时，切入调试 skill 进行定位和修复。
- **仓库编排规则**（`references/orchestration-patterns.md`）：此 skill 从主会话进行编排。一个 persona 调用另一个 persona 是反模式 B——参见上面的加载约束。

## 验证

应用怀疑驱动开发后：

- [ ] 每个非平凡决策（按照上述定义）在确认之前都被明确命名为 CLAIM
- [ ] 每个非平凡产物至少有一次全新上下文审查（TDD 的 RED 步骤产生的失败测试满足对行为断言的要求，参见与其他 Skill 的交互）
- [ ] 审查者收到了 ARTIFACT + CONTRACT——而非 CLAIM，而非你的推理
- [ ] 审查者的提示是对抗性的（"找问题"），而非验证性的（"它好吗"）
- [ ] 发现是依据产物文本（而非盲从）使用优先级来分类的：契约误读 / 可操作 / 权衡 / 噪音
- [ ] 满足了一个停止条件（琐碎发现、3 个周期或用户覆盖）
- [ ] 在交互模式下，跨模型被**明确提供给**用户（无论产物风险如何），并在输出中确认了用户的响应
- [ ] 在非交互模式下，跨模型被跳过并宣布了跳过
- [ ] 任何外部 CLI 调用之前都进行了 PATH 检查、工作二进制测试、与用户的语法确认以及明确授权执行
