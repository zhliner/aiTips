# Doubt-Driven Development（怀疑驱动开发）

## 概述

自信的答案不一定是正确的答案。长时间的会话会积累上下文，悄悄地将假设变成"事实"，而没有人注意到。怀疑驱动开发是一种纪律——在任何非平凡的输出生效之前，引入一个全新上下文的审查者——倾向于**证伪**，而非批准。

这不是 `/review`。`/review` 是对已完成产物的最终裁决。这是一种进行中的姿态：非平凡的决策在纠正代价还很低的时候就被交叉审查。

## 使用时机

当以下至少一个条件成立时，该决策是**非平凡的**：

- 引入或修改了分支逻辑
- 跨越了模块或服务边界
- 断言了类型系统或编译器无法验证的属性（线程安全、幂等性、顺序、不变量）
- 其正确性依赖于未来读者无法看到的上下文
- 其影响范围是不可逆的（生产部署、数据迁移、公共 API 变更）

在以下情况下应用此技能：

- 即将在不确定情况下做出架构决策
- 即将提交非平凡代码
- 即将声称一个非显而易见的事实（"这是安全的"、"这是可扩展的"、"这符合规范"）
- 在你不完全理解的代码中工作

**不应使用的情况：**

- 机械性操作（重命名、格式化、文件移动）
- 遵循明确、无歧义的用户指令
- 阅读或总结现有代码
- 正确性显而易见的一行修改
- 纯工具操作（运行测试、列出文件）
- 用户明确要求速度优先于验证

如果你对每一次按键都怀疑，你将什么都无法交付。此技能仅适用于上述定义的非平凡决策。

## 加载约束

此技能是为**主会话编排者**设计的，其中 Step 3（DOUBT，详见下文）可以生成一个全新上下文的审查者。

- **不要将此技能添加到 persona 的 `skills:` frontmatter 中。** 遵循 Step 3 的 persona 会生成另一个 persona——这是 `references/orchestration-patterns.md` 中明确禁止的编排反模式（"personas do not invoke other personas"）。
- **如果你发现自己在 subagent 上下文中应用此技能**（Claude Code 阻止嵌套 subagent 生成）：首选做法是向用户说明 doubt-driven 无法嵌套运行，并让主会话处理。仅在万不得已时，可以使用降级的自我质疑回退——将 ARTIFACT + CONTRACT 重写为一个新的自我提示，与之前的推理进行严格的心理隔离，然后执行 Step 1–5。这**不是全新上下文审查**（你带着自己的上下文），因此要将结果标记为降级，并在用户可达时优先选择上报。

## 流程

应用此技能时复制此检查清单：

```
Doubt cycle:
- [ ] Step 1: CLAIM — 写出声明及其重要性
- [ ] Step 2: EXTRACT — 隔离产物和契约，剥离推理过程
- [ ] Step 3: DOUBT — 使用对抗性提示调用全新上下文审查者
- [ ] Step 4: RECONCILE — 根据产物文本对每个发现进行分类
- [ ] Step 5: STOP — 满足停止条件（平凡发现、3 个周期或用户覆盖）
```

### Step 1: CLAIM — 明确待审查的内容

用两到三行描述该决策：

```
CLAIM: "新的缓存层在规范中描述的读密集型负载下是线程安全的。"
WHY THIS MATTERS: 此处的竞态条件会破坏用户数据，
                  且在 QA 中难以检测。
```

如果你无法如此简洁地写出声明，说明你只有直觉而非决策。在审查之前先把它明确表达出来。

### Step 2: EXTRACT — 最小可审查单元

全新上下文审查者需要的是**产物**和**契约**，而不是你的推理过程。

- 代码：diff 或函数——不是整个文件
- 决策：3–5 句话的提案加上它必须满足的约束
- 断言：声明加上据称支持它的证据（与 Step 1 的 CLAIM 块分开保留，后者是编排者正在审查的假设）

剥离你的推理过程。如果你把结论交给审查者，你得到的只会是对结论的认可。审查单元必须足够小，让审查者一次阅读就能在脑中完整把握——如果是 500 行的 PR，先进行分解。

### Step 3: DOUBT — 调用全新上下文审查者

审查者的提示**必须是对抗性的**。提问方式决定了回答。

```
对抗性审查。找出这个产物中的问题。
假设作者过于自信。寻找：
- 未声明的假设
- 未处理的边界情况
- 隐藏的耦合或共享状态
- 契约可能被违反的方式
- 可能破坏的现有约定
- 意外输入下的失败模式

不要验证。不要总结。找出问题，或者在彻底检查后
明确声明你无法找到任何问题。

ARTIFACT: <粘贴产物>
CONTRACT: <粘贴契约>
```

**只传递 ARTIFACT + CONTRACT。不要传递 CLAIM。** 把你的结论交给审查者会使其偏向认同。审查者必须独立判断产物是否满足契约。

在 Claude Code 中，`agents/` 中基于角色的审查者默认以隔离上下文启动，可在此处使用——参见 `agents/` 获取完整列表和领域匹配。

**上述对抗性提示优先于 persona 的默认响应格式。** 像 `code-reviewer` 这样的 persona 被设计为产出包含优缺点的平衡裁决；怀疑驱动需要的是仅列出问题的输出。将对抗性提示逐字粘贴到调用中，以覆盖 persona 的默认行为。如果 persona 的响应格式无法干净地覆盖，回退到使用对抗性提示的通用 subagent。

#### 跨模型升级

单模型审查者与原作者共享盲区——一个更冷静的、不同架构的模型能捕捉到这些盲区。怀疑驱动已经是针对非平凡决策的可选技能，因此在该范围内提供跨模型选项是技能价值的一部分，而非可选的摩擦。

**交互式会话：始终提供选项。绝不静默跳过。**

**Step 1: 询问用户**

在上述 Step 3 的单模型审查完成后，但在 RECONCILE 之前，暂停并询问：

> *"单模型审查已完成。需要跨模型的第二意见吗？选项：Gemini CLI、Codex CLI、手动外部审查（你在其他地方粘贴），或跳过。"*

此问题在每个交互式怀疑周期中都是强制性的——即使在感觉低风险的产物上也是如此。由用户——而非 agent——来决定成本是否值得。Agent 的职责是呈现选择。

**Step 2: 如果用户选择了 CLI——验证后调用**

1. 检查工具是否在 PATH 中（`which gemini`、`which codex`）。
2. 在传递完整提示之前测试其是否正常工作（`gemini --version` 或等效命令）——过期或损坏的二进制文件可能通过 `which` 但在实际输入时失败。
3. 与用户确认确切的调用命令，包括必需的标志、认证和环境变量（例如 API 密钥）。实现方式各异；切勿假设。
4. 只传递 ARTIFACT + CONTRACT + 对抗性提示。不传递会话上下文，不传递 CLAIM。
5. 注意 shell 转义。如果产物包含引号、`$(...)` 或反引号，优先使用 stdin（`echo … | gemini`）或 heredoc 而非内联 `-p "…"`。如有疑问，在运行前请用户确认调用命令。
6. 将输出传入 Step 4（RECONCILE）。

**绝不将产物插入 shell 引号参数中。** 代码、markdown 和审查提示通常包含反引号、`$(...)` 和引号字符，这些会截断提示或执行嵌入的 shell 命令。将完整提示写入文件并通过 stdin 传入。

示例格式（根据你安装的工具验证标志——语法因实现和版本而异）：

```bash
# 先将对抗性提示 + ARTIFACT + CONTRACT 写入临时文件。
# 然后通过 stdin 传入，使产物中的 shell 元字符保持惰性。

# Codex（只读沙箱防止 CLI 写入你的工作区）：
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini（'--approval-mode plan' 是只读的；'-p ""' 触发非交互
# 模式，提示从 stdin 读取）：
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙箱是关键细节：怀疑产物本身可能包含指令（有意或无意的提示注入），跨模型 CLI 否则会在你的工作区上执行这些指令。

**Step 3: 如果 CLI 不可用或失败**

明确告知失败情况。提供选项：手动运行、尝试其他工具或跳过。不要静默回退到单模型——用户应该知道跨模型未执行。

**Step 4: 如果用户跳过**

在输出中确认跳过（*"仅使用单模型发现继续"*），然后继续 RECONCILE。跳过没问题；静默跳过不行。

**非交互式上下文**（CI、`/loop`、自主循环、定时运行）：

- 跨模型**跳过**，且必须在输出中**公告**跳过：*"跨模型已跳过：非交互式上下文。"*
- **绝不在没有用户明确授权的情况下调用外部 CLI**——这是一个关键安全属性。

跨模型会增加成本、延迟和工具脆弱性。Agent 在每个周期呈现选择；用户决定此产物是否值得。

### Step 4: RECONCILE — 将发现整合回来

审查者的输出是数据，不是裁决。**你仍然是编排者。** 在对每个发现分类之前，重新对照产物文本阅读——盲目认可审查者和忽略审查者是同样的失败模式。

对每个发现，按以下**优先级顺序**分类（第一个匹配的类别生效）：

1. **契约误读** — 审查者标记的内容是因为你提供的 CONTRACT 不清晰或不完整。先修复契约，在下一个周期重新分类。
2. **有效 + 可操作** — 需要修改产物的真实问题。修改它，重新循环。
3. **有效的权衡** — 问题是真实的，但修复成本超过接受成本。明确记录权衡，让用户看到。
4. **噪声** — 审查者标记的内容在审查者没有的上下文下实际上是正确的。记录下来，继续，并问：如果将那个上下文添加到契约中，能否避免这个误报？

全新的审查者也可能因为缺少上下文而犯错。不要因为它是"全新的"就盲目遵从。

### Step 5: STOP — 有界循环，而非递归

在以下情况下停止：

- 下一次迭代只返回平凡的或已经考虑过的发现，**或**
- 已完成 3 个周期（上报给用户，不要独自进行第四个周期），**或**
- 用户明确说"发布它"

如果 3 个周期后审查者仍然提出实质性问题，产物可能尚未准备好。将此情况上报给用户——三个未解决的周期是关于产物本身的信息，而非继续循环的理由。

如果 3 个周期"明显不够"是因为产物太大：说明产物太大——回到 Step 2 进行分解。不要提高上限。

## 常见的自我合理化

| 合理化 | 现实 |
|---|---|
| "我很自信，跳过怀疑步骤" | 在新问题上，自信与正确性的相关性很差。确定的时刻恰恰是盲区隐藏的时候。 |
| "生成审查者成本太高" | 在生产环境中调试错误的提交成本更高。检查是有界的；bug 不是。 |
| "审查者只会挑小毛病" | 只有在范围不明确时才会。将提示限定为"会导致在契约下失败的问题"。 |
| "我最后用 `/review` 来怀疑" | `/review` 是最终关卡。怀疑驱动在纠正代价低的时候及早捕捉错误方向。到 PR 阶段已经太迟了。 |
| "如果每一步都怀疑就永远无法交付" | 此技能适用于非平凡决策，不是每一次按键。重读"不应使用的情况"。 |
| "两个意见总比一个好" | 当第二个意见上下文更少且产生噪声时并非如此。整合，而非盲从。 |
| "审查者不同意，所以我错了" | 审查者缺少你的上下文——分歧是信息，不是裁决。重新阅读产物，分类，然后决定。 |
| "跨模型总是更好" | 跨模型能捕捉单模型自身的盲区，但会增加成本和工具脆弱性。在每个交互式怀疑周期提供此选项——用户决定产物是否值得。Agent 的职责是呈现选择，而非替用户决定。 |
| "用户说过一次可以，所以我可以继续调用 CLI" | 每次调用都是独立的授权。产物、提示和标志在调用之间会变化——每次运行前都要与用户重新确认确切命令。 |

## 危险信号

- 为一行重命名或格式化修改生成全新上下文审查者
- 不重新阅读产物文本就将审查者输出视为权威
- 循环超过 3 个周期不上报用户
- 用"这样好吗？"而非"找出问题"来提示审查者
- 在时间压力下对高风险决策跳过怀疑
- 对未更改的产物重新生成全新上下文审查（你会得到相同的发现；你只是在拖延）
- **怀疑表演（可检查信号）**：在 2 个或更多周期中，审查者提出了实质性发现，但零个发现被归类为可操作。你在验证而非怀疑。停下来并上报。
- 提交后才怀疑——那是 `/review`，不是怀疑驱动开发
- 硬编码外部 CLI 调用而不与用户确认工具存在、已配置且接受该确切语法
- **在交互式怀疑周期中静默跳过跨模型。** 即使不推荐，也必须让选项可见。跳过没问题；静默跳过不行。
- 当外部 CLI 出错或缺失时静默回退——告知失败情况并让用户重新定向
- 从审查者的输入中剥离契约
- 将 CLAIM 传递给审查者（会偏向认同）

## 与其他技能的交互

- **`code-review-and-quality` / `/review`**：互补。`/review` 是事后的 PR 裁决；怀疑驱动是进行中的逐决策审查。两者都用。
- **`source-driven-development`**：SDD 根据官方文档验证*关于框架的事实*。怀疑驱动验证*你对产物的推理*。SDD 检查 API 是否存在；怀疑驱动检查你在契约下是否正确使用了它。
- **`test-driven-development`**：TDD 的 RED 步骤是具体化的怀疑——一个失败的测试就是一次证伪尝试。当 TDD 适用时，那个失败的测试*就是*行为声明的怀疑步骤。
- **`debugging-and-error-recovery`**：当审查者提出真实的失败模式时，进入调试技能进行定位和修复。
- **仓库编排规则**（`references/orchestration-patterns.md`）：此技能从主会话进行编排。一个 persona 调用另一个 persona 是反模式 B——参见上方加载约束。

## 验证

应用怀疑驱动开发后：

- [ ] 每个非平凡决策（按上述定义）在生效前都被明确命名为 CLAIM
- [ ] 每个非平凡产物至少经过一次全新上下文审查（TDD 的 RED 步骤产生的失败测试对行为声明满足此要求，参见与其他技能的交互）
- [ ] 审查者收到的是 ARTIFACT + CONTRACT——不是 CLAIM，不是你的推理过程
- [ ] 审查者的提示是对抗性的（"找出问题"），而非验证性的（"这样好吗"）
- [ ] 发现根据产物文本进行了分类（而非盲目认可），使用优先级：契约误读 / 可操作 / 权衡 / 噪声
- [ ] 满足停止条件（平凡发现、3 个周期或用户覆盖）
- [ ] 在交互模式下，跨模型已**明确提供**给用户（无论产物风险等级），且响应已在输出中确认
- [ ] 在非交互模式下，跨模型已跳过且跳过已公告
- [ ] 任何外部 CLI 调用之前都进行了 PATH 检查、可用二进制测试、与用户的语法确认以及明确的运行授权
