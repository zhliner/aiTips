# 访谈我

## 概述

人们要求的东西和他们真正想要的东西是不同的。他们要一个"仪表盘"因为那是人们通常要的东西，而不是因为仪表盘能解决他们的问题。他们说"让它更快"却没有一个要达到的具体数字。

发现这个差距最便宜的时刻是在任何计划、spec 或代码存在之前。一旦你开始构建，切换成本是真实存在的，用户会把错误的东西合理化为"够好"的东西。错配被锁定了。

此 skill 在它造成任何成本之前弥合这个差距。其他定义阶段的 skill 假设你已经大致知道自己想要什么：`idea-refine` 从点子生成变体，`spec-driven-development` 把需求写下来，`doubt-driven-development` 在你起草计划后对它进行压力测试。Interview-me 是在所有这些之前的那个部分，你一次问一个问题，附带你的最佳猜测，直到你能在用户说出来之前预测他们将要说什么。

## 何时使用

在以下情况应用此 skill：

- 需求至少缺少以下之一：**谁**是用户、**为什么**他们想要它、什么算作**成功**、约束性**限制**是什么
- 请求是常规性的而非具体的（"给我建个 X"、"让它更快"），你在不猜测的情况下无法解构这个常规
- 你被诱惑从你没有公开的假设开始
- 用户没有说他们在两个合理的价值之间优化哪一个，这两个价值在张力中（简单 vs. 灵活、成本 vs. 速度）
- 用户明确调用："interview me"、"grill me"、"在我们开始之前，我们确定吗？"、"stress-test my thinking"

**何时不使用：**

- 需求明确且自包含（"重命名这个变量"、"修复这个拼写错误"）
- 用户明确要求速度优先于验证
- 纯信息请求（"X 是如何工作的？"、"这段代码做什么？"）
- 机械性操作（重命名、格式化、文件移动）
- 你已经达到 ≥95% 的置信度；在假设你没有之前重新阅读下面的停止条件

## 加载约束

此 skill 需要一个实时的、有响应的用户。**不要在非交互式上下文中调用**，如 CI 管道、定时运行、`/loop` 或自主循环。如果你在这些场景中且需求规格不足，将其标记为用户需要面对的阻塞项，而不是猜测。

## 流程

### 第 1 步：假设，附带置信度数字

在问任何问题之前，用**一句话**写下你目前对用户想要什么的最佳解读，加上一个诚实的置信度数字（0-100%）：

```
HYPOTHESIS（假设）: 你想要一种在站会上回答"我们进展如何？"的方式，而"仪表盘"是你脑海中浮现的常规答案。
CONFIDENCE（置信度）: ~30% — 缺失：为谁、上下文中的"指标"是什么意思、以及成功是什么样子
```

这个数字强迫诚实。如果你写下了一个高数字但你不能真正预测用户对你接下来三个问题的反应，这个数字就是错的。从你能辩护的置信度水平开始。

当置信度低于约 70% 时，在同一行附上简要原因——还有什么未解决或缺失。这告诉用户访谈需要揭示什么，并防止数字成为一个模糊的信号。

### 第 2 步：一次一个问题，每个附带一个猜测

格式：

```
Q（问题）: <一个聚焦的问题>
GUESS（猜测）: <你对答案的假设，附带导致它的推理>
```

等待用户反应后再问下一个问题。

**为什么一次一个，而不是一批：**

- 如果你把它们埋在一个列表里，用户无法对你的假设做出反应
- 批次鼓励略读和表面回答
- 第三个问题常常取决于第一个问题的答案；一次性全部问完会锁定错误的框架
- 用户仔细思考的精力是有限的；一次一个问题地消耗它

**为什么附带一个猜测：**

- 用户对一个错误猜测的反应比他们从零生成答案更快
- 它将你承诺于一个你可以明显犯错的假设，这让你保持诚实
- 它暴露*你*的假设，这正是访谈旨在揭示的

这里的风险是一个有礼貌的用户同意你的猜测以示配合。通过明显愿意犯错来缓解，偶尔朝你预期用户会反驳的方向猜测。

### 第 3 步：听取"想要 vs. 应该想要"

最危险的答案是用户说出了一个深思熟虑的答案*听起来的样子*而非他们真正想要的。警惕：

- 匹配最佳实践话术模式的答案（"我想要它是可扩展的"、"干净的架构"）但没有具体细节
- 屈从于常规的答案（"大多数应用的方式"、"标准方法"）
- 像"我应该大概……"、"我觉得我应该……"、"良好工程实践说……"这样的短语
- 作为目标的流行词——当"现代化"、"可扩展"、"健壮"是答案而非具体结果时

当你听到这些时，要问的问题是：

> *"如果你不需要向任何人解释这件事，你真正想要的是什么？"*

这一个问题常常比前面五个问题更有用。

### 第 4 步：用用户自己的话重述意图

当你的置信度很高时，把你现在认为用户想要的东西写回来。保持紧凑（5-8 行），可能的话使用他们的语言，并结构化它以便用户能逐行确认或修正：

```
这是我目前认为你想要的东西：

- 结果:          <一行>
- 用户:          <一行 — 谁受益>
- 为什么现在:    <一行 — 什么变了>
- 成功:          <一行 — 我们怎么知道它成功了>
- 约束:          <一行 — 约束性限制>
- 不在范围内:    <一行 — 我们明确不做的事>

Yes / no / refine?
```

包含"不在范围内"是不容商量的。一半的错位是默默不同意*不*建什么。

### 第 5 步：确认——明确的 yes，而不是"你觉得怎样都行"

关口是明确的"yes"。以下**不是** yes：

- "你觉得怎样都行。" → 用户是在委托，这意味着他们也没有 95% 的置信度。以两个具体选项作为选择重新询问。
- "听起来不错。" → 模糊的。问："有什么你想调整的吗？"沉默不是确认。
- "好的，开始吧。" → 常常是一个礼貌的退出，而非认可。同样的跟进问题。
- 沉默后跟着"好，我们开始吧。" → 用户放弃了访谈，而非达成一致。停下来问你是否漏掉了什么。

如果他们纠正你，将纠正内容纳入并重新表述。循环直到你得到明确的 yes。

### 95% 置信度停止线

当你能对这个问题回答 yes 时，你就完成了：

> *我能预测用户对我接下来要问的三个问题的反应吗？*

如果能，你们有共同的理解。停止访谈并产出重述。如果不能，你还没完成；问下一个问题。

这是一个可检查的测试，而非一种感觉。它也有一个底线：如果你已经进行了好几轮仍无法预测，这是关于需求的信息，而不是继续较劲的理由。停下来告诉用户："我已经问了 X 个问题，但仍然不能预测你的反应。有一些基础性的东西缺失了。想退一步看看吗？"

## 输出

此 skill 的输出是一个**已确认的意图声明**：第 4 步的重述，加上第 5 步的明确 yes。这就是交付物。Spec、计划和任务列表都是下游产物；它们消费此 skill 产生的意图。

如果用户希望意图持久化（一个跨会话的项目、移交给另一个协作者），提供将其保存到 `docs/intent/[topic].md` 的选择。仅在他们确认后再保存。

## 示例

一个简短的前后对比。

**不使用 `interview-me`：**

```
用户:  给我做一个指标仪表盘
Agent: <开始建议图表库和布局>
```

Agent 已经假设了：为谁、什么指标、"为我们团队"是什么意思、成功是什么样子。这些都没有被陈述。每个假设都是用户以后可能说"那不是我想要的"的地方。

**使用 `interview-me`：**

```
用户: 给我做一个指标仪表盘

Agent:
HYPOTHESIS（假设）: 你想要一种在站会上回答"我们进展如何？"的方式，而"仪表盘"因为那是常规答案而浮现在脑中。
CONFIDENCE（置信度）: ~30% — 缺失：为谁、什么"指标"、以及成功是什么样子

Q（问题）: 当你说"我们进展如何？"时，谁在问——你自己、工程团队在站会上、还是向上汇报（如你的经理、高管、董事会）？
GUESS（猜测）: 工程团队在站会上，因为"我们"通常这样范围化，而站会正是这个问题被问的地方。如果是面向高管，指标和框架会变化很大。

用户: 实际上是给我自己用的。我老是不记得哪些实验在运行以及它们的早期信号长什么样。

Agent:
Updated read（更新解读）: 完全不是一个团队仪表盘。它是一个个人实验跟踪器。Confidence: ~60% — 缺失："早期信号"意味着什么，以及完成长什么样。

Q（问题）: 问题是不知道有哪些实验存在，还是无法在一个地方看到它们的结果？
GUESS（猜测）: 第二个。你某处有一个实验列表，但它们的结果分布在五个不同的工具中，手工汇总它们让你感到疲倦。

用户: 实际上是第一个。我真的没有列表。它们分散在不同的文档里。

Agent: <继续>
```

两个问题下来，agent 发现真正的需求不是"一个仪表盘"。而是"一个列表"。不同的产物，不同的范围，不同的工作量。仪表盘会是错的。

## 与其他 Skill 的交互

- **`idea-refine`**：下游。如果确认的意图是"我想要 X 但我不知道如何范围化它"，移交给 `idea-refine` 以对现在明确的意图生成变体。
- **`spec-driven-development`**：下游。如果确认的意图是具体的（"我想要 X 为 Y 用户以 Z 成功标准"），移交给 `spec-driven-development` 写下来。
- **`planning-and-task-breakdown`**：此 skill 下游两跳（spec 之后）。
- **`doubt-driven-development`**：时间线的另一端。Interview-me 是决策前意图提取；怀疑驱动是决策后产物审查。两者都捕捉偏差，但在不同时刻。
- **`source-driven-development`**：正交。Interview-me 澄清用户想要什么；SDD 验证框架事实。它们不竞争。

## 常见借口

| 借口 | 现实 |
|---|---|
| "需求够清楚了" | 如果你现在不能用一句话写出用户期望的结果，需求就不清楚。在决定之前运行第 1 步。 |
| "问太多问题会浪费他们的时间" | 4-6 个有针对性的问题浪费的时间是小的。构建错误的东西浪费的时间是巨大的，且承担这个成本的是用户。 |
| "我会一边构建一边弄清楚" | 代码存在后的切换成本是现在的 10 倍。实现过程中的发现就是返工。 |
| "他们说了'随便你觉得怎样'，所以我就该自行决定" | "随便你觉得怎样"是委托，不是决策。以两个具体选项作为选择重新询问。 |
| "我应该给他们几个选项来选择" | 当用户知道他们想要什么并在权衡之间选择时，选项是有效的。他们还不知道自己 想要什么。列出选项是扩大搜索；提问是缩小搜索。 |
| "如果我附带我的猜测，我是在引导他们" | 引导正是关键。反应比从零生成更快。风险是谄媚，而非引导；通过明显愿意犯错来缓解。 |
| "我们谈得够多了，我懂了" | 测试一下：你能预测他们对接下来三个问题的反应吗？如果不能，你还没懂。 |
| "用户说了 yes，我们完成了" | 如果 yes 跟随的是一个模糊的重述或一个开放式的"听起来不错"，这个 yes 是空洞的。具体重述并重新确认。 |

## 警示信号

- 一条消息中三个或更多问题：那是批处理，不是访谈
- 一个没有附带假设的问题：那是在调查，不是在承诺
- 接受"你觉得怎样都行"作为最终答案
- 在用户明确确认重述之前产出 spec、计划或任务列表
- 问题框架为"最佳实践是什么？"而非"你真正想要什么？"
- 用户给出了一个复杂性炫耀的答案（"可扩展"、"干净"、"现代"），你未探究是否是他们真正想要的就接受了
- 三轮或更多轮次后你的置信度没有明显上升：你问错了问题，退后并重新框架
- 置信度数字低于约 70% 但没有附带原因：如果用户不知道缺失了什么，他们无法帮助弥合差距
- 在用户确认之前保存意图文档（文档本身暗示了一个用户没给的 yes）
- 在重述中跳过"不在范围内"这一行（对非目标的默默不同意是一半错位的来源）

## 验证

应用 interview-me 后：

- [ ] 在第一轮中声明了带有置信度数字的明确假设
- [ ] 每个低于约 70% 的置信度数字附带了单行原因（什么仍未解决或缺失）
- [ ] 问题一次一个，每个附带了 agent 的猜测
- [ ] 当用户给出了一个复杂性炫耀或常规性炫耀的答案时，至少运行了一次"如果你不需要解释，你真正想要什么？"的探究
- [ ] 一个具体的重述（结果 / 用户 / 为什么现在 / 成功 / 约束 / 不在范围内）被写回给用户
- [ ] 用户以明确的 yes 确认了重述（不是"你觉得怎样都行"，不是"听起来不错"，不是沉默）
- [ ] 在停止点，agent 能预测它对接下来三个问题的反应
- [ ] 任何移交给下游 skill（`idea-refine`、`spec-driven-development`）都被框定在确认的意图范围内，而非原来的规格不足的需求
