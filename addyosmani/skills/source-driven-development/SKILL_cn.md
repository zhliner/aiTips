# 源码驱动开发

## 概述

每个框架相关的代码决策都必须有官方文档支持。不要凭记忆实现——验证、引用，并让用户看到你的来源。训练数据会过时，API 会被弃用，最佳实践会进化。此 skill 确保用户获得他们可以信任的代码，因为每个模式都可以追溯到他们可以验证的权威来源。

## 何时使用

- 用户需要遵循给定框架当前最佳实践的代码时
- 构建样板代码、起始代码或将在整个项目中复制的模式时
- 用户明确要求经过文档验证的或"正确"的实现时
- 实现框架推荐方法很重要的功能时（表单、路由、数据获取、状态管理、认证）
- 审查或改进使用框架特定模式的代码时
- 任何时候你要凭记忆编写框架特定代码时

**何时不使用：**

- 正确性不依赖于特定版本（重命名变量、修复拼写错误、移动文件）
- 纯逻辑，在所有版本中工作方式相同（循环、条件、数据结构）
- 用户明确要求速度优先于验证（"快速搞定就行"）

## 流程

```
DETECT（检测）──→ FETCH（获取）──→ IMPLEMENT（实现）──→ CITE（引用）
   │               │                   │                    │
   ▼               ▼                   ▼                    ▼
  用什么        获取相关            遵循               展示你的
  技术栈？      官方文档            文档化的            来源
                                    模式
```

### 第 1 步：检测技术栈和版本

读取项目的依赖文件以识别确切版本：

```
package.json    → Node/React/Vue/Angular/Svelte
composer.json   → PHP/Symfony/Laravel
requirements.txt / pyproject.toml → Python/Django/Flask
go.mod          → Go
Cargo.toml      → Rust
Gemfile         → Ruby/Rails
```

明确声明你找到的内容：

```
STACK DETECTED:
- React 19.1.0 (来自 package.json)
- Vite 6.2.0
- Tailwind CSS 4.0.3
→ 正在获取相关模式的官方文档。
```

如果版本缺失或不明确，**询问用户**。不要猜测——版本决定了哪些模式是正确的。

### 第 2 步：获取官方文档

获取你正在实现的功能相关的具体文档页面。不是主页，不是完整文档——是相关页面。

**来源层级（按权威性排序）：**

| 优先级 | 来源 | 示例 |
|----------|--------|---------|
| 1 | 官方文档 | react.dev, docs.djangoproject.com, symfony.com/doc |
| 2 | 官方博客 / changelog | react.dev/blog, nextjs.org/blog |
| 3 | Web 标准参考 | MDN, web.dev, html.spec.whatwg.org |
| 4 | 浏览器/运行时兼容性 | caniuse.com, node.green |

**非权威来源——永远不要作为主要来源引用：**

- Stack Overflow 答案
- 博客文章或教程（即使是热门的）
- AI 生成的文档或摘要
- 你自己的训练数据（这正是关键——要验证它）

**精确获取你想要的内容：**

```
BAD:  获取 React 主页
GOOD: 获取 react.dev/reference/react/useActionState

BAD:  搜索 "django 认证最佳实践"
GOOD: 获取 docs.djangoproject.com/en/6.0/topics/auth/
```

获取后，提取关键模式并注意任何弃用警告或迁移指导。

当官方来源相互矛盾时（例如迁移指南与 API 参考不一致），将矛盾向用户报告，并根据检测到的版本验证哪个模式实际可用。

### 第 3 步：遵循文档化模式实现

编写与文档展示相匹配的代码：

- 使用文档中的 API 签名，而非记忆中的
- 如果文档展示了做某件事的新方式，使用新方式
- 如果文档弃用了某个模式，不要使用已弃用的版本
- 如果文档没有涵盖某些内容，将其标记为未验证

**当文档与现有项目代码冲突时：**

```
CONFLICT DETECTED:
现有代码库使用 useState 处理表单加载状态，
但 React 19 文档推荐使用 useActionState 处理此模式。
(来源: react.dev/reference/react/useActionState)

选项:
A) 使用现代模式 (useActionState) — 与当前文档一致
B) 匹配现有代码 (useState) — 与代码库一致
→ 你偏好哪种方式？
```

报告冲突。不要默默选择其中之一。

### 第 4 步：引用你的来源

每个框架特定的模式都要有引用。用户必须能够验证每个决策。

**在代码注释中：**

```typescript
// React 19 使用 useActionState 处理表单
// 来源: https://react.dev/reference/react/useActionState#usage
const [state, formAction, isPending] = useActionState(submitOrder, initialState);
```

**在对话中：**

```
我用 useActionState 替代了手动的 useState 来管理
表单提交状态。React 19 用这个 hook 替换了手动的
isPending/setIsPending 模式。

来源: https://react.dev/blog/2024/12/05/react-19#actions
"useTransition now supports async functions [...] to handle
pending states automatically"
```

**引用规则：**

- 完整 URL，不缩短
- 在可能的情况下优先使用带锚点的深层链接（如 `/useActionState#usage` 而非 `/useActionState`）——锚点在文档重构后比顶层页面更耐用
- 当引用的段落支持一个非显而易见的决策时，引用相关段落
- 在推荐平台功能时包含浏览器/运行时支持数据
- 如果找不到某个模式的文档，明确声明：

```
UNVERIFIED: 我未能找到此模式的官方文档。
这基于训练数据，可能已过时。
在生产环境中使用前请验证。
```

诚实承认你无法验证的内容，比虚假的自信更有价值。

## 常见借口

| 借口 | 现实 |
|---|---|
| "我对这个 API 很有把握" | 自信不是证据。训练数据包含看起来正确但在当前版本下会出错的过时模式。验证。 |
| "获取文档浪费 token" | 幻觉出一个 API 浪费更多。用户调试一小时，然后发现函数签名变了。一次获取可避免数小时的返工。 |
| "文档不一定有我需要的内容" | 如果文档没有涵盖，这就是有价值的信息——该模式可能不是官方推荐的。 |
| "我就提一下可能过时了" | 免责声明没用。要么验证并引用，要么明确标记为未验证。含糊其辞是最差的选择。 |
| "这是个简单任务，不需要检查" | 简单任务中的错误模式会成为模板。用户将你已弃用的表单处理程序复制到十个组件中，然后才发现存在现代方法。 |

## 警示信号

- 未检查该版本的文档就编写框架特定代码
- 使用"我相信"或"我认为"来谈论 API 而不是引用来源
- 在不知道适用于哪个版本的情况下实现某个模式
- 引用 Stack Overflow 或博客文章而非官方文档
- 因为训练数据中出现而使用已弃用的 API
- 在实现之前没有阅读 `package.json` / 依赖文件
- 交付没有框架特定决策来源引用的代码
- 在只有一个页面相关时获取整个文档网站

## 验证

使用源码驱动开发实现后：

- [ ] 框架和库的版本已从依赖文件中识别
- [ ] 已获取框架特定模式的官方文档
- [ ] 所有来源均为官方文档，非博客文章或训练数据
- [ ] 代码遵循当前版本文档中展示的模式
- [ ] 非平凡决策包含带完整 URL 的来源引用
- [ ] 没有使用已弃用的 API（已对照迁移指南检查）
- [ ] 文档与现有代码之间的冲突已向用户报告
- [ ] 任何无法验证的内容已明确标记为未验证
