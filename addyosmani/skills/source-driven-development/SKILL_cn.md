# 源驱动开发（Source-Driven Development）

## 概述

每个框架相关的代码决策都必须有官方文档支撑。不要凭记忆实现——要验证、引用，并让用户看到你的来源。训练数据会过时，API 会被弃用，最佳实践会演变。这个技能确保用户获得他们可以信赖的代码，因为每个模式都可以追溯到一个他们可以核实的权威来源。

## 使用场景

- 用户希望代码遵循某个框架的当前最佳实践
- 构建样板代码、起始代码或将在项目中被复制的模式
- 用户明确要求有文档记录的、经过验证的或"正确"的实现
- 实现框架推荐方式很重要的功能（表单、路由、数据获取、状态管理、认证）
- 审查或改进使用框架特定模式的代码
- 任何时候你准备凭记忆编写框架特定的代码

**不适用的场景：**

- 正确性不依赖于特定版本（重命名变量、修复拼写错误、移动文件）
- 在所有版本中行为一致的纯逻辑（循环、条件判断、数据结构）
- 用户明确要求速度优先于验证（"直接快速完成"）

## 流程

```
检测 ──→ 获取 ──→ 实现 ──→ 引用
 │        │        │        │
 ▼        ▼        ▼        ▼
什么      获取      遵循      展示
技术栈？  相关      有文档    你的
          文档      记录的模式  来源
```

### 第 1 步：检测技术栈和版本

读取项目的依赖文件以识别确切版本：

```
package.json    → Node/React/Vue/Angular/Svelte
composer.json   → PHP/Symfony/Laravel
requirements.txt / pyproject.toml → Python/Django/Flask
go.mod          → Go
Cargo.toml      → Rust
Gemfile         → Ruby/Rails
```

明确陈述你发现的内容：

```
检测到的技术栈：
- React 19.1.0（来自 package.json）
- Vite 6.2.0
- Tailwind CSS 4.0.3
→ 正在获取相关模式的官方文档。
```

如果版本缺失或不确定，**询问用户**。不要猜测——版本决定了哪些模式是正确的。

### 第 2 步：获取官方文档

获取你正在实现的功能的具体文档页面。不是首页，不是完整文档——而是相关页面。

**来源层级（按权威性排序）：**

| 优先级 | 来源 | 示例 |
|--------|------|------|
| 1 | 官方文档 | react.dev, docs.djangoproject.com, symfony.com/doc |
| 2 | 官方博客 / 变更日志 | react.dev/blog, nextjs.org/blog |
| 3 | Web 标准参考 | MDN, web.dev, html.spec.whatwg.org |
| 4 | 浏览器/运行时兼容性 | caniuse.com, node.green |

**不具备权威性——永远不要作为主要来源引用：**

- Stack Overflow 回答
- 博客文章或教程（即使是热门的）
- AI 生成的文档或摘要
- 你自己的训练数据（这正是重点——需要验证）

**精确获取你需要的内容：**

```
错误：获取 React 首页
正确：获取 react.dev/reference/react/useActionState

错误：搜索 "django authentication best practices"
正确：获取 docs.djangoproject.com/en/6.0/topics/auth/
```

获取后，提取关键模式并注意任何弃用警告或迁移指南。

当官方来源之间相互冲突时（例如迁移指南与 API 参考矛盾），向用户说明差异，并针对检测到的版本验证哪个模式实际可用。

### 第 3 步：按照文档记录的模式实现

编写与文档展示一致的代码：

- 使用文档中的 API 签名，而非凭记忆
- 如果文档展示了新的做法，使用新方式
- 如果文档弃用了某个模式，不要使用已弃用的版本
- 如果文档未涵盖某些内容，将其标记为未经验证

**当文档与现有项目代码冲突时：**

```
检测到冲突：
现有代码库使用 useState 处理表单加载状态，
但 React 19 文档推荐对此模式使用 useActionState。
（来源：react.dev/reference/react/useActionState）

选项：
A) 使用现代模式（useActionState）——与当前文档一致
B) 匹配现有代码（useState）——与代码库一致
→ 你更倾向于哪种方式？
```

暴露冲突。不要默默选择一个。

### 第 4 步：引用你的来源

每个框架特定的模式都需要引用。用户必须能够验证每个决策。

**在代码注释中：**

```typescript
// React 19 使用 useActionState 处理表单
// 来源：https://react.dev/reference/react/useActionState#usage
const [state, formAction, isPending] = useActionState(submitOrder, initialState);
```

**在对话中：**

```
我使用 useActionState 而非手动 useState 来处理
表单提交状态。React 19 用这个 hook 取代了手动
isPending/setIsPending 模式。

来源：https://react.dev/blog/2024/12/05/react-19#actions
"useTransition now supports async functions [...] to handle
pending states automatically"
```

**引用规则：**

- 完整 URL，不要缩短
- 尽量使用带锚点的深层链接（例如 `/useActionState#usage` 而非 `/useActionState`）——锚点比顶层页面更能抵御文档重构
- 当相关段落支持一个非显而易见的决策时，引用该段落
- 推荐平台特性时包含浏览器/运行时支持数据
- 如果找不到某个模式的文档，明确说明：

```
未经验证：我找不到此模式的官方文档。
这基于训练数据，可能已过时。
在生产环境中使用前请核实。
```

对你无法验证的内容保持诚实，比虚假的信心更有价值。

## 常见自我合理化

| 合理化借口 | 现实 |
|---|---|
| "我对这个 API 很有信心" | 信心不是证据。训练数据包含看起来正确但在当前版本上会崩溃的过时模式。验证它。 |
| "获取文档浪费 token" | 幻觉出一个 API 浪费更多。用户调试一小时，然后发现函数签名已经改了。一次获取可以防止数小时的返工。 |
| "文档不会有我需要的" | 如果文档没涵盖，那是有价值的信息——该模式可能不是官方推荐的。 |
| "我就提一下可能过时了" | 免责声明没有帮助。要么验证并引用，要么明确标记为未经验证。模棱两可是最差的选择。 |
| "这是个简单任务，没必要检查" | 使用错误模式的简单任务会变成模板。用户在发现现代方法存在之前，已经把你过时的表单处理器复制到了十个组件中。 |

## 危险信号

- 在未查阅该版本文档的情况下编写框架特定的代码
- 对 API 使用"我认为"或"我觉得"而非引用来源
- 在不知道模式适用于哪个版本的情况下实现它
- 引用 Stack Overflow 或博客文章而非官方文档
- 使用已弃用的 API，因为它们出现在训练数据中
- 在实现前未读取 `package.json` / 依赖文件
- 交付代码时未为框架特定的决策提供来源引用
- 只有一页相关时获取了整个文档站点

## 验证

使用源驱动开发实现后：

- [ ] 框架和库版本已从依赖文件中识别
- [ ] 已为框架特定的模式获取了官方文档
- [ ] 所有来源均为官方文档，而非博客文章或训练数据
- [ ] 代码遵循当前版本文档中展示的模式
- [ ] 非显而易见的决策包含带完整 URL 的来源引用
- [ ] 未使用已弃用的 API（已对照迁移指南检查）
- [ ] 文档与现有代码之间的冲突已向用户说明
- [ ] 任何无法验证的内容已明确标记为未经验证
