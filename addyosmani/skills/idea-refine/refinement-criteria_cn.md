# 精炼与评估标准

在阶段 2（评估与收敛）中使用此评估准则来压力测试想法方向。并非每个标准都适用于每个想法——运用判断力确定哪些维度对特定上下文最重要。

## 核心评估维度

### 1. 用户价值

最重要的维度。如果价值不明确，其他都无关紧要。

**止痛药 vs. 维生素：**
- **止痛药：** 解决一个急性的、频繁的问题。用户会主动寻求它。他们会从当前解决方案切换过来。信号：人们用情感描述问题，他们已经构建了临时方案，他们愿意为解决方案付费。
- **维生素：** 锦上添花。让某件事边际上更好。用户不会特意追求。信号：人们礼貌点头，说"挺酷的"，然后不改变行为。

**要问的问题：**
- 你能说出 3 个此刻正有这个问题的人的名字吗？
- 他们今天在用什么替代方案？（真正的竞争对手永远是当前的临时方案。）
- 他们会从当前方法切换过来吗？什么能让他们切换？
- 他们遇到这个问题的频率如何？（每天遇到的问题 > 每月遇到的问题）
- 这是一个"拉"的问题（用户在要求这个）还是"推"的问题（你认为他们应该想要这个）？

**危险信号：**
- "每个人都能用这个"——如果你说不出一个具体的用户，价值就不清楚
- "它像 X 但更好"——边际改进很少驱动采用
- 问题是真实的但很少见——高烈度但低频率很少能证明一个产品的合理性

### 2. 可行性

你真的能构建它吗？不仅是技术上，还有实践上。

**技术可行性：**
- 核心技术是否存在且能可靠工作？
- 最难的技术问题是什么？它是已知的难题还是全新的问题？
- 是否有对你不控制的第三方、API 或数据源的依赖？
- 所需的最小技术栈是什么？（如果答案是"很多"，这是一个信号。）

**资源可行性：**
- 构建 MVP 的最小团队/投入是多少？
- 是否需要你不拥有的专业知识？
- 是否有监管、法律或合规要求？

**实现价值的时间：**
- 你能多快将东西放到用户面前？
- 是否有在几天/几周而非几个月内交付价值的版本？
- 关键路径是什么？什么必须先发生？

**危险信号：**
- "我们只需要先解决[非常难的研究问题]"
- 多个依赖项都需要同时工作
- MVP 仍需数月的功——可能还不够最小

### 3. 差异化

什么让它真正不同？不是更好——是*不同*。

**要问的问题：**
- 如果用户向朋友描述这个，他们会怎么说？那个描述有说服力吗？
- 这件事做了而其他没做到的那一件事是什么？（如果你说不出一个，那就是问题。）
- 这种差异化是持久的吗？竞争对手能在一周内复制吗？
- 这个差异是用户真正关心的，还是只有构建者觉得有趣？

**差异化类型（从最强到最弱）：**
1. **新能力：** 做到了以前不可能的事情
2. **10 倍改进：** 在关键维度上比现有方案好太多，足以改变行为
3. **新受众：** 将现有能力带给之前被排除在外的人
4. **新上下文：** 在现有方案失败的场景中工作
5. **更好的 UX：** 相同能力，显著更简单的体验
6. **更便宜：** 相同的东西，更低的成本（最弱——容易被竞争打败）

**危险信号：**
- 差异化完全围绕技术，而非用户体验
- "我们更快/更便宜/更漂亮"却没有结构性的理由
- 形成差异化的功能并非用户最关心的功能

## 假设审计

对每个想法方向，在以下三个类别中明确列出假设：

### 必须为真（生死线）
如果错了，会完全扼杀这个想法的假设。这些在构建前需要验证。

示例："用户会与我们共享他们的数据"——如果他们不共享，整个产品无法运作。

### 应当为真（重要）
显著影响成功但不会扼杀想法的假设。如果这些错了，你可以调整方法。

示例："用户更喜欢自助服务而非与人交谈"——如果错了，你需要不同的市场推广策略，但核心产品仍然可以运作。

### 可能为真（锦上添花）
关于次要功能或优化的假设。在核心得到证明之前不要验证这些。

示例："用户会想与团队成员分享他们的结果"——一个增长功能，而非核心价值主张。

## 决策框架

在选择方向时，按以下矩阵排序：

|                    | 高可行性 | 低可行性 |
|--------------------|----------|----------|
| **高价值**          | 先做这个  | 值得冒险 |
| **低价值**          | 仅当微不足道 | 不做这个 |

然后用差异化作为同一象限中选项之间的决胜条件。

## MVP 范围确定原则

在确定选定方向的 MVP 范围时：

1. **做好一件事。** MVP 应该精准地完成一项用户任务。不是三项任务半途而废。
2. **最危险的假设优先。** MVP 的主要目的是测试最可能为错的假设。
3. **时间盒，而非功能列表。** "我们在[时间范围]内能构建并测试什么？"优于"我们需要哪些功能？"
4. **"不做"清单是强制性的。** 明确说出你正在砍掉什么及其原因。这防止范围蔓延并迫使诚实的优先级排序。
5. **如果它不令人尴尬，你等得太久了。** 第一个版本对构建者来说应该感觉不完整。如果不觉得，你已经过度构建了。
