# 代码审查与质量

## 概述

带质量门槛的多维代码审查。每个变更在合并前都要审查——没有例外。审查覆盖五个轴：正确性、可读性、架构、安全性和性能。

**批准标准：** 当一个变更明确地改善了整体代码健康状况时批准它，即使它不完美。完美的代码不存在——目标是持续改进。不要因为变更不是你写的方式就阻止它。如果它改善了代码库并遵循项目约定，批准它。

## 何时使用

- 合并任何 PR 或变更之前
- 完成功能实现之后
- 另一个 agent 或模型产生的代码需要你评估时
- 重构现有代码时
- 任何 bug 修复之后（审查修复和回归测试）

## 五轴审查

每次审查评估代码的以下维度：

### 1. 正确性

代码做了它声称做的事吗？

- 它是否匹配 spec 或任务需求？
- 边缘情况是否处理了（null、空、边界值）？
- 错误路径是否处理了（不仅仅是快乐路径）？
- 是否通过了所有测试？测试真正在测试正确的东西吗？
- 是否存在 off-by-one 错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一个工程师（或 agent）能否在没有作者解释的情况下理解这段代码？

- 名称是否具有描述性且与项目约定一致？（不要有没有上下文的 `temp`、`data`、`result`）
- 控制流是否直接（避免嵌套三元表达式、深层回调）？
- 代码组织是否合理（相关代码分组、清晰的模块边界）？
- 有没有应该简化的"聪明"技巧？
- **能否用更少的行数完成？**（1000 行能做的事却写了 100 行是失败的）
- **抽象是否配得上它们的复杂性？**（在第三个用例之前不要泛化）
- 注释是否有助于澄清非显而易见的意图？（但不要为显而易见的代码加注释。）
- 是否存在死代码产物：空操作变量（`_unused`）、向后兼容填充、或 `// removed` 注释？
- **一个新的条件判断是否附加到了无关的流程上？** 这是一个设计坏味，不是挑剔——将逻辑推入自己的辅助函数、状态或策略中，而不是纠缠现有的路径。
- **同一形状上是否出现重复的条件判断？** 它们暗示缺失了模型或分发器。一个"临时"分支通常是永久债务。

### 3. 架构

变更是否符合系统的设计？

- 它是否遵循现有模式还是引入了新模式？如果是新的，是否合理？
- 它是否保持干净的模块边界？
- 是否存在应该共享的代码重复？
- 依赖是否有向正确方向流动（没有循环依赖）？
- 抽象水平是否适当（不过度工程化，不耦合过紧）？
- **这次重构是否降低了复杂性还是仅仅移动了它？** 统计读者跟踪这个变更所需的概念数量。如果"更干净"版本让这个数量不变，它就不更干净——偏好那种让整个分支、模式或层消失的重组而非重新集中相同的逻辑。偏好删除一个抽象，而非打磨它。
- **功能特定的逻辑是否泄漏到了共享或通用模块中？** 将逻辑保留在它的归属层，复用现有的标准辅助函数而非近似重复的函数，不要规范化架构漂移。
- **类型边界是否明确？** 质疑无端出现的 `any`/`unknown`/optional/类型转换和静默回退，它们掩饰了不清晰的不变量——使边界明确常常让周围的流程变得更简单。

### 4. 安全性

关于详细的安全指南，参见 `security-and-hardening`。此变更是否引入了漏洞？

- 用户输入是否经过验证和清理？
- Secrets 是否远离代码、日志和版本控制？
- 认证/授权是否在需要的地方检查过？
- SQL 查询是否参数化（无字符串拼接）？
- 输出是否经过编码以防止 XSS？
- 依赖是否来自可信来源且没有已知漏洞？
- 来自外部来源（API、日志、用户内容、配置文件）的数据是否被视为不可信？
- 外部数据流是否在系统边界验证后才用于逻辑或渲染？

### 5. 性能

关于详细的分析和优化，参见 `performance-optimization`。此变更是否引入了性能问题？

- 是否有 N+1 查询模式？
- 是否有无界循环或无约束的数据获取？
- 是否有应当是异步的同步操作？
- UI 组件中是否有不必要的重渲染？
- 列表端点是否缺失分页？
- 热路径中是否创建了大型对象？

## 结构性补救

当你标记一个结构性问题时，提出行动方案——不仅仅是问题。一个只说了"这很复杂"的审查让作者去猜测。采用一个命名的重构方法：

- **用类型化模型或显式分发器替换条件链。**
- **将重复分支折叠成单一更清晰的流程。**
- **将编排从业务逻辑中分离**，使每个能独立阅读。
- **将功能特定逻辑移出共享模块**到拥有该概念的包中。
- **复用标准辅助函数**而非定制的近似重复。
- **使类型边界明确**从而使下游分支消失。
- **删除穿透性包装器**，它增加了间接层而没有澄清 API。
- **提取一个辅助函数，或将大文件拆分为专注的模块。**

偏好那种消除移动部件的补救方案，而非那种将相同复杂性分散开的方案。

## 变更规模

小而专注的变更更容易审查、更快合并、更安全部署。以这些大小为目 标：

```
~100 行变更    → 好。一次看完可审查。
~300 行变更    → 如果是单一逻辑变更可以接受。
~1000 行变更   → 太大。拆分它。
```

**关注文件大小，而不仅仅是 diff 大小。** 一个小 diff 仍可以让文件超过健康边界——一个文件中大约 1000 行*总*代码（区别于上述约 1000 行*变更*阈值）是一个常见的检查信号，不是硬性上限。当一个变更实质性地增长了一个已经很大的文件时，先问是否提取辅助函数、子组件或模块，再往上加。先分解，再添加。

**什么算作"一个变更"：** 一个单一的、自包含的修改，解决一件事，包含相关测试，并在提交后保持系统功能正常。功能的一部分——而非整个功能。

**当变更太大时的拆分策略：**

| 策略 | 如何操作 | 何时使用 |
|----------|-----|------|
| **堆叠** | 提交一个小变更，在此基础上开始下一个 | 顺序依赖 |
| **按文件组** | 为需要不同审查者的文件组分离开 | 横切关注点 |
| **水平** | 先创建共享代码/stub，然后消费者 | 分层架构 |
| **垂直** | 拆分为功能的更小全栈切片 | 功能工作 |

**何时大变更可以接受：** 完整的文件删除和自动化重构，其中审查者只需要验证意图，而非每一行。

**将重构与功能工作分开。** 一个既重构现有代码又添加新行为的变更是两个变更——分别提交。小的清理（变量重命名）可以视审查者意愿包含在内。

## 变更描述

每个变更都需要一个能在版本控制历史中独立存在的描述。

**第一行：** 简短、祈使句、独立。"Delete the FizzBuzz RPC"而非"Deleting the FizzBuzz RPC。"必须信息充足，以便搜索历史的人能够理解该变更而无需阅读 diff。

**正文：** 变更了什么以及为什么。包含代码本身不可见的上下文、决策和推理。在相关的地方链接到 bug 编号、基准测试结果或设计文档。当存在缺陷时承认方法的不足。

**反模式：** "Fix bug"、"Fix build"、"Add patch"、"Moving code from A to B"、"Phase 1"、"Add convenience functions."

## 审查流程

### 第 1 步：理解上下文

在查看代码之前，理解意图：

```
- 这个变更试图完成什么？
- 它实现了哪个 spec 或任务？
- 预期的行为变更是什么？
```

### 第 2 步：先审查测试

测试揭示意图和覆盖范围：

```
- 是否有针对该变更的测试？
- 它们是否测试行为（而非实现细节）？
- 边缘情况是否覆盖？
- 测试是否有描述性名称？
- 如果代码变了，测试是否能捕获回归？
```

### 第 3 步：审查实现

以五轴思想遍览代码：

```
对于每个变更的文件：
1. 正确性: 这段代码是否做了测试说它应该做的？
2. 可读性: 我能否在没有帮助的情况下理解它？
3. 架构: 这个变更适合系统吗？
4. 安全性: 是否存在漏洞？
5. 性能: 是否存在瓶颈？
```

### 第 4 步：分类发现

用严重性标记每个评论，使作者知道什么是必须的 vs. 可选的：

| 前缀 | 含义 | 作者行动 |
|--------|---------|---------------|
| *(无前缀)* | 需要变更 | 合并前必须处理 |
| **Critical:**（严重） | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:**（吹毛求疵） | 次要、可选 | 作者可忽略——格式、风格偏好 |
| **Optional:**（可选）/ **Consider:**（考虑） | 建议 | 值得考虑但不必须 |
| **FYI**（供参考） | 仅信息 | 无需行动——供未来参考的上下文 |

这防止作者将所有反馈视为强制性的，并浪费时间在可选建议上。

**把重要的放在前面。** 按杠杆作用排序发现：正确性和安全性优先，然后是结构性回归和错过的简化，最后是其他一切。不要将真正的问题埋在表面吹毛求疵之下——几条高度可信的评论胜过一长串。如果你有一个结构性问题和十个吹毛求疵，这个结构性问题*就是*审查。

### 第 5 步：验证证明

检查作者的验证经历：

```
- 运行了哪些测试？
- 构建是否通过？
- 是否手动测试了变更？
- UI 变更是否有截图？
- 是否有前后对比？
```

## 多模型审查模式

使用不同的模型获得不同的审查视角：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人类做最终决策
```

这能捕获单个模型可能遗漏的问题——不同的模型有不同的盲点。

**审查 agent 的示例提示：**
```
审查此代码变更的正确性、安全性以及对我们项目约定的遵守。
Spec 说 [X]。此变更应该 [Y]。
将任何问题标记为 Critical、Required、Optional 或 Nit。
```

## 死代码卫生

在任何重构或实现变更之后，检查孤儿代码：

1. 识别现在不可到达或未使用的代码
2. 明确列出它
3. **在删除之前询问：** "我应该删除这些现在未使用的元素吗：[列表]？"

不要让死代码散落在周围——它会迷惑未来的读者和 agent。但不要默默删除你不确定的东西。不确定时，询问。

```
DEAD CODE IDENTIFIED（识别到的死代码）:
- formatLegacyDate() 在 src/utils/date.ts — 已被 formatDate() 替代
- OldTaskCard 组件在 src/components/ — 已被 TaskCard 替代
- LEGACY_API_URL 常量在 src/config.ts — 没有剩余引用
→ 可以安全删除这些吗？
```

## 审查速度

缓慢的审查会阻塞整个团队。上下文切换来审查的成本小于强加给他人的等待成本。

- **在一个工作日内响应**——这是上限，不是目标
- **理想节奏：** 在审查请求抵达后短时间内响应，除非处于深度专注编码中。一个典型的变更应在一天内完成多个审查轮次
- **优先考虑快速的个别响应**而非快速最终批准。即使需要多轮，快速反馈也能减少挫败感
- **大变更：** 要求作者拆分它们，而不是审查一个巨大的变更集

## 处理分歧

在解决审查争议时，应用此层级：

1. **技术事实和数据**覆盖观点和偏好
2. **风格指南**是风格问题的绝对权威
3. **软件设计**必须基于工程原则评估，而非个人偏好
4. **代码库一致性**在不降低整体健康状况的情况下可以接受

**不要接受"我后面会清理的"。** 经验表明推迟的清理很少发生。除非是真正的紧急情况，否则在提交前要求清理。如果周围问题不能在此变更中处理，要求创建一个 bug 并自我指派。

## 审查中的诚实

在审查代码时——无论是由你、另一个 agent 还是人类编写的：

- **不要橡皮图章。** 没有审查证据的"LGTM"对任何人都没有帮助。
- **不要软化和淡化真正的问题。** "这可能是一个小问题"而当那是一个会打到生产环境的 bug 时，这是不诚实的。
- **在可能时量化问题。** "此 N+1 查询将为列表中的每个条目增加约 50ms"好于"这可能很慢。"
- **对有明确问题的方法提出反驳。** 谄媚是审查中的失败模式。如果实现有问题，直接说并提出替代方案。
- **优雅地接受覆盖。** 如果作者拥有完整上下文且不同意，服从他们的判断。评论代码，而非人——将个人批评重新框定为关注代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**添加任何依赖之前：**
1. 现有技术栈能解决吗？（通常能。）
2. 依赖有多大？（检查 bundle 影响。）
3. 它是否在活跃维护中？（检查最后一次提交、开放 issue。）
4. 它有已知漏洞吗？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 偏好标准库和现有工具函数，而非新依赖。每个依赖都是一项负债。

## 审查检查清单

```markdown
## Review: [PR/变更标题]

### Context（上下文）
- [ ] 我理解这个变更做什么以及为什么

### Correctness（正确性）
- [ ] 变更匹配 spec/任务需求
- [ ] 边缘情况已处理
- [ ] 错误路径已处理
- [ ] 测试充分覆盖此变更

### Readability（可读性）
- [ ] 名称清晰且一致
- [ ] 逻辑直接
- [ ] 没有不必要的复杂性

### Architecture（架构）
- [ ] 遵循现有模式
- [ ] 没有不必要的耦合或依赖
- [ ] 适当的抽象水平
- [ ] 重构降低了复杂性而非移动了它
- [ ] 共享模块中没有功能逻辑；文件保持在健康大小

### Security（安全性）
- [ ] 代码中没有 secrets
- [ ] 输入在边界验证
- [ ] 没有注入漏洞
- [ ] 认证检查到位
- [ ] 外部数据来源被视为不可信

### Performance（性能）
- [ ] 没有 N+1 模式
- [ ] 没有无界操作
- [ ] 列表端点有分页

### Verification（验证）
- [ ] 测试通过
- [ ] 构建成功
- [ ] 手动验证完成（如果适用）

### Verdict（判定）
- [ ] **Approve**（批准） — 已准备好合并
- [ ] **Request changes**（要求修改） — 问题必须处理
```

## 常见借口

| 借口 | 现实 |
|---|---|
| "它能用，够好了" | 能工作但不可读、不安全或架构错误的代码会产生复利增长的债务。 |
| "我写的，所以我知道它是正确的" | 作者对自己假设有盲点。每个变更都受益于另一双眼睛。 |
| "我们后面会清理的" | 后面永远不会来。审查是质量门槛——使用它。在合并前要求清理，不是在之后。 |
| "AI 生成的代码可能没问题" | AI 代码需要更多审查，而非更少。它自信且看起来合理，即使错误。 |
| "测试通过了，所以它是好的" | 测试是必要的但不充分。它们不捕获架构问题、安全问题或可读性问题。 |
| "重构让它更干净" | 移动复杂性不是减少它。如果读者仍然持有同样数量的概念，结构没有改进——寻找分支消失的版本。 |
| "只是对这个文件的一个小增加" | 小 diff 仍会将文件推到健康大小之外，并在无关流程中附加分支。评判结果结构，而非 diff 大小。 |

## 警示信号

- 没有任何审查就合并的 PR
- 只检查测试是否通过的审查（忽略其他轴）
- "LGTM"但没有实际审查的证据
- 安全敏感变更没有安全聚焦的审查
- 太大而"无法正确审查"的大 PR（拆分它们）
- Bug 修复 PR 没有回归测试
- 审查评论没有严重性标签——使不明确什么是必须的 vs. 可选的
- 接受"我后面会修复"——这从不会发生
- 一个移动代码但未减少读者必须持有的概念数量的重构
- 一个增加已经很大文件的变更，而不是分解它
- 新的条件判断分散到无关的代码路径中（缺失的抽象）
- 一个定制的辅助函数重复了已有的标准函数，或功能逻辑被放在共享模块中

## 验证

审查完成后：

- [ ] 所有 Critical 问题已解决
- [ ] 所有 Required（无前缀的）变更已解决或明确推迟且附有理由
- [ ] 测试通过
- [ ] 构建成功
- [ ] 验证经历已记录（变更了什么、如何验证的）

**推定阻塞项：** 对以下每一项提出并建议更简单的设计；仅当变更使结构变差时才升级为 Required：一个移动复杂性而非减少它的重构；一个将文件推过大小边界且没有分解的变更；添加到共享模块的功能逻辑；一个已有标准辅助函数的近似重复；一个隐藏不清晰不变量的静默回退。
