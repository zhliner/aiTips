# 发布与上线（Shipping and Launch）

## 概述

自信地发布。目标不仅仅是部署——而是安全地部署，确保监控就位、回滚方案就绪，并清楚地了解成功的标准。每次发布都应该是可逆的、可观测的、渐进式的。

## 使用时机

- 首次将功能部署到生产环境
- 向用户发布重大变更
- 迁移数据或基础设施
- 开放 Beta 或早期访问计划
- 任何带有风险的部署（所有部署都有风险）

## 发布前检查清单

### 代码质量

- [ ] 所有测试通过（单元测试、集成测试、端到端测试）
- [ ] 构建成功且无警告
- [ ] Lint 和类型检查通过
- [ ] 代码已审查并批准
- [ ] 没有应在发布前解决的 TODO 注释
- [ ] 生产代码中没有 `console.log` 调试语句
- [ ] 错误处理覆盖了预期的失败模式

### 安全性

- [ ] 代码或版本控制中没有密钥
- [ ] `npm audit` 没有显示严重或高危漏洞
- [ ] 所有面向用户的端点都有输入验证
- [ ] 身份验证和授权检查已就位
- [ ] 安全头已配置（CSP、HSTS 等）
- [ ] 身份验证端点有速率限制
- [ ] CORS 配置为特定来源（非通配符）

### 性能

- [ ] Core Web Vitals 在"良好"阈值范围内
- [ ] 关键路径中没有 N+1 查询
- [ ] 图片已优化（压缩、响应式尺寸、懒加载）
- [ ] 包大小在预算范围内
- [ ] 数据库查询有适当的索引
- [ ] 静态资源和重复查询已配置缓存

### 无障碍性

- [ ] 所有交互元素支持键盘导航
- [ ] 屏幕阅读器能够传达页面内容和结构
- [ ] 颜色对比度符合 WCAG 2.1 AA 标准（文本 4.5:1）
- [ ] 模态框和动态内容的焦点管理正确
- [ ] 错误信息具有描述性且与表单字段关联
- [ ] axe-core 或 Lighthouse 中没有无障碍性警告

### 基础设施

- [ ] 生产环境变量已设置
- [ ] 数据库迁移已应用（或准备就绪）
- [ ] DNS 和 SSL 已配置
- [ ] CDN 已为静态资源配置
- [ ] 日志和错误报告已配置
- [ ] 健康检查端点存在且有响应

### 文档

- [ ] README 已更新任何新的设置要求
- [ ] API 文档是最新的
- [ ] 任何架构决策都已编写 ADR
- [ ] 变更日志已更新
- [ ] 面向用户的文档已更新（如适用）

## Feature Flag 策略

通过 feature flag 来解耦部署与发布：

```typescript
// Feature flag 检查
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新功能：任务共享
  return <TaskSharingPanel task={task} />;
}

// 默认：现有行为
return null;
```

**Feature flag 生命周期：**

```
1. 部署时 flag 关闭     → 代码已在生产环境但未激活
2. 为团队/Beta 启用     → 在生产环境中进行内部测试
3. 渐进式发布           → 5% → 25% → 50% → 100% 的用户
4. 每个阶段进行监控     → 关注错误率、性能、用户反馈
5. 清理                 → 全量发布后移除 flag 和无效的代码路径
```

**规则：**
- 每个 feature flag 都有负责人和过期日期
- 在全量发布后 2 周内清理 flag
- 不要嵌套 feature flag（会产生指数级的组合）
- 在 CI 中测试 flag 的两种状态（开启和关闭）

## 分阶段发布

### 发布流程

```
1. 部署到预发布环境
    └── 在预发布环境中运行完整测试套件
    └── 手动冒烟测试关键流程

2. 部署到生产环境（feature flag 关闭）
    └── 验证部署成功（健康检查）
    └── 检查错误监控（无新增错误）

3. 为团队启用（内部用户开启 flag）
    └── 团队在生产环境中使用该功能
    └── 24 小时监控窗口

4. 金丝雀发布（5% 的用户开启 flag）
    └── 监控错误率、延迟、用户行为
    └── 对比指标：金丝雀组 vs. 基线组
    └── 24-48 小时监控窗口
    └── 仅当所有阈值通过时才推进（见下表）

5. 逐步扩大（25% -> 50% -> 100%）
    └── 每个步骤进行相同的监控
    └── 能够随时回滚到上一个百分比

6. 全量发布（所有用户开启 flag）
    └── 监控 1 周
    └── 清理 feature flag
```

### 发布决策阈值

使用以下阈值决定在每个阶段是推进、暂停还是回滚：

| 指标 | 推进（绿色） | 暂停并调查（黄色） | 回滚（红色） |
|--------|-----------------|-------------------------------|-----------------|
| 错误率 | 在基线的 10% 以内 | 高于基线 10-100% | 高于基线 2 倍以上 |
| P95 延迟 | 在基线的 20% 以内 | 高于基线 20-50% | 高于基线 50% 以上 |
| 客户端 JS 错误 | 无新增错误类型 | 新错误影响 <0.1% 的会话 | 新错误影响 >0.1% 的会话 |
| 业务指标 | 持平或正向 | 下降 <5%（可能是噪声） | 下降 >5% |

### 何时回滚

出现以下情况时立即回滚：
- 错误率增长超过基线的 2 倍
- P95 延迟增长超过 50%
- 用户报告的问题激增
- 检测到数据完整性问题
- 发现安全漏洞

## 监控与可观测性

### 需要监控的内容

```
应用指标：
├── 错误率（总量和按端点）
├── 响应时间（p50、p95、p99）
├── 请求量
├── 活跃用户
└── 关键业务指标（转化率、参与度）

基础设施指标：
├── CPU 和内存使用率
├── 数据库连接池使用情况
├── 磁盘空间
├── 网络延迟
└── 队列深度（如适用）

客户端指标：
├── Core Web Vitals（LCP、INP、CLS）
├── JavaScript 错误
├── 从客户端视角看的 API 错误率
└── 页面加载时间
```

### 错误报告

```typescript
// 设置带有报告功能的错误边界
class ErrorBoundary extends React.Component {
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 报告到错误跟踪服务
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 服务端错误报告
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 不要向用户暴露内部信息
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' },
  });
});
```

### 发布后验证

在发布后的第一个小时内：

```
1. 检查健康端点返回 200
2. 检查错误监控仪表板（无新增错误类型）
3. 检查延迟仪表板（无回归）
4. 手动测试关键用户流程
5. 确认日志正在流入且可读
6. 确认回滚机制可用（如可能进行演练）
```

## 回滚策略

每次部署都需要事先准备回滚方案：

```markdown
## [功能/版本] 的回滚方案

### 触发条件
- 错误率 > 基线的 2 倍
- P95 延迟 > [X]ms
- 用户报告 [具体问题]

### 回滚步骤
1. 禁用 feature flag（如适用）
    或
1. 部署上一个版本：`git revert <commit> && git push`
2. 验证回滚：健康检查、错误监控
3. 沟通：通知团队已回滚

### 数据库注意事项
- 迁移 [X] 有回滚方案：`npx prisma migrate rollback`
- 新功能插入的数据：[保留 / 清理]

### 回滚耗时
- Feature flag：< 1 分钟
- 重新部署上一个版本：< 5 分钟
- 数据库回滚：< 15 分钟
```

## 常见的自我合理化

| 自我合理化 | 现实 |
|---|---|
| "在预发布环境能用，生产环境也行" | 生产环境有不同的数据、流量模式和边界情况。部署后必须监控。 |
| "这个不需要 feature flag" | 每个功能都能从紧急开关中受益。即使是"简单"的变更也可能导致问题。 |
| "监控是额外开销" | 没有监控意味着你通过用户投诉而不是仪表板来发现问题。 |
| "我们以后再添加监控" | 在发布前就添加。你无法调试看不到的东西。 |
| "回滚意味着承认失败" | 回滚是负责任的工程行为。发布一个有问题的功能才是真正的失败。 |

## 危险信号

- 没有回滚方案就部署
- 生产环境没有监控或错误报告
- 大爆炸式发布（一次性全部上线，没有预发布环境）
- Feature flag 没有过期时间或负责人
- 部署后第一个小时没有人监控
- 生产环境配置靠记忆，而不是代码
- "周五下午了，直接发布吧"

- [ ] 回滚方案已记录
