# 发布与上线

## 概述

带着信心发布。目标不仅是部署——而是安全地部署，配置好监控，准备好回滚计划，并清晰理解成功的样子。每一次上线都应该是可逆的、可观测的和增量的。

## 何时使用

- 首次将功能部署到生产
- 向用户发布重大变更
- 迁移数据或基础设施
- 开放 Beta 或早期访问计划
- 任何带有风险的部署（所有的部署都带有风险）

## 上线前检查清单

### Code Quality（代码质量）

- [ ] 所有测试通过（单元、集成、端到端）
- [ ] 构建成功，无警告
- [ ] Lint 和类型检查通过
- [ ] 代码已审查并批准
- [ ] 没有应在发布前解决的 TODO 注释
- [ ] 生产代码中没有 `console.log` 调试语句
- [ ] 错误处理覆盖了预期的失败模式

### Security（安全性）

- [ ] 代码或版本控制中没有 secrets
- [ ] `npm audit` 显示没有严重或高危漏洞
- [ ] 所有面向用户的端点有输入验证
- [ ] 认证和授权检查到位
- [ ] 安全头已配置（CSP、HSTS 等）
- [ ] 认证端点有速率限制
- [ ] CORS 配置为特定来源（非通配符）

### Performance（性能）

- [ ] Core Web Vitals 在"良好"阈值内
- [ ] 关键路径中没有 N+1 查询
- [ ] 图片已优化（压缩、响应式尺寸、懒加载）
- [ ] Bundle 大小在预算内
- [ ] 数据库查询有适当的索引
- [ ] 静态资源和重复查询配置了缓存

### Accessibility（无障碍性）

- [ ] 所有交互元素支持键盘导航
- [ ] 屏幕阅读器可以传达页面内容和结构
- [ ] 颜色对比度满足 WCAG 2.1 AA（文本 4.5:1）
- [ ] 模态和动态内容的焦点管理正确
- [ ] 错误消息具有描述性并与表单字段关联
- [ ] 在 axe-core 或 Lighthouse 中没有无障碍警告

### Infrastructure（基础设施）

- [ ] 生产环境变量已设置
- [ ] 数据库迁移已应用（或准备好应用）
- [ ] DNS 和 SSL 已配置
- [ ] CDN 已配置用于静态资源
- [ ] 日志和错误报告已配置
- [ ] 健康检查端点存在并能响应

### Documentation（文档）

- [ ] README 已更新，包含任何新的设置要求
- [ ] API 文档是最新的
- [ ] 任何架构决策已写入 ADR
- [ ] Changelog 已更新
- [ ] 面向用户的文档已更新（如果适用）

## 功能标志策略

在功能标志后面发布，将部署与发布解耦：

```typescript
// 功能标志检查
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新功能: 任务分享
  return <TaskSharingPanel task={task} />;
}

// 默认: 现有行为
return null;
```

**功能标志生命周期：**

```
1. DEPLOY（部署）, flag 为 OFF     → 代码已在生产但未激活
2. ENABLE（启用）给团队/beta       → 在生产环境中内部测试
3. GRADUAL ROLLOUT（渐进上线）     → 5% → 25% → 50% → 100% 的用户
4. MONITOR（监控）在每个阶段       → 关注错误率、性能、用户反馈
5. CLEAN UP（清理）                → 完全上线后移除 flag 和死代码路径
```

**规则：**
- 每个功能标志有所有者和过期日期
- 在完全上线后 2 周内清理标志
- 不要嵌套功能标志（会产生指数级组合）
- 在 CI 中测试两种 flag 状态（开和关）

## 分阶段上线

### 上线顺序

```
1. DEPLOY to staging（部署到 staging）
   └── 在 staging 环境运行完整测试套件
   └── 手动冒烟测试关键流程

2. DEPLOY to production（部署到生产，feature flag OFF）
   └── 验证部署成功（健康检查）
   └── 检查错误监控（没有新错误）

3. ENABLE for team（对内部用户开启 flag）
   └── 团队在生产中使用该功能
   └── 24 小时监控窗口

4. CANARY rollout（金丝雀上线，5% 用户开启 flag）
   └── 监控错误率、延迟、用户行为
   └── 对比指标：金丝雀 vs. 基线
   └── 24-48 小时监控窗口
   └── 仅当所有阈值通过时才前进（参见下表）

5. GRADUAL increase（渐进增加，25% -> 50% -> 100%）
   └── 每步相同监控
   └── 可在任何点回滚到之前的百分比

6. FULL rollout（完全上线，所有用户 flag ON）
   └── 监控 1 周
   └── 清理功能标志
```

### 上线决策阈值

使用这些阈值在每个阶段决定是前进、暂停还是回滚：

| 指标 | 前进（绿色） | 暂停并调查（黄色） | 回滚（红色） |
|--------|-----------------|-------------------------------|-----------------|
| 错误率 | 在基线的 10% 以内 | 高于基线 10-100% | >2x 基线 |
| P95 延迟 | 在基线的 20% 以内 | 高于基线 20-50% | >50% 高于基线 |
| 客户端 JS 错误 | 没有新错误类型 | 新错误在 <0.1% 的会话中 | 新错误在 >0.1% 的会话中 |
| 业务指标 | 中性或正向 | 下降 <5%（可能是噪音） | 下降 >5% |

### 何时回滚

在以下情况下立即回滚：
- 错误率增加超过基线的 2 倍
- P95 延迟增加超过 50%
- 用户报告的 issue 激增
- 检测到数据完整性问题
- 发现安全漏洞

## 监控与可观测性

### 监控什么

```
应用指标:
├── 错误率（总计和按端点）
├── 响应时间（p50、p95、p99）
├── 请求量
├── 活跃用户
└── 关键业务指标（转化、参与度）

基础设施指标:
├── CPU 和内存利用率
├── 数据库连接池使用量
├── 磁盘空间
├── 网络延迟
└── 队列深度（如果适用）

客户端指标:
├── Core Web Vitals（LCP、INP、CLS）
├── JavaScript 错误
├── 从客户端视角的 API 错误率
└── 页面加载时间
```

### 错误报告

```typescript
// 设置带报告的 error boundary
class ErrorBoundary extends React.Component {
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 报告到错误追踪服务
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 服务端错误报告
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 不要向用户暴露内部信息
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: '出了点问题' },
  });
});
```

### 上线后验证

在上线后的第一个小时内：

```
1. 检查健康端点返回 200
2. 检查错误监控仪表盘（没有新错误类型）
3. 检查延迟仪表盘（没有回归）
4. 手动测试关键用户流程
5. 验证日志在流动且可读
6. 确认回滚机制可用（可能的话做演练）
```

## 回滚策略

每次部署在发生之前就需要有回滚计划：

```markdown
## Rollback Plan for [功能/发布]

### 触发条件
- 错误率 > 2x 基线
- P95 延迟 > [X]ms
- 用户报告 [特定问题]

### 回滚步骤
1. 禁用功能标志（如果适用）
   OR
1. 部署之前版本: `git revert <commit> && git push`
2. 验证回滚: 健康检查、错误监控
3. 沟通: 通知团队回滚情况

### 数据库考虑因素
- 迁移 [X] 有一个回滚: `npx prisma migrate rollback`
- 新功能插入的数据: [保留 / 清理]

### 回滚时间
- 功能标志: < 1 分钟
- 重新部署之前版本: < 5 分钟
- 数据库回滚: < 15 分钟
```

## 常见借口

| 借口 | 现实 |
|---|---|
| "在 staging 能用，生产也一定能用" | 生产有不同的数据、流量模式和边缘情况。部署后进行监控。 |
| "我们不需要为这个做功能标志" | 每个功能都受益于一个 kill switch。即使"简单"的变更也可能破坏东西。 |
| "监控是额外开销" | 没有监控意味着你从用户投诉而非仪表盘发现问题。 |
| "我们后面再加监控" | 上线前就加上。你无法调试你看不到的东西。 |
| "回滚是承认失败" | 回滚是负责任的工程。发布有问题的功能才是失败。 |

## 警示信号

- 没有回滚计划就部署
- 生产中没有监控或错误报告
- 大爆炸发布（一次性全部上线，无分阶段）
- 功能标志没有过期日期或所有者
- 第一个小时内没人监控部署
- 生产环境配置凭记忆设置，而非代码
- "周五下午了，我们发布吧"

## 验证

部署前：

- [ ] 上线前检查清单已完成（所有部分绿色）
- [ ] 功能标志已配置（如果适用）
- [ ] 回滚计划已记录在案
- [ ] 监控仪表盘已设置
- [ ] 团队已通知部署

部署后：

- [ ] 健康检查返回 200
- [ ] 错误率正常
- [ ] 延迟正常
- [ ] 关键用户流程能正常工作
- [ ] 日志在流动
- [ ] 回滚已测试或已验证准备就绪
