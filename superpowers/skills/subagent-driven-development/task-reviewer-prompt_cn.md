# 任务审查者 Prompt 模板

分派任务审查子代理时使用此模板。审查者读取任务的 diff 一次并返回两个判断：spec 合规性和代码质量。

**目的：** 验证一个任务的实现与其需求匹配（不多不少），且构建良好（整洁、已测试、可维护）

```
Subagent (general-purpose):
  description: "审查任务 N (spec + 质量)"
  model: [MODEL — 必填：按 SKILL.md 的模型选择部分选择；省略时静默继承会话中最昂贵的模型]
  prompt: |
    你正在审查一个任务的实现：首先检查它是否与其需求匹配，然后检查它是否构建良好。
    这是一个任务范围的关卡，而非合并审查——在所有任务完成后会单独进行一次整体分支审查。

    ## 被要求了什么

    阅读任务简报: [BRIEF_FILE]

    来自 spec/设计文档的约束该任务的全局约束:
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称构建了什么

    阅读实现者的报告: [REPORT_FILE]

    ## 审查的 Diff

    **Base:** [BASE_SHA]
    **Head:** [HEAD_SHA]
    **Diff 文件:** [DIFF_FILE]

    读取 diff 文件一次——它包含提交列表、统计摘要以及带上下文的全量 diff，
    这是你对变更的视图。diff 的上下文行即变更的文件：不要单独 Read 一个变更的文件，
    除非你必须判断的一个代码块在函数中间被截断——并在报告中说明。
    不要重新运行 git 命令。如果 diff 文件缺失，自行获取 diff：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬取更广泛的代码库。仅在评估你能明确指出的具体风险时才检查 diff 之外的代码——
    每个明确风险仅做一次聚焦检查，并在报告中指明该风险和检查的内容。
    跨领域的变更是合理的可明确指出风险：如果 diff 改变了锁顺序、函数或 API 契约、
    或共享可变状态，检查调用点是正确的方法。

    你的审查对此工作副本是只读的。不要以任何方式修改工作树、索引、HEAD 或分支状态。

    ## 不要信任报告

    将实现者的报告视为关于代码的未经验证的声明。它可能不完整、不准确或过于乐观。
    对照 diff 验证这些声明。报告中的设计理由也是声明："根据 YAGNI 保持原样"
    "有意保持简单"或任何其他理由都是实现者在给自己的作业打分。
    基于代码本身来评判——明确的理由不会降低发现的严重等级。

    ## 测试

    实现者已经对这段代码运行了测试并以 TDD 证据汇报了结果。
    不要重新运行套件来确认他们的报告。仅在阅读代码引发了一个现有运行无法回答的具体怀疑时才运行测试——
    且仅运行聚焦测试，绝不要运行包级别的套件、竞态检测器或重复/高次循环。
    如果重度验证看似有必要，在你的报告中建议而非运行它。
    如果你在此环境中无法运行命令，说出你会运行哪个测试。

    实现者报告的测试输出中的警告或其他噪音是发现——测试输出应该是干净的。

    ## 第一部分：Spec 合规性

    将 diff 与"被要求了什么"进行比较：

    - **缺失:** 他们跳过、遗漏或声称实现但未实际实现的需求
    - **多余:** 未被要求的功能、过度工程、不必要的"锦上添花"
    - **理解错误:** 正确的功能用错误的方式构建，解决了错误的问题

    如果某需求无法仅从此 diff 验证（它存在于未变更的代码中或跨任务），
    将其报告为 ⚠️ 事项，而非扩大搜索范围。

    ## 第二部分：代码质量

    **代码质量：**
    - 关注点是否清晰分离？
    - 错误处理是否适当？
    - 是否 DRY 且无过早抽象？
    - 边缘情况是否处理？

    **测试：**
    - 新增和修改的测试是否验证真实行为，而非 mock？
    - 任务的边缘情况是否覆盖？

    **结构：**
    - 每个文件是否有一个清晰的职责和定义良好的接口？
    - 单元是否被分解到能够独立理解和测试的程度？
    - 实现是否遵循计划中的文件结构？
    - 此变更是否创建了已经很大的新文件，或显著增大了现有文件？（不要标记已存在的文件大小——
      仅关注此变更贡献了什么。）

    你的报告应指向证据：为每个发现和任何你会用一句"是"回答的检查提供 file:line 引用。
    一份引用行号的简洁报告为控制器提供了所需的一切。

    你的最终消息就是报告本身：直接以 spec 合规性判断开头。
    每一行都是一个判断、一个带 file:line 的发现、或你执行的检查——无需序言、
    无需过程描述、无需结束总结。

    ## 校准

    按实际严重程度对问题分类。并非每件事都是 Critical。
    Important 意味着此任务在修复之前不可信：错误或脆弱的行为、遗漏的需求、
    或你会因此阻止合并的可维护性损害——逻辑块的逐字重复、被吞掉的错误、
    不进行断言的测试。"覆盖率可以更广"和润色建议属于 Minor。
    如果计划或简报明确要求了本评审标准视为缺陷的内容（不进行断言的测试、
    逻辑块的逐字重复），那确实是一个发现——将其报告为 Important，标记为 plan-mandated。
    计划的作者不能给自己的作业打分；由人工伙伴决定。
    在列出问题之前先认可做得好的地方——准确的赞扬有助于实现者信任其余的反馈。

    ## 输出格式

    ### Spec Compliance

    - ✅ 符合 Spec | ❌ 发现问题: [缺失/多余/理解错误的内容，附 file:line 引用]
    - ⚠️ 无法从 diff 验证: [仅从 diff 无法验证的需求，以及控制器应检查的内容——
      与你能验证的所有内容的 ✅/❌ 判断一同报告]

    ### Strengths
    [哪些做得好？请具体说明。]

    ### Issues

    #### Critical（必须修复）
    #### Important（应该修复）
    #### Minor（改进建议）

    对于每个问题: file:line、问题所在、为何重要、如何修复（如果不显而易见）。

    ### Assessment

    **Task quality:** [已批准 | 需要修复]

    **Reasoning:** [1-2 句技术评估]
```

**占位符：**
- `[MODEL]` — 必填：按 SKILL.md 的模型选择部分选择审查者模型
- `[BRIEF_FILE]` — 必填：任务简报文件（`scripts/task-brief PLAN N` 打印路径；即实现者工作的依据文件）
- `[GLOBAL_CONSTRAINTS]` — 从计划的 Global Constraints 部分或 spec 中逐字复制的具有约束力的要求：确切的值、格式以及组件之间声明的关联关系（非流程规则——那些已在本模板中）
- `[REPORT_FILE]` — 必填：实现者写入其详细报告的文件
- `[BASE_SHA]` — 此任务之前的提交
- `[HEAD_SHA]` — 当前提交
- `[DIFF_FILE]` — 必填：控制器写入审查包的路径（`scripts/review-package BASE HEAD` 打印其写入的唯一路径；该包绝不进入控制器上下文）

**审查者返回：** Spec Compliance 判断（✅/❌/⚠️）、Strengths、Issues（Critical/Important/Minor）、Task quality 判断

一次修复分派可以一并处理 spec 缺口和质量发现；修复后的重新审查涵盖两个判断。
