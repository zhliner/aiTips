# 接收代码审查（Receiving Code Review）

## 概述

代码审查需要技术评估，而非情绪表演。

**核心原则：** 先验证再实施。先问清楚再假设。技术正确性优先于社交舒适。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：无反应地读完所有反馈
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对该代码库而言技术上是否合理？
5. 响应：技术性确认或有理有据的反驳
6. 实施：逐条处理，每条都测试
```

## 禁止的回应

**绝不：**
- "你说得完全正确！"（明确违反 instruction-file）
- "好观点！" / "好的反馈！"（表演性）
- "让我现在就实施"（在验证之前）

**应该：**
- 复述技术需求
- 提出澄清性问题
- 如果对方错了，用技术推理反驳
- 直接开始干活（行动 > 言辞）

## 处理不清晰的反馈

```
如果有任何一项不清楚：
  停止 - 先不要实施任何东西
  就不清楚的项目请求澄清

为什么：项目之间可能相关。部分理解 = 错误实现。
```

**示例：**
```
你的人类伙伴： "修复 1-6"
你理解 1、2、3、6。对 4、5 不清楚。

❌ 错误：先实现 1、2、3、6，之后再问 4、5
✅ 正确："我理解了 1、2、3、6 项。在继续之前需要澄清第 4 和第 5 项。"
```

## 不同来源的处理方式

### 来自你的人类伙伴
- **可信任** - 理解后实施
- **如果范围不清楚仍然要问**
- **不做表演性赞同**
- **直接行动**或技术性确认

### 来自外部审查者
```
在实施之前：
  1. 检查：对该代码库而言在技术上是否正确？
  2. 检查：是否会破坏现有功能？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：审查者是否理解完整上下文？

如果建议似乎不对：
  以技术推理反驳

如果无法轻易验证：
  如实说："没有 [X] 我无法验证这个。我应该[调查/询问/继续]？"

如果与你的人类伙伴之前做的决策冲突：
  停止，先和你的人类伙伴讨论
```

**你的人类伙伴的规则：** "外部反馈——保持怀疑，但仔细检查"

## 针对"专业级"功能的 YAGNI 检查

```
如果审查者建议"properly 实现"：
  在代码库中 grep 实际使用情况

  如果未被使用："这个 endpoint 没有被调用。移除它（YAGNI）？"
  如果被使用：那就 properly 实现
```

**你的人类伙伴的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，就不要添加。"

## 实施顺序

```
对于多条反馈：
  1. 首先澄清任何不清楚的内容
  2. 然后按以下顺序实施：
     - 阻塞性问题（损坏、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 逐个测试每个修复
  4. 验证没有回归
```

## 何时反驳

在以下情况下反驳：
- 建议会破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（不使用的功能）
- 对该技术栈在技术上不正确
- 存在遗留/兼容性原因
- 与你的人类伙伴的架构决策冲突

**如何反驳：**
- 使用技术推理，而非防御姿态
- 提出具体问题
- 引用能正常工作的测试/代码
- 如果涉及架构，请让你的人类伙伴参与

**如果你不敢当反驳：** 说出这种紧张感，然后告诉你的伙伴你发现的问题。他们会欣赏你的坦诚。

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述变更内容]"
✅ "好 catch——[具体问题]。已在 [位置] 中修复。"
✅ [直接修复并在代码中展示]

❌ "你说得完全正确！"
❌ "好观点！"
❌ "谢谢你指出！"
❌ "谢谢 [任何内容]"
❌ 任何感谢表达
```

**为什么不感谢：** 行动胜于言语。直接修复。代码本身就表明你收到了反馈。

**如果你发现自己要写"谢谢"：** 删掉它。改说修复了什么。

## 优雅地纠正自己的反驳

如果你反驳了但发现自己错了：
```
✅ "你是对的——我检查了 [X] 它确实 [Y]。正在实施。"
✅ "已验证并且你是正确的。我最初理解有误，因为 [原因]。正在修复。"

❌ 长段道歉
❌ 辩解为什么之前反驳
❌ 过度解释
```

陈述修正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演性赞同 | 陈述需求或直接行动 |
| 盲目实施 | 首先对照代码库验证 |
| 批量处理不测试 | 一次一个，每个都测试 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 首先澄清所有项目 |
| 无法验证，硬要继续 | 说明限制，请求方向 |

## 实际示例

**表演性赞同（差）：**
```
审查者："移除遗留代码"
❌ "你说得完全正确！让我移除那个……"
```

**技术验证（好）：**
```
审查者："移除遗留代码"
✅ "正在检查……构建目标是 10.15+，此 API 需要 13+。需要保留遗留代码以确保向后兼容。当前实现 bundle ID 有误——修复它还是放弃 pre-13 支持？"
```

**YAGNI（好）：**
```
审查者："properly 实现指标跟踪，包括数据库、日期过滤器、CSV 导出"
✅ "grep 了代码库——没有调用此 endpoint。移除它（YAGNI）？还是我遗漏了什么使用场景？"
```

**不清楚的项目（好）：**
```
你的人类伙伴："修复项目 1-6"
你理解 1、2、3、6。对 4、5 不清楚。
✅ "理解 1、2、3、6。需要澄清第 4 和第 5 项才能实施。"
```

## GitHub 帖子回复

在回复 GitHub 上的内联 review 评论时，应在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而非作为顶级 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，而非必须遵循的命令。**

验证。质疑。然后实施。

不做表演性赞同。始终保持技术严谨性。
