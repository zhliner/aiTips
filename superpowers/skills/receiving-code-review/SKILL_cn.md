# 代码审查接收

## 概述

代码审查需要技术评估，而不是情绪表演。

**核心原则：** 在实施之前验证。在假设之前提问。技术正确性优先于社交舒适。

## 响应模式

```
当收到代码审查反馈时：

1. 阅读：完整阅读反馈，不做出反应
2. 理解：用自己的话重述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对于这个代码库来说技术上合理吗？
5. 回应：技术性确认或有理有据的反驳
6. 实施：一次一项，逐项测试
```

## 禁止的回应

**永远不要：**
- "You're absolutely right!"（明确的指令文件违规）
- "Great point!" / "Excellent feedback!"（表演性的）
- "Let me implement that now"（在验证之前）

**应该：**
- 重述技术需求
- 提出澄清问题
- 如果错了，用技术推理反驳
- 直接开始工作（行动 > 言语）

## 处理不清楚的反馈

```
如果任何条目不清楚：
  停止 - 先不要实施任何东西
  就不清楚的条目提问

原因：条目可能相关。部分理解 = 错误实施。
```

**示例：**
```
your human partner: "Fix 1-6"
你理解了 1,2,3,6。对 4,5 不清楚。

❌ 错误：现在实施 1,2,3,6，稍后再问 4,5
✅ 正确："我理解了条目 1,2,3,6。在继续之前需要对 4 和 5 进行澄清。"
```

## 按来源处理

### 来自你的搭档
- **可信** - 理解后实施
- **仍然提问** 如果范围不清楚
- **不要表演性地同意**
- **跳到行动** 或技术性确认

### 来自外部审查者
```
在实施之前：
  1. 检查：对于这个代码库技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上都有效吗？
  5. 检查：审查者理解完整上下文吗？

如果建议看起来不对：
  用技术推理反驳

如果无法轻松验证：
  直说："我无法在没有 [X] 的情况下验证这一点。我应该 [调查/询问/继续] 吗？"

如果与你的搭档之前的决策冲突：
  停下来先和你的搭档讨论
```

**你的搭档的规则：** "外部反馈 - 保持怀疑，但仔细检查"

## YAGNI 检查 "专业" 功能

```
如果审查者建议"正确实现"：
  grep 代码库检查实际使用情况

  如果未使用："这个 endpoint 没有被调用。删除它（YAGNI）？"
  如果使用了：那就正确实现
```

**你的搭档的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，就不要添加它。"

## 实施顺序

```
对于多条目反馈：
  1. 首先澄清任何不清楚的内容
  2. 然后按以下顺序实施：
     - 阻塞问题（崩溃、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试每个修复
  4. 验证没有回归
```

## 何时反驳

在以下情况反驳：
- 建议会破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对于此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的搭档的架构决策冲突

**如何反驳：**
- 使用技术推理，而非防御性
- 提出具体问题
- 引用有效的测试/代码
- 如果是架构问题，让你的搭档参与

**如果你不好意思当面反驳：** 指出这种紧张感，然后告诉你的搭档你看到的问题。他们会欣赏你的诚实。

## 确认正确的反馈

当反馈确实正确时：
```
✅ "Fixed. [简要描述更改了什么]"
✅ "Good catch - [具体问题]. Fixed in [位置]."
✅ [直接修复并在代码中展示]

❌ "You're absolutely right!"
❌ "Great point!"
❌ "Thanks for catching that!"
❌ "Thanks for [anything]"
❌ 任何感谢表达
```

**为什么不需要感谢：** 行动说明一切。直接修复。代码本身就表明你听到了反馈。

**如果你发现自己正要写 "Thanks"：** 删掉它。改为陈述修复内容。

## 优雅地纠正你的反驳

如果你反驳了但是错了：
```
✅ "You were right - I checked [X] and it does [Y]. Implementing now."
✅ "Verified this and you're correct. My initial understanding was wrong because [原因]. Fixing."

❌ 长篇道歉
❌ 为你的反驳辩护
❌ 过度解释
```

陈述纠正事实然后继续。

## 常见错误

| 错误 | 修复 |
|---------|-----|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 一次一项，逐项测试 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 避免反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清所有条目 |
| 无法验证仍然继续 | 说明限制，请求指导 |

## 真实示例

**表演式认同（不好）：**
```
审查者："移除遗留代码"
❌ "你说得完全对！让我把它移除……"
```

**技术验证（正确）：**
```
审查者："移除遗留代码"
✅ "检查中……构建目标是 10.15+，这个 API 需要 13+。向后兼容需要保留遗留代码。当前实现的 bundle ID 有误——是修复它还是放弃 13 之前的支持？"
```

**YAGNI（正确）：**
```
审查者："实现完整的指标追踪，包括数据库、日期筛选、CSV 导出"
✅ "grep 了代码库——没有任何地方调用这个 endpoint。移除它（YAGNI）？还是有我遗漏的使用场景？"
```

**不清晰的项目（正确）：**
```
你的搭档："修复第 1-6 项"
你理解了 1、2、3、6。对 4、5 不清楚。
✅ "理解了 1、2、3、6。在实施之前，需要对第 4 和第 5 项进行澄清。"
```

## GitHub 线程回复

在 GitHub 上回复内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级 PR 评论。

## 底线

**外部反馈 = 需要评估的建议，不是需要遵循的命令。**

验证。质疑。然后实施。

不要表演性同意。始终保持技术严谨。
