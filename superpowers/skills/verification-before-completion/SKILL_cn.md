# 完成前验证（Verification Before Completion）

## 概述

在没有验证的情况下声称工作完成不是效率，是不诚实。

**核心原则：** 先有证据再有声明，永远如此。

**违反此规则的字面意义就是违反其精神。**

## 铁律

```
没有新的验证证据，不得做出完成声明
```

如果你没有在当前消息中运行过验证命令，你就不能声称它通过。

## 检入函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明此声明？
2. 运行：执行完整命令（全新、完整）
3. 读取：完整输出，检查退出码，统计失败数
4. 验证：输出是否确认该声明？
   - 如果否：用证据说明实际状态
   - 如果是：附带证据做出声明
5. 只有在此之后：做出声明

跳过任何步骤 = 撒谎，不是验证
```

## 常见失败

| 声明 | 需要 | 不足够 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、"应该通过" |
| Linter 无错误 | Linter 输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来好 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了、假设已修复 |
| 回归测试有效 | 红-绿循环已验证 | 测试通过一次 |
| Agent 已完成 | VCS diff 显示有变更 | Agent 报告"成功" |
| 需求已满足 | 逐行清单 | 测试通过 |

## 红线 - 停下

- 使用"应该""可能""似乎"
- 在验证之前表达满意（"太好了！""完美！""搞定了！"等）
- 即将在没有验证的情况下 commit/push/PR
- 信任 agent 的成功报告
- 依赖部分验证
- 想着"就这一次"
- 疲惫了只想快点结束
- **任何暗示成功但没有运行验证的措辞**

## 防止自我合理化

| 借口 | 现实 |
|--------|---------|
| "现在应该工作了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "Agent 说了成功" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分什么也证明不了 |
| "换种说法，规则就不适用了" | 精神大于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到: 34/34 pass] "所有测试通过"
❌ "现在应该通过了" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 编写 → 运行（通过） → 撤销修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ "我已经写了回归测试"（没有红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到: exit 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重新阅读计划 → 创建清单 → 逐项验证 → 报告差距或完成
❌ "测试通过了，阶段完成"
```

**Agent 委派：**
```
✅ Agent 报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任 agent 报告
```

## 为什么这很重要

来自 24 条失败记忆：
- 人工伙伴说"我不信你"——信任破裂
- 未定义的函数上线——会导致崩溃
- 缺失的需求上线——不完整的功能
- 时间浪费在虚假完成 → 重定向 → 返工上
- 违反："诚实是核心价值观。如果你撒谎，就会被替换。"

## 何时适用

**始终在以下情况之前：**
- 任何形式的成功/完成声明
- 任何形式的满意表达
- 任何关于工作状态的正面陈述
- 提交、创建 PR、任务完成
- 进入下一个任务
- 委派给 agent

**此规则适用于：**
- 完全一致的措辞
- 释义和同义词
- 成功的暗示
- 任何暗示完成/正确性的沟通

## 底线

**验证没有捷径。**

运行命令。读取输出。然后声称结果。

这不容商议。
