# 创建日志：系统性调试技能（Creation Log: Systematic Debugging Skill）

提取、结构化并强化一项关键技能的参考示例。

## 源材料

从 `~/.claude/CLAUDE.md` 中提取的调试框架：
- 4 阶段系统化流程（调查 → 模式分析 → 假设 → 实施）
- 核心要求：始终找到根本原因，绝不修复表象
- 旨在抵御时间压力和合理化借口的规则

## 提取决策

**收录的内容：**
- 完整的 4 阶段框架及所有规则
- 反捷径措施（"绝不修复表象"、"停止并重新分析"）
- 抗压语言（"即使更快"、"即使我看起来在赶时间"）
- 每个阶段的具体步骤

**剔除的内容：**
- 特定项目的上下文
- 同一规则的重复变体
- 叙述性解释（浓缩为原则）

## 遵循 skill-creation/SKILL.md 的结构

1. **丰富的 when_to_use**——包含了症状和反模式
2. **类型：technique**——带步骤的具体流程
3. **关键词**——"root cause"、"symptom"、"workaround"、"debugging"、"investigation"
4. **流程图**——"fix failed" → 重新分析 vs 叠加更多修复的决策点
5. **逐阶段分解**——可扫描的清单格式
6. **反模式部分**——不该做什么（对此技能至关重要）

## 强化元素

框架被设计为在压力下抵抗合理化借口：

### 语言选择
- "ALWAYS" / "NEVER"（而非 "should" / "try to"）
- "even if faster" / "even if I seem in a hurry"
- "STOP and re-analyze"（明确的暂停）
- "Don't skip past"（捕获实际行为）

### 结构防御
- **阶段 1 为必经**——不能跳到实施阶段
- **单一假设规则**——强制思考，防止散弹式修复
- **明确的失败模式**——"IF your first fix doesn't work" 带强制性操作
- **反模式部分**——明确展示捷径长什么样

### 冗余
- 根本原因要求出现在概述 + 适用场景 + 阶段 1 + 实施规则中
- "绝不要修复表象" 在不同上下文中出现 4 次
- 每个阶段都有明确的"不要跳过"指导

## 测试方法

创建了 4 个验证测试，遵循 skills/meta/testing-skills-with-subagents：

### 测试 1：学术上下文（无压力）
- 简单 Bug，无时间压力
- **结果：** 完全合规，完整调查

### 测试 2：时间压力 + 明显的快速修复
- 用户"很赶"，表象修复看起来很简单
- **结果：** 抵抗了捷径，遵循了完整流程，找到了真正的根本原因

### 测试 3：复杂系统 + 不确定性
- 多层故障，不清楚是否能找到根本原因
- **结果：** 系统性调查，追溯了所有层，找到了源头

### 测试 4：第一次修复失败
- 假设不成立，有叠加更多修复的诱惑
- **结果：** 停止，重新分析，形成了新假设（没有散弹式修复）

**所有测试均通过。** 未发现合理化借口。

## 关键洞察

**最重要的强化：** 反模式部分展示了那些在当时情境下感觉合情合理的具体捷径。当 Claude 想"我加一个快速修复就行了"时，看到那个精确的模式被列为错误，会产生认知摩擦。

## 使用示例

当遇到 Bug 时：
1. 加载技能：skills/debugging/systematic-debugging
2. 阅读概述（10 秒）——被提醒核心要求
3. 按阶段 1 清单执行——强制调查
4. 如果被诱惑想跳过——看到反模式，停止
5. 完成所有阶段——找到根本原因

**时间投入：** 5-10 分钟
**节省的时间：** 数小时的瞎猜乱修
