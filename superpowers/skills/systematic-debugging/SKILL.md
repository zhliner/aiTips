# 系统性调试（Systematic Debugging）

## 概述

随意修补浪费精力并制造新 Bug。快速补丁掩盖了底层问题。

**核心原则：** 在尝试修复之前，始终先找到根本原因。修复表象即为失败。

**违反此流程的字面含义即是违反调试精神。**

## 铁律

```
未完成根本原因调查，不得进行修复
```

若尚未完成阶段 1，就不得提出修复方案。

## 适用场景

任何技术性问题均适用：
- 测试失败
- 生产环境 Bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**尤其适用于以下情况：**
- 时间紧迫（紧急情况让猜测变得诱人）
- "只做一个快速修复" 看起来很明显
- 已经尝试过多次修复
- 之前的修复没起作用
- 尚未完全理解问题

**以下情况也不可跳过：**
- 问题看似简单（简单 Bug 也有根本原因）
- 时间匆忙（急于求成必然返工）
- 经理要求立刻修好（系统化比反复折腾更快）

## 四个阶段

必须完成每个阶段后才能进入下一阶段。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读 stack trace
   - 注意行号、文件路径、错误码

2. **可靠复现**
   - 能否稳定触发？
   - 确切步骤是什么？
   - 每次都会发生吗？
   - 若无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变更可能导致此问题？
   - Git diff、最近的 commit
   - 新的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，添加诊断 instrumentation：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，显示问题出在哪里
   然后分析证据以确定失败的组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这将揭示：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误出现在调用栈深处时：**

   参见本目录中的 `root-cause-tracing.md` 了解完整的回溯追踪技术。

   **快速版本：**
   - 错误数据来源于哪里？
   - 是什么以错误数据调用了这里？
   - 一直向上追踪直到找到源头
   - 在源头修复，而非表象处修复

### 阶段 2：模式分析

**先找到模式，再修复：**

1. **找到可用的示例**
   - 在同一代码库中定位类似的可工作代码
   - 什么与出问题的代码类似但却能正常工作？

2. **与参考实现对比**
   - 如果要实现某个模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 在应用前充分理解该模式

3. **辨别差异**
   - 可工作和出问题的之间有什么不同？
   - 列出每一项差异，不论多微小
   - 不要假设"这不可能是原因"

4. **理解依赖**
   - 这还需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做出尽可能小的变更来测试假设
   - 一次只改变一个变量
   - 不要一次修复多个事项

3. **确认后再继续**
   - 成功了吗？是 → 阶段 4
   - 没成功？形成新的假设
   - 不要在上面叠加更多修复

4. **不知道时**
   - 说出"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 进一步调研

### 阶段 4：实施

**修复根本原因，而非表象：**

1. **创建失败的测试用例**
   - 尽可能简单的复现
   - 尽可能使用自动化测试
   - 没有测试框架则使用一次性测试脚本
   - 在修复前必须有测试用例
   - 使用 `superpowers:test-driven-development` 技能来编写正确的失败测试

2. **实施单一修复**
   - 针对确定的根本原因
   - 一次只做一项变更
   - 不做"顺便"的改进
   - 不做捆绑的重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试被破坏？
   - 问题实际解决了吗？

4. **如果修复不成功**
   - 停止
   - 计数：已经尝试了多少次修复？
   - 如果 < 3：返回阶段 1，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 不要在未进行架构讨论的情况下尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复都在别处产生新的症状

   **停下来质疑基本面：**
   - 这个模式从根本上可行吗？
   - 我们是不是"单纯靠惯性在坚持"？
   - 应该重构架构，还是继续修复表象？

   **在尝试更多修复之前，与你的 human partner 讨论**

   这不是假设失败——这是架构错误。

## 红旗信号——停止并遵循流程

如果你发现自己这样想：
- "先快速修一下，之后再来调查"
- "试试改 X 看看行不行"
- "把多个改动一起做了，跑下测试"
- "跳过测试，我手动验证"
- "很可能就是 X 的问题，我来修一下"
- "我不完全理解，但这也许能行"
- "模式说 X，但我换个方式用"
- "主要问题有：[未调查就列出修复方案]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经试了 2 次以上）**
- **每次修复都在不同地方暴露新问题**

**所有这些都意味着：停止。返回阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（参见阶段 4 第 5 步）

## human partner 表明你做错了的信号

**注意以下纠正信号：**
- "这不是没发生吗？"——你做了未经验证的假设
- "它能告诉我们……吗？"——你应该添加证据收集
- "别猜了"——你还没有理解就在提修复方案
- "深度思考一下"——质疑基本面，而不仅是表象
- "我们被困住了？"（沮丧）——你的方法不奏效

**当你看到这些时：** 停止。返回阶段 1。

## 常见的合理化借口

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要走流程" | 简单问题同样有根本原因。对于简单 Bug 流程也很快。 |
| "紧急情况，没时间走流程" | 系统性调试比瞎猜试错更快。 |
| "先试一下这个，之后再来调查" | 第一次修复定了基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复站不住脚。先测试才能证明。 |
| "一次修多个省时间" | 无法隔离出什么起效了。还会导致新 Bug。 |
| "参考太长，我改改模式用" | 片面的理解必然导致 Bug。完整阅读。 |
| "我看到问题了，我来修" | 看到表象 ≠ 理解根本原因。 |
| "再试一次修复"（失败 2 次以上后） | 失败 3 次以上 = 架构问题。质疑模式，不要继续修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找到可用示例、对比 | 辨别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程揭示"没有根本原因"时

如果系统性调查表明问题确实是环境性、时序依赖或外部因素导致的：

1. 你已经完成了流程
2. 记录你调查过的内容
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志以便未来调查

**但是：** 95% 的"没有根本原因"情况都是调查不完整。

## 配套技术

以下技术是系统性调试的一部分，位于本目录中：

- **`root-cause-tracing.md`**——通过调用栈回溯追踪 Bug 以找到原始触发点
- **`defense-in-depth.md`**——找到根本原因后，在多个层级添加验证
- **`condition-based-waiting.md`**——用条件轮询替代任意超时等待

**相关技能：**
- **superpowers:test-driven-development**——用于创建失败的测试用例（阶段 4，第 1 步）
- **superpowers:verification-before-completion**——在声称成功之前验证修复是否有效

## 实际效果

来自调试实践：
- 系统性方法：15-30 分钟修复
- 随机修补方法：2-3 小时的反复折腾
- 首次修复成功率：95% vs 40%
- 引入的新 Bug：接近零 vs 常见
