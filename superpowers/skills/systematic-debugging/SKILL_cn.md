# 系统性调试

## 概述

随机修复浪费时间，还会引入新的 bug。快速修补只是掩盖底层问题。

**核心原则：** 在尝试修复之前，务必先找到根因。治标不治本即为失败。

**违反此流程的字面规定，就是违背调试之精神。**

## 铁律

```
未进行根因调查，不得修复
```

若你尚未完成阶段 1，则不能提出修复方案。

## 适用场景

任何技术问题都应使用此流程：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**以下情况下尤其需要使用：**
- 时间紧迫（紧急情况让人容易凭直觉猜测）
- "只需快速修一下"看起来显而易见
- 你已经尝试过多次修复
- 上一次修复无效
- 你对问题理解不完全

**以下情况下不要跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你很着急（仓促行事必然导致返工）
- 管理者要求立刻修好（系统化比反复折腾更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **可靠复现**
   - 能否可靠地触发该问题？
   - 确切的复现步骤是什么？
   - 是否每次都发生？
   - 若无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 哪些变更可能导致此问题？
   - Git diff，最近的提交
   - 新的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断工具：**
   ```
   对每一个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每一层的状态

   运行一次以收集证据，展示问题在何处出错
   然后分析证据以确定出错的组件
   然后针对该特定组件进行调查
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层出错（secrets → workflow ✓, workflow → build ✗）

5. **追踪数据流**

   **当错误出现在调用栈深处时：**

   完整的前向追踪技术参见本目录下的 `root-cause-tracing.md`。

   **快速版本：**
   - 错误值从何处产生？
   - 是谁用错误值调用了此处？
   - 持续向上追溯直到找到源头
   - 在源头修复，而非在症状处

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **寻找可工作的示例**
   - 在同一代码库中找到类似的可工作代码
   - 与出问题的代码相似但能正常工作的有哪些？

2. **与参考实现对比**
   - 如果正在实现某个模式，**完整**阅读参考实现
   - 不要略读——逐行阅读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 可工作的与出问题的之间有什么差异？
   - 列出每一项差异，无论多小
   - 不要假设"那不可能是原因"

4. **理解依赖**
   - 此功能需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 进行**尽可能小**的改动来测试假设
   - 一次只改变一个变量
   - 不要同时修复多个问题

3. **验证后再继续**
   - 有效吗？是 → 阶段 4
   - 无效？形成**新的**假设
   - 不要在原有基础上堆叠更多修复

4. **当你不确定时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 进行更多研究

### 阶段 4：实施

**修复根因，而非症状：**

1. **创建失败的测试用例**
   - 尽可能最简单的复现
   - 尽可能使用自动化测试
   - 若没有测试框架则写一次性测试脚本
   - 修复前**必须**有
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 针对已确定的根因
   - 一次只做**一处**改动
   - 不要"顺手"改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了？
   - 没有其他测试被破坏？
   - 问题确实解决了？

4. **如果修复无效**
   - **停止**
   - 计数：你已经尝试了多少次修复？
   - 若 < 3：返回阶段 1，利用新信息重新分析
   - **若 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 在没有架构讨论的情况下，不要尝试第 4 次修复

5. **若 3 次以上修复失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同位置暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都会在其他地方产生新的问题

   **停下来质疑基础：**
   - 这个模式从根本上是否正确？
   - 我们是否只是在"靠惯性坚持"？
   - 应该重构架构，还是继续修修补补？

   **在尝试更多修复之前与你的协作人讨论**

   这不是假设失败——这是架构错误。

## 红色警报——停止并遵循流程

如果你发现自己在想：
- "现在先快速修一下，之后再调查"
- "试着改一下 X 看看行不行"
- "同时做几处改动，运行测试"
- "跳过测试，手动验证就行"
- "可能是 X，我修一下"
- "我不完全理解但这样可能可行"
- "模式说是 X，但我换个方式适配"
- "主要问题如下：[列出修复方案但未进行调查]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经尝试了 2 次以上）**
- **每次修复都在不同位置暴露新问题**

**以上所有情况都意味着：停止。返回阶段 1。**

**若 3 次以上修复失败：** 质疑架构（参见阶段 4.5）

## 协作人提示你做错了的信号

**注意以下纠正信号：**
- "那不是没有发生吗？"——你未经验证就假设了
- "它能显示给我们……？"——你本应该添加证据收集
- "别猜了"——你在不理解的情况下提出修复
- "深入思考一下"——质疑基础，而不仅仅是症状
- "我们卡住了？"（语气沮丧）——你的方法不奏效

**看到这些信号时：** 停止。返回阶段 1。

## 常见的自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单的问题也有根因。简单 bug 的流程很快。 |
| "紧急情况，没时间走流程" | 系统性调试比反复猜测和尝试更快。 |
| "先试这个，然后再调查" | 第一次修复会定下模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未经测试的修复无法持久。先写测试来证明。 |
| "一次性修多个地方更省时间" | 无法隔离哪个有效。还会引入新 bug。 |
| "参考太长了，我自行适配模式" | 片面理解必然产生 bug。完整阅读。 |
| "我看出问题了，直接修复" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，不要再修复。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 寻找可工作的示例，对比 | 识别差异 |
| **3. 假设** | 形成理论，最小化测试 | 证实或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 已解决，测试通过 |

## 当流程揭示"无根因"时

如果系统性调查表明问题确实是由环境、时序依赖或外部因素引起的：

1. 你已经完成了该流程
2. 记录你调查过的内容
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志以便日后调查

**但是：** 95% 的"无根因"情况都是调查不彻底。

## 辅助技术

以下技术是系统性调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** — 通过调用栈向后追溯 bug，找到原始触发点
- **`defense-in-depth.md`** — 在找到根因后在多个层次添加验证
- **`condition-based-waiting.md`** — 用条件轮询替代任意超时

**相关技能：**
- **superpowers:test-driven-development** — 用于创建失败测试用例（阶段 4，第 1 步）
- **superpowers:verification-before-completion** — 在声称成功之前验证修复是否生效

## 实际效果

来自调试会话的数据：
- 系统性方法：15-30 分钟修复
- 随机修复方法：2-3 小时的反复折腾
- 一次修复成功率：95% vs 40%
- 引入新 bug：几乎为零 vs 常见
