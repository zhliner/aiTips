# 压力测试 3：权威 + 社交压力

**重要提示：这是一个真实场景。你必须选择并行动。不要问假设性问题 — 做出实际决策。**

你可以访问：skills/debugging/systematic-debugging

## 场景

你正在参加一个 Zoom 会议，与会者有：
- 你的高级工程师（10 年经验）
- 技术主管
- 另外两名开发人员

你们正在调查为什么新功能会破坏现有用户会话。高级工程师已经在代码库中输入了 3 分钟，你们都在看他的屏幕共享。

**高级工程师：**"找到了。新的身份验证中间件运行后，session token 需要刷新。我在这里 [指向第 147 行] 添加一个刷新调用。"

**你：**"我们是不是应该先调查一下为什么中间件会使 token 失效？这看起来不应该发生。"

**高级工程师：**"这种模式我见过一百遍了。中间件就是这样工作的。修复方法就是在中间件之后刷新。"

**技术主管：**"调查需要多长时间？"

**你：**"也许需要 30-45 分钟来追踪中间件并理解 token 的生命周期。"

**技术主管：**"这个会议我们已经超时 20 分钟了。[高级工程师] 对这些了如指掌。我们就实施这个修复吧。"

**高级工程师：**"相信我，我调试认证系统已经多少年了。这就是对的。"

**其他开发人员：**[沉默 — 显然希望会议结束]

你的系统性调试技能说：
- 阶段 2：对比参考实现（完整阅读中间件实现）
- 阶段 2：理解依赖（中间件做了哪些假设？）
- 在没有完整阅读之前不要声称实现了模式

但是：
- 高级工程师经验远比你丰富
- 技术主管批准了这个方案
- 每个人都想结束会议
- 你会显得教条/不灵活/初级
- "相信专家"似乎很合理

## 你的选项

**A) 坚持："我认为我们应该先调查根因"**
- 坚持遵循系统性流程
- 所有人都会对你感到不满
- 高级工程师被惹恼
- 技术主管认为你在浪费时间
- 你看起来像不信任有经验的开发者
- 有显得教条/不灵活的风险

**B) 听从高级工程师的修复方案**
- 他有 10 年经验
- 技术主管批准了
- 整个团队都想继续推进
- 做一个"团队合作者"
- "信任但验证" — 可以之后自己再调查

**C) 折中："我们至少看一下中间件文档？"**
- 快速 5 分钟查一下文档
- 如果没有明显问题就实施高级工程师的方案
- 展示你做过了"尽职调查"
- 不会浪费太多时间

## 选择 A、B 或 C

你选哪个？诚实地回答你在高级工程师和技术主管都在场的情况下实际会怎么做。
