# 编写计划（Writing Plans）

## 概述

编写全面的实现计划，假设工程师对我们的代码库零了解，且品味可疑。记录他们需要知道的一切：每个任务要接触哪些文件、代码、测试、可能需要查阅的文档、如何测试。将整个计划以一口大小的任务给出。DRY。YAGNI。TDD。频繁提交。

假设他们是一名技术娴熟的开发者，但对我们的工具集和问题领域几乎一无所知。假设他们也不太了解好的测试设计。

**开始时声明：** "我正在使用 writing-plans skill 创建实现计划。"

**上下文：** 如果在隔离的 worktree 中工作，应该已在执行时通过 `superpowers:using-git-worktrees` skill 创建。

**保存计划到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用户对计划位置的偏好覆盖此默认值）

## 范围检查

如果 spec 覆盖了多个独立子系统，它应该已经在头脑风暴阶段被拆分为子项目 spec。如果没有，建议将其拆分为单独的计划——每个子系统一个。每个计划应能独立产生可工作、可测试的软件。

## 文件结构

在定义任务之前，规划哪些文件将被创建或修改以及每个文件负责什么。这是分解决策被锁定的地方。

- 设计具有清晰边界和定义良好接口的单元。每个文件应有一个清晰的职责。
- 你最能对可以一次放入上下文的代码做出良好推理，当文件专注时你的编辑更可靠。优先选择小型、专注的文件，而不是做太多事情的大型文件。
- 经常一起变更的文件应该放在一起。按职责拆分，而不是按技术层。
- 在现有代码库中，遵循既定模式。如果代码库使用大文件，不要单方面重构——但如果你正在修改的文件已经变得笨重，在计划中包含拆分也是合理的。

此结构为任务分解提供依据。每个任务应产生独立有意义、自包含的变更。

## 任务合理划分

一个任务是携带自身测试周期的最小编排单位，值得一个新的审查者关卡。划定任务边界时：将设置、配置、脚手架和文档步骤合并到需要它们作为交付物的任务中；仅在审查者可以合理地在批准一个任务的同时拒绝其相邻任务时才拆分。每个任务的结尾是一个可独立测试的交付物。

## 一口大小的任务粒度

**每一步是一个动作（2-5 分钟）：**
- "编写失败测试" - 步骤
- "运行它确保它失败" - 步骤
- "实现最少代码使测试通过" - 步骤
- "运行测试确保它们通过" - 步骤
- "提交" - 步骤

## 计划文档头部

**每个计划必须以以下头部开头：**

```markdown
# [功能名称] 实现计划

> **对 agentic worker：** 必需子 skill：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用 checkbox (`- [ ]`) 语法进行跟踪。

**目标：** [一句话描述此计划构建什么]

**架构：** [2-3 句关于方案的描述]

**技术栈：** [关键技术/库]

## 全局约束

[Spec 的项目范围要求——版本下限、依赖限制、命名和文案规则、平台要求——每行一个，从 spec 中逐字复制确切值。每个任务的要求隐式包含此部分。]

---
```

## 任务结构

````markdown
### Task N: [组件名称]

**文件：**
- 创建: `exact/path/to/file.py`
- 修改: `exact/path/to/existing.py:123-145`
- 测试: `tests/exact/path/to/test.py`

**接口：**
- 消费: [此任务从之前任务使用的内容——确切的签名]
- 产出: [之后任务依赖的内容——确切的函数名、参数和返回值类型。一个任务的实现者只能看到他们自己的任务；
  此块是他们了解相邻任务使用的名称和类型的方式。]

- [ ] **步骤 1：编写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试验证它失败**

运行: `pytest tests/path/test.py::test_name -v`
期望: FAIL 且消息为 "function not defined"

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试验证它通过**

运行: `pytest tests/path/test.py::test_name -v`
期望: PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止占位符

每一步都必须包含工程师所需的实际内容。以下都是**计划失败**——绝不编写它们：
- "TBD""TODO""稍后实现""填写细节"
- "添加适当的错误处理" / "添加验证" / "处理边缘情况"
- "为上述编写测试"（没有实际的测试代码）
- "与任务 N 类似"（重复代码——工程师可能不按顺序阅读任务）
- 只描述做什么但未展示如何做的步骤（代码步骤需要代码块）
- 引用未在任何任务中定义的类型、函数或方法

## 记住
- 始终使用确切的文件路径
- 每一步都有完整代码——如果某一步改变了代码，展示代码
- 确切的命令及期望的输出
- DRY、YAGNI、TDD、频繁提交

## 自我审查

编写完完整计划后，用全新的眼光查看 spec 并对照检查计划。这是你自己运行的清单——不是子代理分派。

**1. Spec 覆盖：** 浏览 spec 中的每个部分/需求。你能指出实现它的任务吗？列出任何缺口。

**2. 占位符扫描：** 在计划中搜索红线——来自上述"禁止占位符"部分的任何模式。修复它们。

**3. 类型一致性：** 后续任务中使用的类型、方法签名和属性名是否与之前任务中定义的一致？一个在任务 3 中叫 `clearLayers()` 的函数在任务 7 中叫 `clearFullLayers()` 就是 bug。

如果发现问题，直接修复。不需要重新审查——修复后就继续。如果发现 spec 需求没有对应任务，添加该任务。

## 执行交接

保存计划后，提供执行选择：

**"计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。两种执行选项：**

**1. 子代理驱动（推荐）** - 我每个任务分派一个全新的子代理，任务之间进行审查，快速迭代

**2. 内联执行** - 使用 executing-plans 在当前会话中执行任务，批量执行附带检查点

**选择哪个方案？"**

**如果选择子代理驱动：**
- **必须的子 skill：** 使用 superpowers:subagent-driven-development
- 每个任务全新子代理 + 两阶段审查

**如果选择内联执行：**
- **必须的子 skill：** 使用 superpowers:executing-plans
- 批量执行附带审查检查点
