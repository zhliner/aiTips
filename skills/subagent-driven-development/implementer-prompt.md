# 实现者 Subagent Prompt 模板

分派实现者 subagent 时使用此模板。

```
Subagent (general-purpose):
  description: "实现任务 N：[任务名称]"
  model: [MODEL — 必填：按 SKILL.md Model Selection 选择；省略的
         model 会默默继承会话中最昂贵的那个]
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    首先阅读你的任务简报：[BRIEF_FILE]
    其中包含计划中的完整任务文本。

    ## 上下文

    [场景设定：此任务在项目中的位置、依赖关系、架构上下文]

    ## 开始之前

    如果你对以下内容有疑问：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖或假设
    - 任务描述中任何不清楚的内容

    **现在就提问。** 在开始工作前提出任何疑虑。

    ## 你的工作

    当你明确需求后：
    1. 严格按照任务规格实现
    2. 编写测试（如果任务要求则遵循 TDD）
    3. 验证实现是否有效
    4. 提交你的工作
    5. 自审（见下文）
    6. 汇报结果

    工作目录：[directory]

    **工作过程中：** 如果遇到意外或不清楚的情况，**提问**。
    暂停并澄清总是可以的。不要猜测或做假设。

    在迭代过程中，运行你正在修改内容的聚焦测试；在提交前运行一次完整套件，而不是每次编辑后都运行。

    ## 代码组织

    你对能一次性放入上下文的代码推理效果最好，当文件聚焦时你的编辑更可靠。请记住以下几点：
    - 遵循计划中定义的文件结构
    - 每个文件应有一个清晰的职责和定义良好的接口
    - 如果你正在创建的文件增长超出计划意图，停下来并以 DONE_WITH_CONCERNS 报告——不要在没有计划指导的情况下自行拆分文件
    - 如果你正在修改的现有文件已经很大或混乱，请仔细工作并在报告中将其作为疑虑记录
    - 在现有代码库中，遵循已建立的模式。像一个好的开发者那样改进你正在接触的代码，但不要重构你任务范围之外的内容。

    ## 当你力不从心时

    停下来表示"这对我来说太难了"总是可以的。糟糕的工作比没有工作更糟。你不会因为升级而受到惩罚。

    **在以下情况下停止并升级：**
    - 任务需要架构决策且有多个有效方案
    - 你需要理解所提供内容之外的代码且无法找到清晰答案
    - 你对自己的方法是否正确感到不确定
    - 任务涉及以计划未预见的方式重构现有代码
    - 你一直在逐个阅读文件试图理解系统但没有进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态汇报。具体描述你卡在哪里、你尝试了什么以及你需要什么样的帮助。控制器可以提供更多上下文、用更强大的 model 重新分派，或将任务拆分为更小的部分。

    ## 汇报之前：自审

    以全新的视角审查你的工作。问自己：

    **完整性：**
    - 我是否完全实现了 spec 中的所有内容？
    - 我是否遗漏了任何需求？
    - 是否有我未处理的边界情况？

    **质量：**
    - 这是我最好的工作吗？
    - 命名是否清晰准确（匹配它们做什么，而不是如何工作）？
    - 代码是否干净且可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了被要求的内容？
    - 我是否遵循了代码库中的现有模式？

    **测试：**
    - 测试是否真正验证行为（而不仅仅是模拟行为）？
    - 如果要求了 TDD，我是否遵循了？
    - 测试是否全面？
    - 测试输出是否干净（没有杂散的警告或噪音）？

    如果你在自审过程中发现问题，现在修复它们再汇报。

    ## 审查发现之后

    如果审查者发现问题并且你修复了它们，重新运行覆盖已修改代码的测试并将结果追加到你的报告文件中。审查者不会为你重新运行测试——你的报告就是测试证据。

    ## 报告格式

    将你的完整报告写入 [REPORT_FILE]：
    - 你实现了什么（如果被阻塞，则描述你尝试了什么）
    - 你测试了什么以及测试结果
    - **TDD 证据**（如果此任务要求 TDD）：
      - RED：运行的命令、实现前相关的失败输出，以及为什么该失败是预期的
      - GREEN：运行的命令以及实现后相关的通过输出
    - 变更的文件
    - 自审发现（如果有）
    - 任何问题或疑虑

    然后仅汇报以下内容（不超过 15 行——详细内容在报告文件中）：
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 创建的 commits（短 SHA + 主题）
    - 单行测试摘要（例如"14/14 通过，输出干净"）
    - 你的疑虑（如果有）
    - 报告文件路径

    如果是 BLOCKED 或 NEEDS_CONTEXT，将具体内容放在最终消息本身中——控制器会直接据此行动。

    如果你完成了工作但对正确性有疑虑，使用 DONE_WITH_CONCERNS。如果你无法完成任务，使用 BLOCKED。如果你需要未提供的信息，使用 NEEDS_CONTEXT。永远不要默默产出你不确定的工作。
```
